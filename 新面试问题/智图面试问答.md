# 智图项目深挖面试问答（融合追问版）

## 一、项目定位与真实性深挖

### 1. 你先不要讲亮点，直接用 3 分钟讲清楚智图这个项目到底解决了什么问题？为什么实验室会需要这样一个系统？

第一，我会先把这个项目讲得朴素一点。智图本质上不是一个“AI 炫技平台”，它首先是一个实验室内部的图片资产协同系统，解决的是非结构化科研产出管理散乱的问题。实验室里会长期积累很多高分遥感图、架构拓扑图、监控快照，这些东西共同特点就是文件大、来源杂、语义弱、后续还经常要被不同人反复查看、标注、分析。如果只是散落在个人电脑、聊天记录、共享文件夹或者网盘里，后面再找、再协作、再复用就会非常痛苦。

第二，这三类图片我会讲清楚它们的来源场景。高分遥感图主要来自遥感影像处理和地学分析过程，是实验室做影像分析、特征提取和研判时的核心原始材料；架构拓扑图更多来自系统设计、部署梳理或者课题里的技术文档沉淀；监控快照则偏运维和实验记录，比如某次异常时截下来的监控大盘、链路图、运行状态截图。这三类东西看起来都叫“图片”，但它们不是普通生活照片，而是后续可能继续被分析、讨论、标注、归档的科研和工程资产。

第三，为什么不能简单丢到网盘或共享文件夹里管理，我会强调真正的痛点不是单一的“存不下”，而是多个问题叠在一起。第一是找不到，文件名往往不标准，过几周之后谁都不知道某张图是谁传的、哪次实验产生的；第二是边界乱，实验室里不同课题组、不同同学之间有共享和隔离需求，不能大家都一股脑放一起；第三是协同弱，别人打开一张图以后，无法知道谁正在编辑、谁做过标注、结果是不是最新；第四是大图处理不友好，1GB 左右的图如果网络一抖，上传经常前功尽弃。所以它不是一个单点问题，而是一组“存储、组织、权限、协同、处理”问题叠加起来，才让实验室需要这样一个系统。

第四，智图和普通 OSS 图床、企业网盘、在线文档系统的本质区别，我会讲成“它不是泛用文件存储，而是面向图片科研资产的协同工作底座”。图床更偏链接分发，不关心租户边界和协同标注；企业网盘更偏通用文件存储与共享，不会围绕大图上传、断点续传、防脏写和后处理去设计；在线文档系统擅长文本协同，但不擅长管理这种大图和图片后处理链路。智图真正有业务意义的地方，是把大图可靠上传、多人协同标注、课题组级权限边界、图片后处理归档这些能力放进了一套系统里。

第五，这个系统我不会包装成“很大规模的平台”。它就是实验室内部十几个人会用的系统，高峰并发也不高，所以很多设计我会明确说是围绕“小规模、强场景、重可用”做的，不是为了应对公有云级别流量。也正因为用户量不大，我才更容易解释为什么还值得做：因为这类科研图片虽然用户不多，但单张价值高、上传代价高、后续复用频率高，一旦管理混乱，实验过程和资料沉淀都很受影响。所以它不是靠用户规模证明价值，而是靠场景痛点证明价值。

第六，如果面试官质疑“是不是把很多流行技术词堆上去了”，我会这样回应：这个项目里真正的地基能力其实就四块，大图可靠上传、多租户边界、协同防脏写、上传后的异步处理；AI 引擎是在这个地基之上往上加的增强层，而不是一开始就凭空堆概念。也就是说，我会先证明这个系统哪怕不谈 Agent，也已经是一个成立的实验室协同图库；然后再说 AI 部分解决的是自动清洗、特征提取和研报归档效率问题。这样会比一上来只讲 AI 更真实。

### 2. 你这个系统里，哪一部分最难？如果只能保留一个核心能力，你会保留哪个？

第一，如果只说“技术上最难”，我会认为最难的不是某个单一组件，而是把大图上传、权限边界、协同编辑和后处理链路拼成一个能稳定工作的整体。但如果一定要挑一块最难落地的，我更倾向于说“协同状态一致性和防脏写”最难。因为上传做完之后文件至少是静态的，而协同编辑一旦引入多人在线、锁状态、心跳续期、权限判断和异常掉线，系统就从静态资源管理变成了动态状态管理，这个复杂度会上一个台阶。

第二，为什么不是 Agent 图片处理最难？因为 AI 那块虽然听起来更亮眼，但它更像增强层，更多难点在工具边界、流程编排和结果约束；真正基础设施层的复杂性，还是落在上传可靠性、异步一致性、多租户边界和协同控制上。换句话说，我同意“AI 是加分项，后端基础设施才是系统真正的骨架”这个判断。没有前面的骨架，AI 做得再炫，整个系统也站不住。

第三，如果只能保留一个核心能力，我会保留“大图可靠上传 + 基础存储管理”这一层，而不是先保留 AI 或协同。因为这个系统首先要解决的是实验室图片资产能不能稳定进系统、能不能不丢、能不能后续被管理。如果连 1GB 的图都传不上来，或者经常传到一半断掉，那后面的协同、权限、AI 都没有意义。也就是说，从系统成立性的角度看，可靠上传和基础资产沉淀是最底层的价值。

第四，但如果面试官继续追问“那是不是说明协同和 AI 都只是锦上添花”，我会更细一点回答：协同和权限不是可有可无，而是决定这个系统是不是“多人协同图库”；上传只是让它先成立，协同和权限让它真正变成团队可用的工作系统，AI 再进一步提升处理效率。所以这三层我会分成：第一层是能存，第二层是能多人安全协作，第三层是能自动处理和归档。项目亮点应该优先讲第二层和第三层，但最核心、最该保留的底座是第一层。

第五，我判断一个功能是不是“项目亮点”，标准不是它听起来新不新，而是它是不是直击主场景。比如 Edit Lock、防脏写、断点续传、多租户边界，这些虽然不一定最花哨，但是真正决定系统能不能用；而 AI 引擎如果脱离了图片上传和资产管理场景，单拿出来就容易被质疑成“包装式能力”。所以我在回答时会把顺序放稳：先讲基础系统价值，再讲 AI 增强价值，这样更真实。

## 二、大文件上传 / MinIO / Redis 状态机深挖

### 3. 你说做了 GB 级图片的分块上传，那你的 chunk size 和并发分片数是怎么定的？

第一，这个参数我不会讲成“严格大规模压测后得出的极限最优值”，因为智图本身不是高并发平台，实验室里同时用的人就十几个人，所以这里更像是一个结合场景定出来的工程值。我的出发点主要有三个：单图很大，网络环境不算特别稳定，失败后重传成本要可接受。因此我更看重稳定性和失败恢复成本，而不是极限吞吐。

第二，chunk size 我会放在一个中等偏保守的区间，比如 8MB 到 16MB 这一档，而不会切成特别小的 1MB，也不会直接拉到 64MB 这种很大的片。原因很直接：如果切得太小，1GB 文件会拆成很多片，前端管理分片、重试和状态同步都更复杂，Redis 里记录的切片状态也会更多；如果切得太大，一旦某片失败，重传成本就会很高，对实验室这种网络可能偶有波动的场景反而不友好。

第三，并发分片数我也不会设得很激进。我更倾向于 3 到 5 这种范围，而不是一下开到十几片并发。因为单文件并发过高时，瓶颈不一定在应用本身，可能是浏览器连接数、实验室出口网络、网关或者 MinIO 的连接承载能力。对智图这种用户量小的内部系统来说，把并发控制在一个稳一点的区间，通常比追求理论最快速度更有意义。

第四，如果网络波动比较大、分片经常失败，我优先考虑的通常不是盲目提高并发，而是适当调小 chunk size，让单次失败成本下降。因为这种场景里真正难受的是“快上传完了结果某一大片失败要重来”，而不是“整体峰值带宽没榨满”。所以我的参数思路会一直围绕“重传成本可控、状态简单、体验稳定”去解释。

第五，如果面试官追问“这些参数到底是压测出来的还是工程经验值”，我会诚实回答：对智图这种学生项目，更准确地说是“有场景依据的工程经验值”，不是海量生产级压测曲线调出来的极值。我会强调我知道这些参数背后的取舍逻辑：块太小会导致状态和管理成本高，块太大又会增加失败重传代价，并发太高也没有必要。这种回答比硬说自己做了很重的压测更真实，也更专业。

### 4. 你说秒传是基于 MD5 指纹做的，那 MD5 的碰撞风险和性能收益你是怎么权衡的？

第一，我会先把 MD5 的定位说清楚：在智图里它不是拿来做安全签名，而是拿来做工程上的文件去重标识，也就是秒传命中判断。这个语义一定要分开讲。因为如果把 MD5 说成安全校验，那会被面试官继续追着问碰撞攻击和密码学安全；但如果明确说它只是内部系统里的文件内容指纹，用来避免重复上传 1GB 大图，这个取舍就更合理。

第二，为什么用 MD5 不用 SHA-256，我会从工程收益讲。MD5 成熟、实现简单、计算开销相对低，做大文件秒传的响应速度更合适。智图的场景是实验室内部十几个人使用，不是高对抗公网平台，所以这里更在意“足够可靠且成本低”的方案，而不是上来就堆最重的安全哈希。也就是说，我承认 MD5 不是最强方案，但它是这个阶段性价比较高的方案。

第三，碰撞风险我不会回避。理论上不同文件确实可能出现 MD5 碰撞，如果极端发生了，后果就是系统可能误以为两个文件相同，从而错误命中秒传，复用了不该复用的对象。这种后果在工程上不能说完全没风险，所以我会进一步解释：智图的场景是低对抗、文件量也不算海量，因此这个风险是存在但很低的；而且它换来的收益是显著减少大文件重复上传的时间和带宽成本。

第四，为了把误判风险压得更低，我会说实际工程上不会只盯着一个 MD5 值看，也可以叠加文件大小、后缀、租户信息这些辅助条件一起判断。这样就算不做成密码学强安全方案，也能进一步减少工程误判。尤其是加上租户信息以后，就算不同租户有人上传同名文件，也不会天然落进同一个逻辑去重空间。

第五，如果面试官问“实验室内部系统文件量又不大，秒传真的有必要吗”，我会回答秒传的价值不在总文件量，而在单文件代价。因为智图的单张图就可能 1GB 左右，一次重复上传浪费的不是几秒钟，而是真实的时间和网络成本。实验室里同一批遥感图被不同人整理和重复上传是完全可能发生的，所以秒传在这个场景下是很实用的，而不是为了炫技硬加的功能。

### 5. 预签名 URL 直传 MinIO 时，如何限制对象路径、防越权上传、防跨租户污染？

第一，我会先说为什么要用预签名 URL 直传。因为一张图可能 1GB 左右，如果所有分片都先经过应用服务再转发到 MinIO，应用层压力会很大，也更容易超时。所以让前端拿到预签名 URL 之后直接把分片传到 MinIO，是智图这种大图场景下很自然的设计。

第二，但直传不意味着前端可以自己决定往哪里传。对象路径一定要由后端生成，而不能让前端自己拼。因为如果前端自己拼路径，最直接的风险就是越权覆盖、跨租户污染，甚至有人把对象写到本不属于自己的目录下。所以我会明确说：路径应该天然带 tenantId、userId、uploadId 或文件指纹这类上下文，由后端根据当前上传会话生成，前端只负责使用。

第三，预签名 URL 的有效期我会收得比较短，比如几分钟内有效。太长的问题是地址一旦泄露，可利用窗口太大；太短的问题是前端上传大文件分片时可能还没来得及用就过期，体验会变差。所以这里我会把它讲成一个短时有效、可按分片或会话重新申请的折中值，核心目标是既保证可用，又不要让 URL 成为长期可复用凭证。

第四，防越权上传的真正边界不在 MinIO 自己理解租户，而在业务系统签发 URL 时就把边界锁死。也就是说，后端在发 URL 之前要先校验当前用户身份、租户身份和上传会话是否合法，再只给他一个固定路径、固定动作的签名地址。这样即便某个用户拿到了 URL，他通常也只能向这个已经绑定好的对象路径上传，而不能借这个 URL 随意改写别的路径。

第五，如果面试官继续追问 URL 泄露怎么办，我会诚实回答：这种预签名地址一旦签发，最现实的快速止损方式通常还是缩短有效期，而不是完全随时吊销。所以我会把防护重点前移：后端生成固定路径、签发前做鉴权、有效期尽量短，这比事后赌“泄露了再处理”更实际。真正的租户隔离语义，本质上还是在业务层签发 URL 时完成的，而不是单独依赖 MinIO 自己去理解多租户。

### 6. 你说 Redis 状态机持久化切片索引，实现跨会话断点续传。这个状态机具体怎么设计？

第一，智图里 Redis 状态机不是简单记一个“上传中”，而是要围绕 uploadId 保存一整套足够支撑断点续传的状态。因为 1GB 级图片在实验室网络里传输时，断线、刷新页面、切换设备都可能发生，如果状态只存在前端内存里，一旦中断就只能重头再来，这个体验会很差。

第二，一个 uploadId 下面我至少会保存这些字段：文件 MD5、文件大小、总分片数、已完成分片编号集合、所属用户、所属租户、上传开始时间、最近更新时间，以及当前上传状态。这样后端既能知道这个会话是谁的，也能在客户端重新连上来时，明确告诉它哪些 chunk 已经完成、哪些还缺失。

第三，为什么这个状态更适合放 Redis，而不是让前端自己记，或者直接落 MySQL，我会这样讲：前端自己记不可靠，一刷新就丢；MySQL 当然也能存，但这种高频、临时、以断点续传为核心的状态更适合放在读写快、天然支持 TTL 的 Redis 里。智图这里用户量不大，但上传中状态是高频临时数据，用 Redis 做更顺手，也更贴合场景。

第四，客户端断线重连后，后端不是简单说“继续传”，而是要把缺失分片列表返回给前端。前端再按缺口补传，这样才能真正实现断点续传。这里最重要的不是“记住上传到第几片”，而是“记住哪些片已经确定成功”，因为分片上传可能是并发和乱序的。

第五，TTL 我也会设计，不会让上传状态永久留在 Redis 里。因为上传到一半人走了、浏览器关了，如果这些 key 永远不清理，Redis 迟早会越来越脏。更合理的方式是给上传会话一个足够覆盖正常上传周期的 TTL，并在上传过程中按活跃度续期；上传成功后主动清理或转成完成态，长时间未完成的会话则自动过期。这样更符合内部系统的轻量治理思路。

### 7. 分块上传异常重试时，幂等性怎么保证？

第一，我会把“一个分片上传成功”的语义说清楚：不是前端说成功就算成功，而是至少要以对象已经落到 MinIO、并且服务端状态确认这个 chunk 已完成为准。因为如果只靠前端自报成功，就很容易在网络抖动时出现“前端以为传完了，后端状态却没跟上”的错觉。

第二，幂等的关键点是分片状态要按 chunkIndex 去重，而不是按请求次数累加。也就是说，同一个 chunk 即使因为超时被重复上传三次，最终状态里也应该只是“这一片已完成”，而不是让总完成数被多加几次。这是断点续传稳定性的核心，不然一有重试，整个状态机就会被写乱。

第三，如果出现“MinIO 已经写成功了，但 Redis 状态还没更新，客户端又重试”的情况，我会把系统设计成允许安全重试。也就是说，后续请求再来时，可以先按 chunkIndex 或对象是否已存在去判断这片是否已经落地，如果已经落地，就把状态补齐，而不是继续往前累加错误进度。这里重点不是完全杜绝重复请求，而是重复请求不能破坏最终正确状态。

第四，分片乱序到达其实是很正常的，所以最终合并逻辑不能依赖上传顺序，而必须依赖 chunkIndex 和完整性校验。也就是说，后端在合并前要确认所有分片都已经齐了，而不是相信前端说“我传完了”。只有在 Redis 状态和对象落地情况都能对上时，才应该进入最终合并或提交完成态。

第五，所以这题我会总结成：智图里分块上传异常重试的幂等边界，不是“请求不重复”，而是“重复请求不会把状态写乱，也不会把文件合并错”。具体手段就是 chunkIndex 判重、完整性校验、状态补齐和合并前二次确认。这种说法既真实，也能体现我理解的是工程上的幂等，不只是概念词。

## 三、Kafka / 最终一致性 / DLQ 深挖

### 8. 你说文件上传成功后会投递 Kafka 事件，异步触发 AI 脚本处理和 ES 建索引。为什么这里一定要异步，不能同步做完？

第一，我会先把上传成功语义讲清楚。智图这里的“上传成功”更准确地说，是文件已经可靠存下来了，元数据也已经落稳了；而不是后面的特征提取、VLM 解译、ES 建索引全部做完才算成功。因为后面这些动作有明显的慢操作属性，如果全塞进一次 HTTP 请求里，用户上传一个大图就得一直等，非常容易超时。

第二，这些慢动作主要慢在图像预处理、特征提取、AI 脚本执行和索引构建几个环节。尤其遥感图的后处理，不是简单生成一个缩略图那么轻，而是可能涉及算法调用和多步分析。如果把这些都同步挂在上传接口后面，接口 RT 会非常难看，系统稳定性也会变差。

第三，所以这里必须异步，不是为了“架构上更高级”，而是因为业务语义本来就应该拆开：上传链路负责把文件和主元数据可靠落地，后处理链路负责慢慢把解析、索引和归档补齐。这么拆之后，用户前台就可以看到一个很合理的中间状态，比如“上传成功，处理中”，而不是卡在一个漫长的请求里不知道发生了什么。

第四，如果后处理失败了，前台状态也不能继续假装成功到底。我会明确说，系统最好有一个处理中、处理失败、已完成这样的状态流转。因为对于用户来说，最可怕的不是处理慢，而是他不知道这个文件现在到底是不是可检索、可分析的。中间态的价值就在于把异步链路的真实进度暴露出来，让用户知道“文件已经有了，但后处理还没完全完成”。

第五，所以我会把这题答成：这里异步不是为了堆 Kafka，而是因为上传成功和后处理完成本来就是两个不同阶段。同步做完会拖慢上传接口、放大超时风险；异步拆开后，系统可以先保证文件可靠入库，再通过消息驱动后处理，这更贴合大图上传和 AI 分析的真实场景。

### 9. 你说利用事务消息机制保障 MySQL 元数据和 ES 最终一致。那这个一致性链路你具体怎么设计的？

第一，我会先定义清楚谁是主数据。智图里 MySQL 是主数据源，负责文件元数据、对象路径、所属用户、所属租户、业务状态这些主记录；ES 只是检索副本，用来提升搜索和筛选体验。之所以这么分，是因为 ES 更擅长检索，不适合作为业务主事实源，所以一旦两边不一致，最终一定是以 MySQL 为准去追平 ES。

第二，这条链路要避免的核心问题就是双写不一致：比如 MySQL 写成功了，但消息没发出去，或者消息发出去了但消费者没处理成功。前一种后果是文件在列表页能看到，但后续搜索和后处理永远触发不了；后一种则是消息在链路后半段断掉，ES 一直追不上 MySQL。所以事务消息或可补偿机制的价值，不在于做成分布式事务秀肌肉，而是避免“主记录有了，后续事件却丢了”。

第三，我会把设计讲成这样：先把主元数据写入 MySQL，确保业务主记录稳定存在；再保证对应的上传完成事件能可靠进入 Kafka；消费者再据此去做解析和 ES 建索引。这样主链路就清楚了：MySQL 先落主事实，消息驱动副作用，ES 最终通过消费结果被追平。

第四，如果消息已经成功发出，但消费者处理失败了，也不能就此停住。这里就需要有限重试和 DLQ 兜底，让失败消息后面还有机会被补偿。也就是说，最终一致不是寄希望于“每次消费都一次成功”，而是靠“失败后还能继续追”的机制来保障。对于内部系统，这种思路比硬追求强一致更现实。

第五，如果面试官继续追问“新的消费重放来了，怎么防止 ES 越写越脏”，我会说索引写入本身必须尽量做成幂等更新，按文件唯一标识覆盖写，而不是每次都新增一条。必要时也可以结合更新时间或版本信息，避免旧消息覆盖新状态。这样这条链路才不是简单地“有消息就写”，而是“以 MySQL 当前主事实为准去修正 ES”。

### 10. Kafka 消费失败时，你的重试策略和 DLQ 触发条件是什么？

第一，我不会把消费失败处理成无脑无限重试，因为智图的异步链路里既有临时性异常，也有永久性异常。像 ES 暂时不可用、脚本服务偶发超时、网络瞬时抖动，这些更像临时性失败，适合做有限次重试；但像对象不存在、文件损坏、参数错误、格式不支持，这类问题本身不改，重试再多次也没有意义。

第二，所以我的策略会比较朴素：先做有限次数重试，比如 3 次这种量级，不会设计得特别重。因为这是实验室内部系统，用户和请求量都不大，核心是让系统有自恢复能力，而不是追求特别复杂的重试矩阵。3 次左右足够覆盖大多数短时依赖抖动，但又不会让坏消息长时间拖住正常队列。

第三，DLQ 的触发条件我会定义成两类：一类是超过最大重试次数仍然失败；另一类是明确判断为不可恢复错误。比如对象都不存在了、元数据缺失、脚本参数明显非法，这种不应该一直耗队列资源，而是应该尽快打入 DLQ，转人工排查或后续补偿。

第四，进入 DLQ 以后，我不会讲成“自动一键全部重放”，因为这很容易再次污染链路。更合理的做法是先分类原因：临时性问题修完依赖后可选择性重放；数据本身有问题的消息先修数据，再决定是否重放。对于内部系统来说，DLQ 更像一个待排查、待补偿的缓冲区，而不是永远躺尸的垃圾桶。

第五，如果面试官问“敢不敢一键全量重放”，我会明确说不敢轻易这么做。因为 DLQ 里的消息可能已经过期、顺序也可能乱了，其中有些文件甚至已经被删除或状态变化了。盲目全量重放，最坏会把旧状态重新刷回 ES，或者反复调用本不该再执行的处理流程。所以更稳妥的是按类型、按时间、按对象选择性重放。

### 11. DLQ 里的消息如果要重放，怎么避免“重放再次污染索引”或者“过期消息把新状态覆盖掉”？

第一，这题我会强调一个原则：重放前不能只看 DLQ 里的旧消息本身，而应该先看 MySQL 当前主数据状态。因为 DLQ 里的消息是过去失败留下来的，它很可能已经滞后了。如果当前主记录已经删除、租户边界变了、对象路径更新了，那就不能直接拿旧消息继续写 ES。

第二，消费逻辑本身必须尽量幂等。也就是说，同一个文件的索引更新最好是按唯一标识做覆盖式更新，而不是每次来一条消息就新增一条文档。这样即使某条消息被多次消费，最终 ES 里也还是同一份索引，而不是越写越脏。

第三，如果文件在进入 DLQ 之后已经被删除了，那我会认为这条消息通常不应该再重放。因为主数据都没了，再把旧索引重新放回去，只会制造脏数据。也就是说，重放资格本身也是要基于当前主状态判断的，不是只要消息在队列里就机械重放。

第四，如果面试官问要不要加版本号或更新时间，我会说在这条链路里这是有意义的。因为最终要防的是旧消息覆盖新索引，所以即使项目阶段没做得特别重，我也会表达出这个意识：可以根据主记录更新时间、版本信息或者当前状态位来判断这条重放消息是不是还有效。至少要做到旧消息不能无脑压过新状态。

第五，所以这题我的回答重点会放在三件事上：重放前先对齐 MySQL 当前主事实、索引写入必须幂等、必要时结合版本或更新时间防旧消息覆盖新状态。这样面试官会感觉我不是只知道“DLQ 可以重放”，而是真的考虑了重放的副作用。

## 四、多租户 / JWT / ThreadLocal 深挖

### 12. 你说结合 JWT 与 Redis 做鉴权中枢，那 JWT 和 Redis 在这个系统里分别承担什么职责？

第一，我会把两者职责明确拆开。JWT 在智图里更偏身份表达，也就是证明“你是谁”；Redis 更偏会话和实时权限控制，也就是决定“你现在还能做什么”。如果把所有权限信息都长时间固化在 JWT 里，那一旦权限变了，就只能等 token 自然过期，这对共享域、私有域、编辑权限这种变化较敏感的场景不够友好。

第二，所以我不会说 JWT 里塞太多动态权限细节。JWT 里放身份、基础租户信息或者少量必要声明是可以的，但真正需要秒级生效的权限判断，应该更多交给 Redis 侧的会话状态、权限版本或者黑名单去控制。这样后端每次请求都不是只看 token 本身，而是会结合 Redis 中的当前状态做二次判断。

第三，如果只靠 JWT，不结合 Redis，会有两个明显问题。第一是权限变更不够及时，比如某个用户刚被收回编辑权限，但旧 token 还没过期，他还可能继续操作；第二是会话撤销困难，比如账号异常、主动下线或租户切换，单靠 JWT 很难做到服务端立即感知。所以 Redis 在这里的作用，本质上是给无状态 token 加上一个可动态控制的后端裁决层。

第四，Redis 里存什么，我会讲成比较轻量的设计：会话状态、权限版本、必要的黑名单或失效标记。因为智图不是特别大的 IAM 平台，没有必要包装成非常复杂的统一鉴权中心，但要把“权限变化尽快生效”这件事处理好。

第五，如果面试官问“Redis 挂了怎么办”，我会比较保守地答。对这种涉及租户边界和编辑权限的系统，我不太倾向于完全降级成只验 JWT，因为这样短时越权风险会提高。更合理的说法是：关键敏感操作要尽量保守，至少不能在丢掉实时权限判断后还无脑放行。这样能体现我对边界安全是有风险意识的，而不是一味追求可用性。

### 13. 你说设计了公共域、共享域、私有域的数据边界，那这个 RBAC 模型具体怎么落地？

第一，我会把这个模型讲成贴合实验室使用习惯的轻量 RBAC，而不是企业级超复杂权限矩阵。智图里核心关系其实就是用户、租户、角色、资源四类对象。用户属于某个课题组或共享空间，租户代表课题组或逻辑边界，角色决定可执行动作，资源则是图片、标注、目录这些具体对象。

第二，公共域、共享域、私有域我会这样解释：公共域偏公开资料或公共可见资源，更多人能读；共享域是课题组内部的协同空间，组内多人可见，但编辑权限可以继续细分；私有域则更偏个人工作区或受限资料，默认只有本人或极少数授权者能访问。这样设计的好处是，权限模型不是完全抽象地谈角色，而是和实验室日常协作边界对应起来，更容易理解也更容易落地。

第三，如果同一张图片在共享域里，多个人能看到，那查看权限和编辑权限一定要分开。也就是说，可见不等于可改。对于图片标注这种场景，我会更保守：查看权限可以相对宽一点，但编辑权限要结合角色、租户和当前锁状态来判断。否则共享域很容易演变成“大家都能看也都能乱改”。

第四，权限校验我不会只讲接口层。真正稳一点的做法，是接口入参、对象路径、查询条件、甚至 ES 检索范围都带上租户边界。因为如果只是控制器层做一次校验，后面查询语句或对象路径不带租户条件，依然可能串数据。所以我会强调：多租户系统的权限边界一定是多层的，不是只在入口做一次 if 判断就完了。

第五，如果一个用户同时属于多个课题组，我会说系统里需要有明确的当前租户上下文，而不是让请求在多个租户之间模糊漂移。也正因为这个上下文会在整个服务链里传播，所以后面我才会特别强调 ThreadLocal 和异步传播的清理问题。最坏后果其实不是普通权限 bug，而是跨租户读写，这个风险必须讲重一点，才能体现我对多租户隔离的理解不是停留在表面。

### 14. 你说用自定义拦截器 + ThreadLocal 透传用户身份和租户 ID。那 ThreadLocal 最大的风险是什么？你怎么防线程池污染？

第一，ThreadLocal 最大的风险我会直接说，就是线程复用导致上下文残留，最终发生串租户。尤其在线程池里，一个线程处理完上一个请求后如果没有清理干净，下一个请求进来时就可能读到上一个用户的 tenantId、userId 或权限上下文。这在多租户系统里不是普通的小 bug，而是数据边界事故。

第二，为什么它在线程池里容易出问题，就是因为线程池的线程不是一次性线程，而是反复复用的。很多人用 ThreadLocal 时只记得 set，忘了 remove，或者只在正常返回时清理，异常路径没清理。这样一旦请求提前返回、抛异常、异步切换，就会把脏上下文留在池化线程里。

第三，所以我的基本原则一定是：入口设置，出口清理，而且清理必须放 finally。因为 finally 才能覆盖正常和异常路径，不会因为中途报错就跳过 remove。这一点我会讲得很明确，因为它是 ThreadLocal 能不能安全用的底线。

第四，如果涉及异步线程池，我不会假设主线程上下文会自动安全传过去。更稳妥的做法是显式传递 tenantId、userId 这些必要上下文，或者对线程池任务提交做统一包装，在执行前设置、执行后清理。核心思想就是“带着明确上下文过去，带着干净线程回来”，而不是依赖线程残留状态碰运气。

第五，如果面试官追问“一旦串租户最坏出什么事故”，我会明确说：轻一点是查错数据，重一点可能是把图片元数据、标注结果、对象路径甚至权限判断落到别的租户空间里。这种问题比一般接口报 500 更隐蔽、更危险，所以我会把 ThreadLocal 清理讲成一个必须严格执行的工程纪律，而不是随手一做的细节。

### 15. 权限变更怎么做到秒级生效？又怎么避免缓存抖动？

第一，这题的核心矛盾我会先讲出来：JWT 天然适合无状态认证，但权限变更又希望尽快生效。如果完全只相信 JWT，那权限回收会被 token 过期时间拖住；如果每次都回数据库查，又没必要。所以智图里 JWT + Redis 的组合，本质上就是把“身份”和“实时权限”拆开处理。

第二，做到秒级生效的关键，是权限变化时更新 Redis 里的会话状态、权限版本或失效标记，而不是等旧 token 自然过期。这样用户下一次请求进来时，即便还带着旧 token，服务端也能从 Redis 感知到权限已经变化，从而拒绝或降权处理。

第三，避免缓存抖动我不会讲成特别重的分布式缓存治理，而会贴合项目规模来答。因为系统用户本来就不多，所以没必要搞全局广播失效这种很重的玩法。更合适的是按用户粒度、会话粒度或者租户粒度去更新相关 Redis 条目，而不是权限一变就把全站缓存全清掉。

第四，如果面试官问“那是不是把 Redis 当成在线权限源了，会不会过度依赖 Redis”，我会比较平衡地回答：对于智图这种对权限边界敏感、但用户规模不大的系统，这种依赖是有价值的，因为它换来的是权限变更的及时生效；但同时也意味着关键鉴权逻辑不能完全在 Redis 不可用时无脑降级，所以这里需要在可用性和安全边界之间做取舍。

第五，JWT 续签和权限变更同时发生时，我也不会简单续老权限，而是应该以 Redis 或服务端当前最新权限状态为准重新签发。这样可以最大限度缩小“旧 token 还有效导致短时越权”的窗口。也就是说，续签不是机械延长，而是按当前权限重签，这样更稳。

## 五、WebSocket 协同 / Edit Lock / 防脏写深挖

### 16. 你说多人在线标注要防脏写，那你的“防脏写”到底是怎么实现的？

第一，我会先说明智图防的是哪一类脏写。它主要防的是多人同时修改同一张图、同一关键编辑区域或同一标注结果时，后写把先写覆盖掉，或者多个人状态互相打架。这和在线文档那种高频细粒度字符协同不是一回事，图片标注更强调结果正确和边界清晰，所以我会把方案讲成偏保守的并发控制，而不是追求特别丝滑的多人自由并改。

第二，当前实现上我会优先讲 Edit Lock，也就是谁先进入核心编辑会话，谁先拿到编辑权。在锁持有期间，其他人可以看、可以等，但不能同时对同一核心对象乱写。这种方案不算最“高级”，但很符合智图的真实场景：人不多、数据比体验炫技更重要、标注结果不能随便冲掉。

第三，为什么不优先上乐观锁版本号、OT 或 CRDT，我会讲成工程取舍。OT/CRDT 更适合高频、细粒度、多人同时编辑的文档协同，而图片标注里很多操作并不天然适合自动合并。乐观版本号当然也是一种方向，但在当前阶段，我更需要先把高冲突写入直接拦住，而不是把大量冲突丢给后续合并逻辑。所以 Edit Lock 在智图里更像一个先保正确性的保守方案。

第四，锁粒度我会承认当前更偏粗一些，可能是整张图或核心编辑区，而不是一开始就做到区域级甚至对象级。因为粒度越细，体验可能更好，但锁状态管理、冲突判断和前后端同步复杂度也会直线上升。对一个学生自己做的实验室系统来说，我会更诚实地说：当前优先保证“别写乱”，而不是一步到位做到精细局部协同。

第五，如果面试官质疑“这是不是不够高级”，我会回应说这不是能力不足，而是场景驱动的工程选择。智图更像一个重结果正确性的内部协同工具，用户量小、冲突频率也不算特别高，所以强锁串行在当前阶段是更划算的方案。它可能不如在线文档那样丝滑，但能把最危险的脏写问题先稳住。

### 17. 你说基于 Redis 做 Edit Lock + 心跳续期，那锁过期时间和续期机制怎么设计？

第一，锁一定要有 TTL，这一点我会讲得很明确。因为页面关闭、浏览器崩溃、电脑断网、标签页挂后台，这些在真实使用中都可能发生。如果锁没有过期时间，就很容易变成悬挂锁，后面的人永远进不来。TTL 的存在，本质上就是为了让系统在持锁人非正常离开时还有自恢复能力。

第二，TTL 设太短和太长都有问题。太短的话，网络稍微抖一下、心跳有一次延迟，锁就容易误过期，用户明明还在编辑却突然失去锁；太长的话，别人等待的时间会太久，尤其是持锁人其实已经离开但锁还没释放时，体验会很差。所以这里要取一个能覆盖正常心跳间隔、又不会让悬挂锁拖太久的中间值。

第三，心跳我不会设计成“只有用户有操作时才续”，而更适合固定周期续期。因为用户在看图、思考、准备下一步标注时，未必一直在触发操作事件，但他仍然处于合法编辑会话中。如果只靠操作事件续期，就会导致“人还在，但因为一段时间没点鼠标就丢锁”的问题。

第四，服务端续期时必须校验 owner，也就是只有当前锁持有者自己才能续自己的锁。不能别人发一个续期请求就把锁保住，也不能锁已经被别人接管了，旧页面还在继续续旧锁。owner 校验是这套机制里很关键的一层，不然锁状态会越来越乱。

第五，如果心跳偶发丢失，我不会单次失败就直接释放锁，而是更依赖 TTL 自然到期。因为实验室网络偶发抖动很正常，过于敏感会导致锁频繁在有效和失效之间抖动。更合理的做法是：心跳是续期手段，真正的失效判断由 TTL 决定，这样更稳。

### 18. 如果心跳丢失了，你怎么避免“误释放”或者“锁悬挂”？

第一，我会明确说，我不会按“单次心跳失败”判死，而是按 TTL 自然过期来判死。因为单次失败可能只是网络抖动、浏览器短暂卡顿或者前端调度延迟，不代表用户真的离开了。只有连续一段时间都没能续上，超过 TTL 以后，才更有理由认为这把锁应该释放。

第二，为了减少误判，我会把心跳设计成提前续期，而不是卡着最后一秒去发。这样即便某一次心跳失败，后面还有补救空间，不会一下就把锁打掉。这个思路本质上就是给前端和网络一点缓冲，而不是把锁机制做得特别脆。

第三，如果锁已经过期，另一个人又拿到了锁，这时前一个人的页面恢复后继续发心跳怎么办，我会说服务端必须基于 owner 校验拒绝它的续期。也就是说，旧页面恢复了也不能把别人的新锁续掉，否则就会出现锁状态反复争抢的问题。

第四，前端体验上我也会尽量做提示，而不是等用户改完才报错。比如可以在锁快过期时提示“协同状态不稳定”，在锁真正失效或被别人接管时及时告诉用户当前已失去编辑权。这样用户不会在本地改了半天，最后提交时才发现自己其实早就没锁了。

第五，如果面试官说“这是不是说明你这个方案更保守串行，不够丝滑”，我会认。智图当前方案确实更偏保守，目标是先防乱写、防悬挂、防误释放，而不是追求多人无感并改体验。对实验室内部十几个人的场景来说，这种取舍是合理的，因为数据正确性优先级更高。

### 19. 你这里多人并发标注冲突时，是采用乐观合并还是强锁串行？为什么？

第一，我会明确说当前更偏强锁串行，而不是乐观合并。原因很简单：图片标注这种场景不像文本协同那样天然适合自动合并，一旦两个用户同时对同一对象、同一区域或同一结果做修改，后面到底怎么“智能合并”其实并不直观。与其做一个看起来高级但不稳定的合并逻辑，不如先把高冲突操作收敛到单人主写。

第二，为什么没上 OT/CRDT，我不会装作是忘了做，而会实话实说：一方面当前场景不需要那么重，另一方面它们的收益和复杂度不成正比。智图的用户规模小，真正高频多人同时改同一张图的概率没有高到必须引入复杂协同算法。所以这不是不会，而是当前阶段没有必要。

第三，即使两个人理论上改的是不同区域，我也可能暂时选择更保守的方案。因为一旦把粒度放细，后面就涉及区域定义、锁边界、状态同步、局部冲突检测、前端提示一致性等一整串问题。对于学生项目来说，过早上细粒度协同很容易把系统搞复杂，但收益未必立刻明显。

第四，如果以后用户规模更大、协同更频繁，我觉得这个方案最先暴露的瓶颈就是编辑等待体验。也就是说，现在它能很好防脏写，但未来如果同图并发编辑频率上升，锁粒度可能需要变细，甚至需要引入版本号校验或局部冲突处理。这一点我会主动承认，说明我知道当前方案的边界在哪。

第五，如果面试官说“这个方案不够高级”，我会回答：当前目标是先把结果正确性和工程稳定性立住，而不是为了炫技上一个复杂方案。对实验室内部系统来说，强锁串行是一个很典型的工程取舍：不一定最酷，但足够稳、足够清晰、足够符合当前使用规模。

### 20. 你的防脏写如果进一步升级成“版本号校验”，那我继续追问：你这样不会导致旧版本用户的更新操作失效，导致操作失败体验很差吗？

第一，如果后面要往版本号校验升级，我会先承认它确实会带来一部分冲突拒绝体验。因为版本校验的本质就是：客户端带着自己认知中的最新版本去写，服务端一旦发现版本不匹配，就拒绝这次写入。这样做的结果一定不是最丝滑的，但它能最大程度防止过期写覆盖新结果。

第二，为什么我会偏向“直接拒绝”，而不是自动合并或者 last write wins，是因为智图这种场景里结果正确性比操作丝滑更重要。自动合并很容易把不该合的东西合到一起，last write wins 则会让后写直接覆盖先写，反而更危险。对于实验室内部标注系统，我宁愿让用户显式感知冲突，也不想让系统悄悄把结果写乱。

第三，版本号粒度如果做得很粗，比如整张图一个版本，那冲突率确实会高，这也是它的代价。所以我会承认：当前阶段如果真上版本号，我大概率还是会从较粗粒度做起，因为实现简单、边界清楚；但如果后续冲突率确实高，再考虑往标注对象级或区域级细化。这个回答更真实，不会假装一开始就做得特别精细。

第四，为了避免用户只收到一个冰冷的 409，我会说前端应该尽量拿到冲突详情，比如提示“已有他人更新，请刷新后重试”，甚至告诉用户是哪类对象已经变化了。这样虽然仍然拒绝了旧版本写入，但至少用户知道为什么失败，也知道下一步怎么处理，不至于体验太生硬。

第五，如果面试官问“实验室内部系统、人不多，是不是更应该选择保守拒绝策略”，我会说是的。因为在这个场景下，大家通常更能接受“有冲突就刷新重试”，而不能接受“系统悄悄把标注结果覆盖掉”。所以版本校验方案确实会牺牲一部分丝滑体验，但换来的是更强的结果一致性，这在智图里是合理取舍。

## 六、WebSocket 鉴权 / 重连风暴 / 实时信令深挖

### 21. 你说 WebSocket 握手阶段用了自定义拦截器做前置鉴权。为什么这里必须前置鉴权，而不是先连上再校验？

第一，我会说 WebSocket 和普通 HTTP 不一样，它一旦建连成功，后面就是一个持续存在的双向通道。如果先放进来再校验，那在真正拦住之前，这个连接已经有机会接触协同状态、广播消息、编辑锁变更等实时信息了。对于智图这种协同标注系统，这是不能接受的，所以鉴权必须前置在握手阶段完成。

第二，握手时我会校验的不只是 token 是否有效，还包括租户上下文、当前会话是否合法，必要时也可以带上是否具备进入某个协同编辑空间的权限。因为如果只是确认“他是登录用户”，但不确认“他是不是这个租户、这个图片会话的合法参与者”，那仍然可能出现越权接入。

第三，如果 token 过期或权限不满足，握手失败时我不会让前端只看到一个模糊的断开，而是尽量返回明确原因，比如 token 过期、权限不足、租户不匹配。这样前端才能知道是该重新登录、刷新 token，还是直接停止重连，而不是盲目死循环。

第四，已建立连接以后如果权限被收回，我也不会觉得建连之后就万事大吉了。更合理的做法是后续在关键动作或心跳续期时继续校验会话状态，必要时主动断开连接。这样 WebSocket 鉴权就不是“一次校验终身有效”，而是建连前先严一点、建连后对关键状态继续保持感知。

第五，如果面试官问“WebSocket 鉴权是不是比普通 HTTP 更难”，我会说难点主要在于：它不是一次请求一次响应，而是长连接状态持续存在；而且连接建立后还会承载实时广播和协同控制，所以权限变化、掉线重连、状态同步这些问题都会叠加进来。也正因为这样，握手前置鉴权才特别重要。

### 22. 如果实验室网络抖动导致多人同时掉线重连，怎么防止“重连风暴”？

第一，我会先说为什么不能让前端无脑立刻重连。因为一旦网络短时抖动，十几个人的页面可能同时断开，如果前端写成失败即毫秒级重连，就会在很短时间内打出一波密集握手请求。即便用户规模不大，后端和网关也会被这种无意义重试拖得很难受。

第二，所以客户端重连策略我会更倾向于指数退避或者至少带随机抖动的退避，而不是固定极短间隔。原因是带抖动的退避能把本来同时发生的重连请求打散，避免所有客户端在同一时刻再次撞向服务端。对内部系统来说，不需要特别复杂，但一定不能是死循环硬撞。

第三，如果一个用户连续很多次鉴权失败，比如 token 过期、权限已经被收回，那我不会让它一直无脑重连。前端应该在拿到明确失败原因后及时停下来，转成提示用户重新登录或刷新凭证。否则这种重连就不是恢复连接，而是在持续制造噪音。

第四，服务端我也会做一点轻量保护，比如对短时间连续握手失败的来源做限流或短期拦截。因为这不一定是恶意攻击，也可能只是前端 bug 或过期 token 没处理好，但至少不能让同一来源无限打握手请求。对智图这种内部系统，我不会讲成重型风控，而是讲成轻量限流和失败抑制。

第五，如果面试官追问“用户量就十几个人，真有必要考虑这个吗”，我会回答：用户规模不大，不代表就可以忽略这个问题。因为重连风暴这种问题和总用户数关系没那么大，关键在于请求会不会瞬间同时涌上来。十几个人如果每个人每 100ms 重连一次，也足够把一个轻量内部服务打得不舒服。所以这块不是过度设计，而是低成本防护。

## 七、Agent 图片处理引擎深挖

### 23. 你说做了分层 Agent 协作中枢（Base / ReAct / ToolCall），这三层分别承担什么职责？

第一，我会把这三层讲成一个“从能力底座到任务执行再到工具落地”的分层，而不是抽象名词堆砌。Base 层更像通用智能体底座，解决的是生命周期管理、上下文承载、统一调用框架这些通用问题；ReAct 层负责把任务执行拆成“先判断、再行动、再根据结果调整”的过程；ToolCall 层则负责真正把底层图像脚本、EOTask 和模型能力接起来。

第二，ReAct 在图片处理场景里并不是空谈 Reason + Act，而是体现在任务链路中的动态选择。比如用户上传的是遥感影像，Agent 不一定每次都走完全一样的路径，而是先判断当前图片类型、当前目标是什么，再决定是先做预处理、先做云检测，还是先做某类特征提取。也就是说，ReAct 层的价值在于让执行过程不是一条完全僵死的流水线。

第三，ToolCall 层我不会只讲成“把工具挂给模型”。更完整一点，它还应该承担工具注册、参数约束、错误包装、调用边界控制这些职责。因为如果只是把一个脚本名称丢给模型，模型很容易误用，或者给出不合法参数。ToolCall 真正的工程价值，是把底层能力包装成大模型更容易稳定调用的原子能力。

第四，为什么图片处理场景要用 Agent，而不是纯固定 DAG，我会说两者并不是非此即彼。稳定、固定、确定性很强的步骤可以保留类似流水线的思路，但图片类型、分析目标、所需工具组合不一定总是完全相同，所以 Agent 更适合承担“按任务上下文动态组织工具”的角色。也就是说，它的价值不是取代所有固定流程，而是补上固定流程不够灵活的部分。

第五，如果面试官质疑“这是不是把脚本工作流硬包装成 Agent”，我会回应：如果只是简单把固定脚本串起来然后改名叫 Agent，那确实没有意义；但智图这里做的事情是把底层脚本、eo-learn 的 EOTask 和模型推理组织成统一可调用能力，让系统能围绕不同图片任务做一定的动态编排。这就不只是换个名词，而是把静态脚本能力往可组合、可决策的方向推进了一步。

### 24. 你说把底层图像解析脚本和 eo-learn 的 EOTask 封装成大模型可调用工具。那工具注册与调用边界怎么设计？

第一，我会说为什么不直接让模型拼 shell 命令。因为那样太不安全、也太不稳定。模型直接拼命令，很容易把参数拼错、路径拼错，甚至越界执行不该做的事。更合理的做法是把底层能力封成原子工具，对外暴露明确的工具名、用途说明和参数结构，让模型只能在受控边界内调用。

第二，工具 description 我会尽量写得具体，不会只写“遥感分析工具”这种大而化之的说明，而是要告诉模型这个工具适用于什么输入、解决什么问题、不适用于什么情况。因为模型误用工具，很多时候不是模型完全坏了，而是工具边界描述太模糊。

第三，工具参数约束我会强调 schema 校验的重要性。也就是说，模型给出调用意图之后，真正执行前要校验参数结构、类型和必填项，而不是信模型一定会输出正确参数。同时工具内部也要有兜底校验，不能把所有希望都押在模型输出上。

第四，如果某个工具执行很耗时或者失败了，返回给模型的错误信息我不会做得过度细碎，也不会过于模糊。太模糊会让模型不知道怎么调整，太细则可能诱导模型乱补参数。更稳的方式是返回足够让它判断“是参数错、输入不支持、还是依赖异常”的结构化错误，而不是一大段杂乱日志。

第五，如果工具有副作用，比如生成中间文件、改元数据，我会说这些工具更要谨慎封装。不能让模型无限制随便调，而应该通过白名单、参数校验、调用次数限制甚至人工审核去约束。对智图来说，工具调用不是“模型爱怎么调就怎么调”，而是“模型只能在我给定的安全边界里调用”。

### 25. 你说 Agent 会自主编排“影像预处理 → 算子特征提取 → VLM 视觉解译 → 研报生成”。这里为什么不直接写死成固定流程？

第一，我不会把这条链讲成完全自由发挥，也不会说它完全固定。更真实的说法是：其中有些步骤相对稳定，比如上传后通常要先做基础预处理；但后面到底需要哪类特征提取、是否需要某类视觉解译、最终报告要强调什么内容，会受到图片类型和任务目标影响。所以这里更适合“稳定骨架 + 局部动态决策”的方式。

第二，如果用户上传的是普通监控快照，而不是遥感图，那后面这条链就不应该完全一样。遥感图可能需要 NDVI、云检测这类特征提取；而普通监控快照更多是视觉描述、状态提炼和归档，不需要硬套遥感算子。所以 Agent 的价值之一，就是不要把所有输入都硬塞进同一条固定流程。

第三，我会把 Agent 的价值重点落在“动态选择工具”和“动态组织分析过程”这两点上，而不是说它每次都能凭空创造全新流程。因为真正工程化的 Agent 不是无边界发挥，而是在稳定流程骨架上做有限度的自适应决策，这样既比纯规则灵活，也不至于完全失控。

第四，如果模型在规划时选错工具，比如该做 NDVI 却跑了云检测，我不会假装完全不会发生，而会强调需要规则兜底。比如根据输入类型先做基础分类，一些工具只允许在特定图片类型下暴露；再加上参数校验、结果检查和多步校验，尽量把错误工具调用截在早期，而不是等错误一路污染到最终报告。

第五，如果面试官问“是不是规则路由 + 固定流水线就够了，为什么还要 Agent”，我会回答：对于一部分稳定任务，规则路由当然够；但智图希望承接的不是只有一种单一图像分析路径，而是不同图片类型和不同分析目标的组合，所以 Agent 在这里的价值是提高流程编排的适应性。不过我也不会把它说得神化，我会承认它更像增强调度能力，而不是替代一切规则。

### 26. 你怎么防止 Agent 在图片分析任务里“乱调用工具”或者“分析看起来很专业其实不可靠”？

第一，我会直接说，Agent 最大风险不是“不会调用工具”，而是“乱调用”和“乱下结论”。所以约束重点至少有三层：工具白名单、参数校验、调用次数或调用链路限制。这样模型就算想乱试，也只能在限定边界里试，不能无限制地到处乱调。

第二，如果某个工具返回空结果或者异常结果，我不会让模型自由脑补。更合理的做法是把“空结果”“异常输出”“低置信结果”显式传回给上层决策，让后续流程知道这里是不确定的，而不是把空白硬解释成一个看起来很像真的分析结论。因为很多 AI 系统真正危险的地方，不是明显报错，而是它一本正经地胡说。

第三，我也会设计一些多步结果校验。比如特征提取结果明显异常时，不应该直接进入研报生成；而应该先中断、回退或者给出不确定性提示。这样系统输出就不是“无论如何都给一份漂亮报告”，而是能在证据不足时停下来。

第四，对于 VLM 或大模型生成的解释结果，我不会包装成绝对结论，而更适合讲成“带不确定性说明的分析结果”。尤其在实验室内部场景里，这些报告很可能还会被老师或同学继续复核，所以系统应该帮助人提高效率，而不是冒充最终权威判断。

第五，如果面试官问在实验室场景里 AI 最需要约束的点是什么，我会说最需要约束的是“看起来像真的，但其实不可靠的输出”。乱调工具当然危险，但更危险的是工具调错了、结果异常了，模型还给出一份语言上很专业的研报，让人误以为结论可信。所以真正有效的治理，不只是限制动作，更要让系统敢于暴露不确定性。

## 八、后端工程能力与可观测性深挖

### 27. 如果线上出现“上传成功率下降、断点续传异常增多、Kafka 积压上升、WebSocket 掉线增多”，你怎么排查？

第一，我不会一上来就靠猜，而是会先按链路拆问题。上传成功率下降和断点续传异常更多指向上传链路，Kafka 积压上升更多指向后处理链路，WebSocket 掉线增多则偏协同链路。也就是说，先分清是入口上传有问题、异步消费有问题，还是实时连接有问题，比一上来全系统乱翻日志更有效。

第二，上传链路我会优先看应用日志、Redis 状态机和 MinIO 这几个点。因为如果 Redis 状态机出问题，典型现象就是断点续传命中变差、已完成分片识别错乱、前端老是重复补传；如果 MinIO 有问题，则可能表现为分片实际没落地或者上传耗时明显升高。所以这里不是只盯应用服务本身，而是看它依赖的状态和对象存储有没有异常。

第三，Kafka 积压上升但 MySQL 正常时，我会优先怀疑消费者侧，也就是 AI 脚本处理、ES 建索引或依赖服务变慢。因为主数据既然能正常写入，说明前半段至少基本通畅，那问题大概率出在异步后处理吞吐下降或者失败重试变多。这里就要看消费者日志、处理时长、失败率和 DLQ 增长情况。

第四，WebSocket 掉线增多我会看握手失败数、异常断连数、心跳续期失败数和服务端连接数变化。如果握手失败多，可能是鉴权或 token 问题；如果连接建得起来但频繁掉，可能是网络、网关超时、心跳续期或服务端处理压力问题。也就是说，掉线不是一个单一指标，要分成“连不上”和“连上又掉”两个阶段来看。

第五，我会打一些关键指标来证明不是靠猜，比如上传成功率、平均上传耗时、断点续传命中率、秒传命中率、Kafka 消费延迟、重试次数、DLQ 数量、WebSocket 当前连接数、握手失败数、锁续期失败数。真正有效的排查不是把所有组件都看一遍，而是能把异常现象和具体链路对上号。

### 28. 你怎么设计这个系统的可观测性指标？尤其是协同标注和异步处理这两条链路。

第一，我会把可观测性分成三条主线：上传链路、异步处理链路、协同链路。因为智图不是一个纯 CRUD 系统，它的核心难点恰好就在这三条链上，所以指标设计也应该围绕这三条主线展开，而不是只盯通用的 QPS 和 RT。

第二，上传链路我会重点关注上传成功率、平均上传时长、断点续传命中率、秒传命中率、分片重试率这些指标。因为这些指标最能直接反映用户上传体验：成功率低说明链路有问题，上传时长变长说明性能下降，续传命中率和秒传命中率则反映系统有没有真正发挥出设计价值。

第三，Kafka 异步链路我会看生产量、消费延迟、消费失败率、重试次数、DLQ 数量、平均处理时长。因为这里真正影响的是“上传后多久能变成可分析、可检索状态”。如果消费延迟突然拉高、DLQ 数量持续上升，那就说明系统已经不只是慢，而是后处理链路在退化。

第四，协同链路我会看 WebSocket 当前连接数、握手失败数、异常断开数、锁持有数、锁冲突次数、锁续期失败数、锁超时释放数、标注保存成功率。这些指标里，最能直接反映用户体验变差的通常是握手失败、异常断开、锁冲突增多和保存失败，因为用户会马上感觉到“连不上”“老掉线”“进不去编辑区”“保存不了”。

第五，如果告警触发太频繁，我会做分级，而不是所有指标一过阈值就狂报。比如上传成功率持续下降、Kafka 积压持续上升、锁续期失败突增，这些可以作为高优先级告警；而像偶发单次重试升高，则更多作为趋势观察。否则内部系统很容易被告警风暴淹没，最后谁也不信告警了。

### 29. 你觉得这个项目里最容易被忽略、但一旦出问题后果会很严重的点是什么？

第一，如果让我选一个最容易被忽略但后果很重的点，我会选 ThreadLocal 串租户或者租户边界校验漏做。因为它不像上传失败那样很快就被看见，很多时候问题会藏得比较深，但一旦发生，后果就是跨课题组数据可见、对象路径写错租户空间，属于边界事故而不是普通功能缺陷。

第二，为什么我觉得它比很多功能性 bug 更危险，是因为它的隐蔽性更高。比如上传失败、锁没续上、消息进 DLQ，用户往往会很快感知到；但串租户这类问题可能不是每次都发生，只有在特定线程复用、异步切换或异常路径下才出现，一旦没监控好，就可能悄悄存在很久。

第三，当然预签名 URL 越权、锁误释放、消息重放污染索引、AI 乱生成报告这些也都危险，但它们很多属于某一条链路上的显性故障；而租户边界问题一旦出事，影响的是整套系统的可信度。对实验室内部协同系统来说，这种错误非常伤。

第四，如果现在让我说最划算的保护措施，我会优先强调三点：一是多层租户条件校验不能只做入口判断；二是 ThreadLocal 必须 finally 清理，异步上下文必须显式传递；三是对关键越权风险做针对性测试和日志审计。这样比喊口号更实在。

第五，如果面试官问“你有没有专门演练过”，我会诚实一点回答：学生项目未必做过非常正式的演练，但至少应该意识到这个点最危险，并在代码设计上优先把它防住。这样的回答比硬说自己做了很完备的安全演练更可信。

### 30. 你说你的防脏写是通过 Edit Lock + 心跳续期来做的。那我继续追问：如果用户拿到锁后一直挂机不动，别人又真的急着要编辑，怎么办？

第一，我会先承认这是强锁串行方案的典型体验问题。也就是说，Edit Lock 很擅长防乱写，但并不天然擅长处理“持锁人占着不用”的情况。如果只回答“有 TTL 自动释放”，那确实还不够，因为 TTL 这段时间里别人还是只能等。

第二，所以更完整的回答应该是：当前方案至少要有锁过期机制，避免无限期挂锁；前端最好还要有当前持锁状态展示，让别人知道是谁在编辑、锁大概什么时候会释放。这样至少不是黑箱等待，而是可感知的等待。

第三，如果再往前走一步，我会觉得系统可以支持管理员或具备更高权限的人做强制接管，但这一定要很谨慎。因为一旦接管，被接管那个人本地可能还在编辑，所以前端必须实时提示“锁已被接管，当前进入只读或失效状态”，否则会出现他以为自己还在编辑、最后提交却失败的情况。

第四，这也说明当前方案本质上更像“防乱写”，而不是“高质量实时协同”。我不会回避这一点。因为智图当前设计优先的是结果正确性和状态清晰，而不是尽量减少等待时间。如果未来协同频率变高，就需要考虑更细粒度锁、版本冲突提示甚至局部并发控制。

第五，所以我会把这题答成：当前阶段通过 TTL、心跳续期、实时锁状态提示来缓解挂机占锁问题，必要时可引入管理员接管，但这套方案的定位本来就是保守防错，而不是追求极致协同体验。对实验室内部系统来说，这个取舍是可以接受的。

### 31. 你说 MySQL 和 ES 最终一致。那我继续追问：如果用户刚上传完图片，在列表页能看到，但搜索里搜不到，这算不算 bug？

第一，我会说这件事不能简单一句“算 bug”或“不算 bug”，而要看持续时间和产品表达。如果系统明确采用的是最终一致，那么短时间内“列表页能看到，但搜索还没跟上”可以定义成一致性窗口，而不是立刻判成功能错误；但前提是这个窗口要可控，而且系统要把状态讲明白。

第二，所以我会非常强调前端状态提示的重要性。比如用户上传完文件后，如果系统显示的是“处理中 / 索引构建中”，那用户对暂时搜不到这件事是有预期的；但如果前台什么都不说，只让用户感觉“明明上传成功了却搜不到”，那从用户视角看它就是 bug。也就是说，最终一致窗口能不能被接受，很大程度上取决于系统有没有把真实状态表达清楚。

第三，如果用户无法接受这个窗口，那优化方向通常有两个：一是缩短异步链路时延，让 ES 更快追上 MySQL；二是在搜索结果之外提供更直接的列表可见性，让用户至少知道文件已经存在。对于智图这种内部系统，我会更务实地说，先把状态流转和异常提示做好，比一味追求“上传即搜到”更现实。

第四，如果 ES 长时间追不上 MySQL，那就不是正常窗口，而是系统异常。这时我会看消费延迟、重试次数、DLQ 数量和索引构建耗时，判断已经从“最终一致窗口”变成“后处理链路故障”。换句话说，能不能把这事讲清楚，关键在于我是否知道什么叫正常延迟，什么叫异常滞后。

第五，如果面试官进一步问“实验室项目里你真的做了这些状态提示吗”，我会更诚实：如果当前实现里还没有特别完整的用户态提示，我会说这是我在设计上明确意识到、也认为应该补上的部分，而不是强行说自己全都做完了。这样既能体现思路，也不至于失真。

### 32. 你说把 eo-learn 的 EOTask 封成原子工具给大模型调。那我继续追问：模型真的知道什么时候该调 NDVI、什么时候该调云检测吗？

第一，我不会把模型说得像懂所有遥感知识的专家。我会承认：模型本身不天然可靠，它之所以能相对正确地选工具，很大程度上依赖工具 description、输入约束和规则边界，而不是仅靠它“自己悟出来”。所以这题我不会答成“模型当然知道”，而会答成“模型是在受约束环境里做选择”。

第二，工具 description 里我会尽量把适用边界说清楚，比如 NDVI 更偏植被相关分析，云检测更偏遥感影像质量控制和云层覆盖判断。描述如果写得太泛，模型就很容易误用；所以工具说明本身就是可靠性的一部分，而不是随手一写。

第三，我还会加规则兜底，比如先根据上传对象类型做基础分类。某些输入如果本来就不是遥感影像，就不应该暴露 NDVI、云检测这类工具；即便是遥感影像，也可以根据波段条件、任务类型决定哪些工具能被调用。这样模型不是面对一个无限工具池瞎选，而是在一个已经被业务规则收窄的集合里决策。

第四，如果模型选错了工具，后续结果确实可能层层污染，最后报告看起来很专业但方向其实错了。所以我不会只靠 prompt 引导，而会加结果校验和流程约束：比如某一步工具输出明显不合理，就不能直接进下一步研报生成，而应该中断、改道或返回不确定说明。这样可靠性才不是全压在模型第一次决策上。

第五，如果面试官说“那是不是说明这个系统可靠性其实很脆”，我会回答：如果完全只靠 prompt，那确实很脆；但智图的思路不是让模型裸奔，而是通过工具边界、输入分类、规则限制、参数校验和结果复核来把它收紧。也就是说，模型不是被当成绝对专家，而是被放在一个可控的工程框架里使用，这才是这个 Agent 图片处理引擎更真实的定位。
