# 智图项目面试问答

## 一、智图系统深挖（存储/一致性/协同）

### 你们的分块上传大小、并发分片数如何确定？

第一，这个项目的文件场景和普通图片站不一样，智图主要处理的是实验室里的高分遥感图、架构拓扑、监控快照，其中遥感图一张图能到 1GB 左右，所以我当时定分块策略时，核心不是追求特别高的并发吞吐，而是优先考虑上传稳定性、失败后重传成本，以及实验室同学日常网络环境下的可用性。

第二，分块大小我会定在一个中等偏保守的范围，比如 8MB 到 16MB 这一档，而不会切得特别碎。因为如果切成 1MB 这种很小的块，1GB 文件会拆出上千个分片，前端管理复杂，Redis 记录状态也会很多；但如果切成 64MB 甚至更大，一旦某一片上传失败，重传成本就太高，对实验室里不太稳定的网络其实不友好。所以我更倾向于讲成“这是一个结合大文件、低并发、重稳定场景做出来的折中值”。

第三，并发分片数我也不会说做得特别激进。这个系统本身并发量不高，平时就十几个人在用，所以没必要把单文件并发拉到十几二十片去压榨带宽。我会控制在 3 到 5 个并发分片这种比较稳的范围。这样做的好处是前端和 MinIO 都比较稳定，同时也能避免浏览器、网关或对象存储连接数被瞬间打满。

第四，我回答面试时会强调，这个参数不是企业级海量上传场景里那种“精细压测得出的极限值”，而是学生自己做系统时结合实际使用环境定出来的工程值。因为智图不是短视频平台，也不是公有云网盘，重点不是几千人同时上传，而是让实验室同学上传一张 1GB 左右的大图时，别因为网络抖动前功尽弃。

第五，所以总结下来，这个项目里分块大小和并发数的确定依据主要有三点：一是图片非常大，失败重传代价高；二是用户少，并发不高，没必要做极限优化；三是实验室场景更重稳定和断点续传体验。所以我会把它讲成一个“稳定优先、维护简单、适合内部使用”的参数设计。

### MD5秒传在碰撞风险与性能上的工程权衡是什么？

第一，MD5 秒传本质上是拿文件指纹去判断“这个文件之前是不是已经上传过”，如果命中了，就直接复用已有对象，不再重复传整个 1GB 文件。对智图这种项目来说，这个收益是很明显的，因为实验室里经常会出现同一批遥感图被不同同学重复整理、重复上传的情况，不做秒传的话，存储和带宽浪费会比较大。

第二，MD5 的优势主要是成熟、快、实现简单。学生项目里我不会把它讲得太重，不会说什么上来就做特别复杂的多重哈希体系。因为智图的使用范围就是实验室内部十几个人，文件虽然大，但文件总量和攻击面都远小于公网平台。在这种场景下，用 MD5 做秒传的工程性价比是比较高的。

第三，碰撞风险肯定是有的，这个不能回避。但我在面试里会把它讲得比较真实：从密码学角度 MD5 已经不适合做安全签名，但在实验室内部这个低对抗、低并发、重实用的图库场景里，把它作为“文件去重标识”是够用的，至少当前阶段能换来非常直接的秒传收益。也就是说，我会承认它不是最强方案，但它是当前项目阶段的合理方案。

第四，如果面试官追问怎么降低边界风险，我会说我不会只看一个“文件名相同”就秒传，而是看文件 MD5 这种内容指纹；另外如果要再稳一点，可以叠加文件大小、后缀、上传人租户信息这些辅助信息一起校验。这样即使不是绝对密码学安全，也能把工程上的误判概率压得更低。

第五，所以这题我会总结成：智图里用 MD5 做秒传，核心取舍是“接受极低概率的碰撞风险，换取大文件场景下非常可观的带宽和时间收益”。这个方案不算特别豪华，但很适合实验室内部的学生项目，够实用，也方便落地。

### 预签名URL直传MinIO后，如何防越权上传与跨租户污染？

第一，智图用了预签名 URL 直传 MinIO，主要是因为图片太大，一张图 1GB 左右，如果都让文件流先经过应用服务器，再转发到对象存储，应用层压力会很大，也更容易超时。所以让前端拿到预签名地址后直接传 MinIO，是这个项目里很自然的选择。

第二，但直传以后不能变成“谁拿到地址都能乱传”，所以我会把安全边界放在签发 URL 的时候，而不是放在上传结束后再补救。最核心的一点就是：对象路径不能让前端自己拼，而应该由后端按租户、用户、业务目录来生成。比如路径里天然带上 tenantId、userId、uploadSessionId 这一类信息，这样即使两个租户文件名一样，也不会写到同一个逻辑空间里。

第三，第二个关键点是预签名 URL 要短时有效，不能长期复用。因为这个系统不是公网大平台，用户少、场景固定，所以我完全可以把 URL 有效期收得比较短，比如几分钟内有效，超时就重新申请。这样即使地址泄露，可利用窗口也比较小。

第四，我还会补一句，后端在签发 URL 前一定要先做鉴权，先通过 JWT 和 Redis 确认当前用户身份、租户身份和上传目标是否合法，然后再给这个用户发只对应当前对象路径的预签名地址。也就是说，权限校验发生在“发地址”之前，而不是用户传完之后才发现不对。

第五，所以我会把这题答成：智图防越权上传和跨租户污染，核心不是上传后做拦截，而是签发阶段就控制住三件事——固定对象路径、绑定租户身份、缩短 URL 时效。这样既保住了大文件直传的效率，也没有把多租户边界放空。

### Redis状态机记录分片进度时，如何处理客户端断线重传？

第一，智图做断点续传时，Redis 的作用不是简单存一个“上传中”标记，而是要把一个上传会话的分片状态保存下来。因为这种 1GB 左右的大图很容易受网络抖动影响，如果不把分片索引持久化下来，用户一断线就得从头上传，体验会非常差。

第二，我会把它设计成一个比较轻量的上传状态机。比如一个 uploadId 对应一条 Redis 记录，里面至少要知道：文件 MD5、总分片数、已完成分片编号集合、所属用户、所属租户、开始时间、最近更新时间。这样用户重新连上来之后，前端先问后端“这个 uploadId 现在传到哪了”，后端再把缺的分片列表返回给前端，前端只补传缺失部分。

第三，断线重传时最重要的是保证幂等。也就是说，同一个分片重复上传不能把状态写乱。我在面试里会说：分片状态更新必须是“按 chunkIndex 去重”的，而不是每来一次就把完成数 +1。这样即使客户端因为超时重试，把第 5 片又传了一遍，Redis 里也只是确认“第 5 片已完成”，不会导致整体状态错乱。

第四，考虑到这是学生自己做的实验室系统，我不会把状态机讲得特别复杂，比如不会说成分布式工作流引擎那种感觉。我会强调它是一个围绕断点续传设计的实用状态结构，重点解决两个问题：第一，不让用户断线后重头来；第二，不让重复重传把分片进度搞脏。

第五，所以总结就是：智图里 Redis 状态机处理客户端断线重传，关键点是“保存已完成分片集合 + 按分片编号幂等更新 + 前端按缺口补传”。这样设计很贴合大图上传、低并发、学生项目的真实场景。

### Kafka 异步处理链路里，如何保证 MySQL 元数据与 ES 索引最终一致？

第一，这个项目里 Kafka 不是为了炫技，而是因为大图上传完成后，后面还有特征提取、AI 脚本处理、索引构建这些比较耗时的动作。如果全部塞进一次 HTTP 请求里，很容易超时，所以我才把“上传成功”和“后处理”拆开，用 Kafka 做异步解耦。

第二，MySQL 和 ES 的一致性我不会讲成强一致，因为这个项目明显更适合最终一致。我的理解是：MySQL 里先落业务元数据，保证文件记录、所属用户、租户、对象路径这些核心信息先稳定保存；然后再投递消息，消费者异步去做解析和 ES 建索引。这样系统的主事实源还是 MySQL，ES 是检索增强层。

第三，为了避免“数据库写成功了，但消息没发出去”，我会在回答里提事务消息这个思路。也就是说，业务事务和消息投递要尽量协同，至少保证文件元数据提交成功后，后续一定有机会触发 ES 建索引，而不是靠应用代码里一前一后随手写两行。对学生项目来说，我不会把它包装得特别复杂，但会讲清楚核心目标就是避免“元数据已经有了，索引却永远缺失”。

第四，如果后续消费失败，也不能让数据就一直不一致，所以这里又配了重试和 DLQ。也就是说，MySQL 成功只是第一步，ES 没跟上时，系统要靠消息重试和补偿把索引慢慢追平。这种说法会更符合“最终一致”的语义，也更贴近智图这种内部系统的真实实现思路。

第五，所以我会总结成：智图里 MySQL 是元数据主存，ES 是检索副本，Kafka 负责把上传成功后的后处理异步化；一致性不是靠强事务一把锁死，而是靠“先写主数据、再发消息、失败可重试、最终把索引补齐”来保证最终一致。

### 消费失败重试策略和DLQ触发条件是什么？

第一，智图里的 Kafka 消费失败，我不会设计成无脑无限重试。因为后处理链路里可能会调用 AI 脚本、图像解析脚本、索引构建流程，有些失败是临时性的，比如脚本服务瞬时不可用；但也有些失败是数据本身有问题，比如文件损坏、格式不支持。这两类情况必须分开。

第二，所以我的重试策略会比较朴素但实用：先做有限次数重试，比如 3 次这种量级。临时性问题通常在短时间内就能恢复，尤其这个系统使用人数少，后台压力也不大，没必要设计特别复杂的指数退避矩阵，但至少要避免一失败就直接丢掉。

第三，DLQ 的触发条件我会定义成“超过最大重试次数仍失败”或者“明确识别为不可恢复错误”。比如文件元数据缺失、对象根本不存在、格式不支持、脚本参数不合法，这种就没必要一直重试，应该尽快打到 DLQ，避免污染正常消费队列。

第四，打进 DLQ 以后也不能当作永远不管。我会在面试里讲成：DLQ 更像人工排查和后续补偿的缓冲区。因为智图本来就是实验室内部系统，体量不大，很多异常其实可以靠人工看一下日志、修一下元数据、重新触发处理来解决，不需要把它讲成特别重的平台化故障治理。

第五，所以这题我会回答成：消费失败优先做有限重试，适合处理临时性异常；超过次数或者明确不可恢复时进入 DLQ。这样既保证了系统有自恢复能力，也不会让坏消息一直反复污染主消费链路。

### 事务消息怎么和业务事务协同，避免“业务成功消息丢失”？

第一，这题的核心不是 Kafka 本身，而是“上传元数据落库”和“后续异步处理消息”这两个动作之间不能出现断裂。因为如果 MySQL 已经写成功了，但消息没发出去，那用户界面上会看到文件已经上传成功，可后面的解析、检索、归档却一直没发生，这个体验会很奇怪。

第二，所以我会把这件事讲成“业务事务和消息投递要协同”，本质目标就是避免双写不一致。对于智图这种项目，我不会夸成一个特别复杂的分布式事务平台，但会讲清楚：至少要保证数据库提交成功后，消息最终能被可靠投递；如果消息阶段出问题，系统也要能感知到并补发，而不是静默丢失。

第三，面试时我会强调一个很朴素的工程原则：MySQL 的文件元数据是主事实，消息是驱动后续动作的事件。只要主事实已经成功，就必须有办法把事件补出来。所以事务消息的意义不只是“让 Kafka 更高级”，而是保证后续 ES 建索引、AI 处理这些异步链路不会因为一次消息丢失彻底断掉。

第四，考虑到这是学生项目，我也会把表达控制得真实一点，不会说成自己做了特别重的分布式一致性框架。我会说，这里更重要的是思路：把元数据提交和消息投递看成一组需要协同的动作，然后通过事务消息或可补偿机制避免“库里有数据，队列里没事件”。

第五，所以这题的回答重点就是：事务消息是为了解决业务成功但后续异步链路没被触发的问题。智图里它服务的不是理论上的一致性完美，而是一个非常实际的目标——让上传成功后的解析、索引和归档流程别掉链子。

### 在线协同编辑锁如何设置过期与续期？心跳丢失怎么处理？

第一，智图的协同场景不是几十上百人同时改一个文档，而是实验室里少量同学在线标注和协作，所以我做编辑锁时，目标不是追求特别复杂的分布式协同算法，而是先把“明显的并发脏写”拦住。也就是谁先拿到编辑锁，谁在当前时间窗口内拥有编辑权。

第二，锁一定要有过期时间，不能变成永久锁。因为浏览器崩了、电脑断网了、页面直接关掉，这些情况在真实使用里都很常见。如果没有 TTL，锁就会悬挂，后面的人根本进不来。所以我会把锁设计成短 TTL，比如几十秒量级，然后前端定时发心跳去续期。

第三，续期逻辑的关键是“只有锁持有者自己能续”。也就是说，心跳里要带上当前用户身份或会话标识，服务端续期前先确认这个锁确实还是他自己的，不能别人随便发个心跳就把锁保住。这样能避免协同状态被写乱。

第四，心跳丢失时，我不会设计成一丢就立刻抢锁，而是允许一个很短的缓冲窗口。因为实验室网络偶尔抖一下很正常，如果过于敏感，就会出现锁频繁释放和重新抢占，用户体验很差。所以更合适的做法是：只要 TTL 真正过期了，才认为锁失效；而不是单次心跳失败就立刻判死。

第五，所以我会把这题总结成：智图的 Edit Lock 设计重点是“短 TTL + 持有者续期 + 过期自动释放 + 对短时心跳丢失保持一定容忍”。这样既能防脏写，也比较符合实验室内部低并发协同的真实场景。

### 多人同时编辑时，冲突检测与冲突解决策略是什么？

第一，智图这个项目里，多人协同的重点是“防止明显脏写”，而不是追求像在线文档那种特别复杂的实时协同算法。因为它主要是图片标注、图片管理这种场景，本身和富文本协同不是一回事。我在面试里会明确说：我这里更偏向“轻量冲突控制”，而不是 OT 或 CRDT 那种重方案。

第二，冲突检测上，我会先靠编辑锁挡住大部分并发修改。也就是说，核心画布区谁先进入编辑状态，谁先持锁，其他人只能看或者等待，这样已经能避免很多最直接的脏写问题。毕竟实验室里同时编辑同一张大图的人不会特别多，这种方式很贴合实际。

第三，如果面试官继续追问“那多人同时改不同区域怎么办”，我会讲得稍微灵活一点：当前项目阶段更偏保守，优先保证一致性，不急着做特别细粒度的局部合并。因为学生自己做系统，先把锁、心跳、状态同步做稳，比一上来就做复杂合并算法更现实。否则系统复杂度会一下子上来，收益未必明显。

第四，冲突解决策略上，我会说当前更接近强锁串行，也就是把高冲突场景尽量收敛成“同一时刻一个编辑者主写”，而不是开放多人自由并改后再智能合并。这种方案听起来没那么炫，但非常符合智图的场景：人少、图片大、标注结果比操作炫技更重要。

第五，所以这题我会总结成：智图当前的冲突处理策略是“先检测、再串行”，优先用 Edit Lock 阻断并发脏写，而不是做复杂的乐观合并。对于实验室内部协同图库，这个方案简单、稳定、够用，也更符合学生项目的实现边界。

### JWT + Redis 鉴权下，权限变更如何实时生效？

第一，智图里用 JWT + Redis 做鉴权，核心目的是既保留 JWT 的轻量身份表示，又不让权限完全写死在一个长期不变的 token 里。因为实验室场景里虽然用户不多，但共享域、私有域、公共域这些边界很重要，一旦某个同学权限变了，系统最好能尽快生效，而不是等 token 自然过期。

第二，我在回答时会讲成：JWT 更多承担“我是谁”的作用，Redis 更承担“我现在还能做什么”的作用。也就是说，请求进来以后，不是只验 token 签名就完事，还会结合 Redis 里的当前会话状态或权限版本去做一次校验。这样权限调整以后，服务端这边是有机会立刻感知到的。

第三，如果权限发生变更，比如某个用户从共享域编辑者变成只读，或者某个租户权限被收回，我可以通过更新 Redis 中对应的权限信息或会话版本，让旧 token 在服务端校验时失效或降权。这样做的好处是，不需要等 JWT 很久以后自己过期。

第四，当然我不会把它讲成企业级非常复杂的统一身份平台，而会强调这是一个比较实用的内部系统方案：用户少、权限模型相对清晰，所以用 JWT 表身份、Redis 控实时权限，已经能把“权限变更要尽快生效”这个问题处理得比较好了。

第五，所以这题我会总结成：智图里权限实时生效的关键，不是让 JWT 自己变聪明，而是把权限判断的一部分收回到 Redis 和服务端校验逻辑里。这样权限一变，后续请求就能较快感知到。

### ThreadLocal 透传租户上下文如何防止线程池污染？

第一，智图用了 ThreadLocal 去透传用户身份和租户 ID，这样在服务链路里拿上下文会比较方便，尤其是做多租户隔离时很实用。但 ThreadLocal 最大的问题就是：如果线程来自线程池，复用以后很容易把上一个请求的租户信息带到下一个请求里，这个风险必须承认。

第二，所以我在面试里会强调一个最基本但也最关键的点：请求结束后必须清理。也就是说，拦截器或者过滤器在 finally 里一定要 remove 掉上下文，而不是只在成功路径里清。否则只要出现异常、提前返回、异步切换，就可能留下脏数据。

第三，如果涉及异步线程池，我不会说 ThreadLocal 天然就能传过去，而是会明确说明：异步任务要么显式传递必要上下文，要么做线程池包装，任务执行完再清理。因为多租户系统里一旦串租户，不是普通 bug，而是数据边界问题，这个后果比一般空指针严重得多。

第四，结合智图场景，我会特别强调为什么这事重要。因为这个项目里有公共域、共享域、私有域，还有大图元数据、标注数据、对象路径这些都和租户边界强相关。如果上下文污染了，最坏情况不是查错一条记录，而是用户看到别的组数据或者把对象写错租户目录，这就很危险。

第五，所以我会把这题答成：防线程池污染的核心就是“入口设置、出口清理、异步显式传递、执行完再 remove”。ThreadLocal 在智图里很好用，但前提是一定要把清理做扎实，不然多租户隔离很容易出问题。

### WebSocket 握手鉴权失败和连接重连风暴怎么处理？

第一，智图的 WebSocket 主要是做协同标注的实时双向信令，所以连接建立前先鉴权是必须的，不然任何人都能接进来，协同状态就不可信了。项目描述里也提到用了自定义握手拦截器做前置鉴权，这个点本身就很关键。

第二，如果握手鉴权失败，我不会让它模糊通过，而是直接拒绝连接。因为协同通道不是普通查询接口，一旦放进来一个没权限的连接，后面状态广播、编辑锁通知、协同消息都可能越界。所以这里宁可严格一点，也不能抱着“先连上再说”的想法。

第三，至于重连风暴，智图这种系统虽然用户少，但也不能完全不考虑。比如实验室网络抖动一下，十几个人页面同时断开再自动重连，如果客户端写成无间隔死循环重连，后端和网关都会比较难受。所以我会在回答里强调：客户端应该做退避重连，比如失败后逐步拉长重连间隔，而不是毫秒级疯狂重试。

第四，如果某个用户连续多次鉴权失败，我也会讲成一个轻量黑名单或短期限流思路。因为这不一定是恶意攻击，也可能是 token 过期或者前端 bug，但至少服务端不能被无意义的握手请求反复打。考虑到是学生项目，我不会说成很复杂的风控系统，而会讲成“有限保护措施”。

第五，所以这题我会总结成：智图里 WebSocket 对握手鉴权要前置且失败即拒绝；对重连风暴则通过客户端退避重连和服务端轻量限流/短期拦截来控制。这个设计不重，但足够适合实验室内部协同场景。

## 二、智图（SpringBoot / MySQL / Redis / Kafka / MinIO / WebSocket / ES）

### 预签名URL直传MinIO时，如何限制对象路径、防重放、防跨租户污染？

第一，这题我会直接围绕智图的大图上传场景来答。因为图片很大，一张图差不多 1GB，所以直传 MinIO 是非常合理的，不然应用服务器很容易被文件流拖住。但直传效率上去了，安全边界就一定要收紧，尤其是对象路径和租户边界不能放给前端自己控制。

第二，对象路径限制上，我会坚持后端生成、前端只使用。也就是说，路径规则应该是服务端按租户、用户、上传会话去拼，比如 `tenantId/userId/fileMd5/chunkIndex` 这一类结构，而不是让前端说自己要往哪里传。这样做最直接的好处就是从源头上减少跨租户覆盖和乱写对象的问题。

第三，防重放主要靠两个点：一个是预签名 URL 短时有效，过期后就必须重新申请；另一个是 URL 绑定具体对象路径和具体动作，而不是发一个“大而全”的可长期复用上传地址。这样别人就算拿到了这个地址，也很难在别的时间、别的路径、别的租户空间里继续复用。

第四，防跨租户污染本质上还是鉴权前置。也就是说，发预签名 URL 前，后端要先通过 JWT + Redis 确认当前用户身份和租户身份，再确认这个上传会话是不是他自己的，再给他签只属于该租户目录的 URL。这里不是靠 MinIO 自己替你理解租户语义，而是业务系统先把边界定清楚。

第五，所以我会把这题总结成：智图在直传 MinIO 时，核心控制点是“路径由后端生成、URL 有效期要短、签发前做租户鉴权、URL 只绑定当前上传动作”。这样既能保住大文件直传的效率，也能把越权上传和跨租户污染风险压住。

### 分块上传断点续传的Redis状态机如何设计，异常重试如何保证幂等？

第一，这个项目里断点续传的核心不是前端“记住传到哪了”，而是服务端要有一个可靠的上传状态。因为实验室里传 1GB 级图片时，浏览器刷新、电脑断网、页面切走都很常见，如果上传状态只留在前端内存里，断了就全没了。

第二，所以 Redis 状态机我会设计成围绕 uploadId 的一套状态记录，至少包括：文件 MD5、总分片数、已上传分片集合、文件大小、所属租户、所属用户、上传会话状态、最近更新时间。这样无论用户是刷新页面还是重新登录，只要 uploadId 还在，系统就能知道这个文件已经传到第几片了。

第三，异常重试的幂等关键点，是分片状态必须按 chunkIndex 去判重，而不是按“请求次数”累加。也就是说，第 8 片重复上传三次，最终状态里依然只是“第 8 片已完成”，不会把总进度算错。这个设计看起来简单，但其实是断点续传稳定性的关键。

第四，真正合并文件之前，还要校验是否所有分片都已经齐了，而不是前端说“我传完了”就相信。因为网络抖动下很容易出现前端自己以为成功、但某些分片其实没落到 MinIO 或状态没写成功的情况。所以后端在合并前做一次完整性检查，是非常必要的。

第五，所以这题我会答成：智图的断点续传 Redis 状态机，本质上是一个“以 uploadId 为主键、以 chunkIndex 集合记录进度”的轻量状态系统；异常重试要靠分片编号幂等更新来保证，不能让重复上传把整体进度写乱。

### Kafka事务消息如何协调MySQL与ES最终一致，失败补偿链路怎么走？

第一，智图这里 MySQL 和 ES 的关系，我会定义得很清楚：MySQL 负责存文件元数据和业务主记录，ES 负责检索和搜索体验增强。也就是说，ES 不是主数据源，所以这条链路做的是最终一致，不是强一致。

第二，事务消息的意义就在于协调“业务主记录成功”之后，后面的异步处理不要漏掉。比如用户上传成功后，MySQL 里已经有文件信息了，这时必须让 Kafka 上也有对应事件，后续消费者才能去做 AI 脚本处理、特征提取、ES 建索引。如果这一步断了，就会出现“数据有了，搜不到”的问题。

第三，失败补偿链路我会讲得比较口语化一点：主链路先正常消费并建索引，如果失败了先重试；重试多次还不行，就打到 DLQ；进了 DLQ 以后，人工或者后台补偿任务再去看是对象丢了、脚本挂了、参数错了还是 ES 临时不可用，然后修完再重放。对实验室内部系统来说，这种“可恢复、可人工介入”的链路其实就很够用了。

第四，我不会把它讲成特别重的平台级一致性框架，因为智图本身不是企业级海量检索系统。我的回答重点会放在：一是主数据和索引数据职责分清；二是消息不能丢；三是失败后有重试和补偿链路，最终把 ES 追平。

第五，所以这题我会总结成：智图里 Kafka 事务消息主要服务于“主数据成功后，异步索引动作不能丢”；失败补偿链路则是“正常消费失败先重试，再进 DLQ，最后人工或补偿任务重放”，从而把 MySQL 和 ES 的状态慢慢追到一致。

### DLQ里的消息如何分类重放，如何避免“重放再次污染索引”？

第一，DLQ 里的消息不能一股脑全部重放，因为失败原因不一样。有些是临时性失败，比如 ES 抖一下、脚本服务超时；有些是数据问题，比如对象不存在、文件损坏、元数据不完整。这两类消息如果不先分类，直接全重放，很容易把系统弄得更乱。

第二，所以我会先按失败原因分类。比较适合重放的是临时性异常，比如依赖短暂不可用；不适合立刻重放的是数据本身就有问题的消息，因为你重放十次它还是错。对这种消息，更适合先修数据、再重放，而不是让 DLQ 变成死循环重试池。

第三，避免重放再次污染索引，关键是消费逻辑要幂等。也就是说，同一个文件的索引更新，最好按文件唯一标识去覆盖式写入，而不是每重放一次就新增一条。这样即使某条消息被重复消费，最终 ES 里还是同一份索引文档，而不会越放越脏。

第四，我还会补一句，重放前最好再查一次 MySQL 当前主数据状态。因为 DLQ 里的消息可能已经滞后了，如果主记录都删了、租户变了、对象路径换了，还拿旧消息直接冲 ES，很容易写出过期索引。这个动作不算特别复杂，但很实用。

第五，所以这题我会回答成：DLQ 消息要先按失败原因分类，再决定是直接重放还是先修数据；为了避免再次污染索引，消费逻辑必须幂等，而且重放前最好再对齐一次 MySQL 当前主数据状态，这样更稳。

### Edit Lock + 心跳续期如何避免锁悬挂与误释放？

第一，Edit Lock 的目的就是防止多人同时改同一张图的同一编辑区域，把标注结果写脏。但如果锁设计不好，又会出现两个反问题：一个是锁悬挂，谁都进不来；另一个是误释放，明明还在编辑，锁却没了。

第二，为了避免锁悬挂，我一定会给锁加 TTL，不会让锁永久存在。因为在真实场景里，页面崩掉、浏览器关闭、电脑睡眠都可能发生，如果没有自动过期机制，这把锁就会一直卡在那里，后面的人只能干等。

第三，为了避免误释放，续期必须由锁持有者自己发心跳，而且续期前要校验当前锁 owner 还是不是自己。不能任何一个客户端来了都把锁续上，也不能锁都不是自己的了还继续续期。这个校验其实非常关键，不然协同状态会越来越乱。

第四，至于心跳丢失，我不会设计成一次丢失就立即释放。更合理的做法是依赖 TTL 自然到期，也就是给网络短抖动留一点缓冲。因为实验室网络环境下，偶发丢包很正常，如果过于敏感，锁会频繁在“还在编辑”和“已失效”之间抖动，反而影响使用。

第五，所以这题我会总结成：智图避免锁悬挂靠的是 TTL，避免误释放靠的是 owner 校验和持有者续期，避免因偶发心跳丢失带来误判则靠短期容忍和自然过期。这套方案不重，但很适合当前协同图库的场景。

### WebSocket握手鉴权失败后，重连退避与黑名单策略如何设计？

第一，智图里 WebSocket 不是一个随便连上的聊天通道，而是协同编辑和实时状态同步的关键通道，所以握手鉴权失败后一定要直接拒绝，不能模糊放行。因为一旦未经授权的连接进来了，后面的锁状态、标注广播、协同通知都可能越权。

第二，客户端重连一定要做退避，不然网络一抖或者 token 过期，十几个人的页面可能瞬间都进入高频重连。虽然用户量不大，但如果前端写成 100ms 一次那种死循环，后端照样会被打得很难受。所以我会讲成“失败后逐步拉长重连间隔”，这样比较稳。

第三，黑名单策略我不会设计得特别重，因为这是实验室内部系统，不是公网社交平台。但轻量策略还是有必要，比如某个连接来源在短时间内连续很多次鉴权失败，就先短时间限制它继续发起握手，防止它因为前端 bug 或者过期 token 不断打后端。

第四，我还会补一句，握手失败时最好给前端一个明确原因，比如 token 过期、权限不足、租户不匹配。这样前端可以决定是去刷新 token、提示重新登录，还是直接停止重连，而不是盲目地一直撞。

第五，所以这题我会回答成：智图里 WebSocket 握手鉴权失败后，服务端应立即拒绝；客户端要做退避重连；对于短时间连续失败的来源，可以加轻量黑名单或限流。这个设计既不夸张，也足够适合内部协同系统。

### JWT+Redis鉴权下，权限变更如何秒级生效且不引入大量缓存抖动？

第一，这题的核心矛盾是：JWT 本身适合无状态鉴权，但权限变更又希望尽快生效。如果完全只靠 JWT，用户拿着老 token 还能继续用到过期；如果每次都重查数据库，成本又没必要。所以智图这里才会用 JWT + Redis 结合的方式。

第二，我会把它解释成：JWT 解决身份识别，Redis 解决权限实时性。请求进来时，先确认 token 没问题，再去 Redis 看当前会话状态、权限版本或者关键权限缓存。这样一来，只要权限发生变化，Redis 这边一更新，后续请求就能很快感知到，不需要等很长时间。

第三，所谓“不引入大量缓存抖动”，我不会讲成特别复杂的缓存一致性架构，而是说因为这个系统用户本来就少，十几个人在用，所以没必要把每个权限变化都设计成特别重的广播刷新。更实际的方式是按用户级别、会话级别去更新 Redis 中对应权限信息，而不是全量失效。

第四，也就是说，权限变更影响的是这个用户、这个租户的缓存，而不是把整个系统所有鉴权缓存全部打掉。这样既能做到比较快生效，也不会造成大范围缓存抖动。对于实验室内部系统，这样的粒度已经很够用了。

第五，所以我会总结成：智图里权限秒级生效，靠的是把实时权限判断的一部分放到 Redis；而避免缓存抖动，靠的是按用户或会话粒度更新，而不是全局粗暴失效。这种方式简单、实用，也适合当前规模。

### ThreadLocal在异步线程池传播时，如何防止上下文串租户？

第一，这题我会先说明，ThreadLocal 在主线程链路里拿上下文确实方便，但一旦到异步线程池，就不能想当然地以为它会自动安全传播。尤其智图是多租户系统，如果异步任务里把租户上下文串了，后果不是普通小 bug，而是数据边界直接错位。

第二，所以第一原则是：异步线程不要偷偷依赖老线程里残留的 ThreadLocal，而是要么显式把 tenantId、userId 这些必要上下文当参数传进去，要么在任务提交时做包装，把上下文复制过去，执行完再清理。核心思想就是“带着清楚的上下文去，带着干净的线程回来”。

第三，第二原则是 finally 清理，这一点我会反复强调。因为线程池的线程是复用的，如果任务执行完不 remove，下一个任务进来时就可能读到上一个租户的信息。对于智图这种公共域、共享域、私有域都很敏感的项目，这个风险必须防得很严。

第四，面试里我还会顺手把危害讲出来：一旦串租户，轻一点是查到错误数据，重一点可能是把文件元数据、标注记录、对象路径写到别的租户下面。这种问题比普通接口报错更隐蔽，也更危险，所以上下文传播和清理不能马虎。

第五，所以这题我会回答成：智图里异步线程池场景下，防止上下文串租户的关键就是“显式传播必要上下文 + 执行后及时清理 + 不依赖线程残留状态”。ThreadLocal 可以用，但一定要用得很克制。

## 三、智图（协同图库）

### 分块上传的chunk size和并发数怎么定，依据是什么？

第一，智图的上传对象主要是高分遥感图，一张图大概 1GB 左右，所以我在定 chunk size 的时候，首先考虑的是失败重传成本，而不是极限吞吐。因为实验室同学上传这类大图时，最怕的是传到一半断掉，如果单块太大，失败一次就要重传很多内容。

第二，所以我更倾向把 chunk size 放在一个中等范围，比如 8MB 到 16MB 左右。这样不会把分片切得过多，也不会让单片失败代价太高。对学生项目来说，这种取值很容易解释，也符合实际使用体验。

第三，并发数我不会设置得很高，因为系统本身同时在线也就十几个人，没必要把单文件上传做成很激进的并发模型。我更倾向于 3 到 5 这种比较稳的并发片数，让浏览器、网络和 MinIO 都处在一个比较舒服的状态。

第四，依据其实就三条：文件大、用户少、稳定优先。这个项目不是为了做上传 benchmark，而是为了让实验室内部同学真的能把大图传上来、断了还能续、不要频繁失败。所以参数选择更偏工程实用，不会特别追求炫技。

第五，所以这题我会总结成：智图里 chunk size 和并发数的设定，是围绕“大文件上传稳定性”和“实验室低并发内部使用”做的折中，不是按公网大平台思路去卷极限性能。

### 直传MinIO时，如何保证预签名URL不被跨租户复用？

第一，这个问题的核心不在 MinIO，而在业务系统怎么签这个 URL。因为 MinIO 只知道对象路径和签名，不知道你的租户语义，所以租户隔离一定要在业务侧先做好。

第二，我会把对象路径天然设计成带租户边界的结构，比如路径前缀里就带 tenantId，再加上 userId、uploadId 或文件指纹。这样即使别人拿到了这个 URL，它对应的也只是某个固定租户目录下的固定对象，不会变成一个通用上传入口。

第三，URL 本身必须短时有效，不能长期复用。因为内部系统虽然对抗风险不高，但也不能完全没边界。有效期收短以后，就算有地址泄露，能利用的时间窗口也很有限。

第四，签发前后端还要做一次绑定校验：这个用户是不是当前租户成员，这个上传会话是不是他发起的，这个对象路径是不是属于他当前应该写入的空间。也就是说，真正的防跨租户复用，不是靠前端自觉，而是靠服务端发 URL 时就把边界锁死。

第五，所以我会把这题回答成：智图防预签名 URL 跨租户复用，主要靠“路径带租户前缀、签名只对当前对象有效、URL 短时失效、签发前做租户鉴权”这四个点，思路并不复杂，但很实用。

### 秒传命中后如何校验“文件同名不同内容”的边界情况？

第一，秒传不能按文件名判断，这个是最基本的。因为实验室里文件同名非常常见，比如不同日期导出的图片都可能叫同一个名字。如果只按文件名命中秒传，肯定会出错。

第二，所以智图这里秒传的核心判断一定是文件内容指纹，比如项目描述里提到的 MD5。也就是说，只有文件内容的 MD5 一样，才认为它是同一个物理文件，可以直接复用对象；而不是因为文件名一样就直接秒传。

第三，如果面试官追问“那同名不同内容怎么办”，我会直接说：这种情况在秒传逻辑里就应该视为新文件，因为它的 MD5 不同。也就是说，名字只影响展示层，不影响物理去重层。这个分层一定要讲清楚。

第四，如果要讲得更稳一点，我还会补一句：除了 MD5，本身也可以结合文件大小一起做一个辅助校验。虽然核心还是内容指纹，但多一层大小校验，工程上会更放心一些，尤其是在学生项目里，成本也不高。

第五，所以这题最关键的回答就是：智图秒传命中的依据是内容指纹，不是文件名；文件同名不同内容时，因为 MD5 不同，就不会命中秒传，而会走正常上传流程。

### Kafka消费失败重试与DLQ切换阈值如何设置？

第一，这个项目里 Kafka 主要承接大图上传后的异步处理，所以失败重试一定要有，但不能无限重试。因为有些问题是临时性的，有些问题是永久性的，如果不设阈值，队列很容易被坏消息拖住。

第二，我会把重试阈值设置得比较克制，比如 3 次左右。因为智图不是高并发企业平台，没必要把策略设计得特别复杂；但也不能一次失败就放弃，毕竟脚本服务、ES、网络这些依赖偶发抖动是很正常的。

第三，切到 DLQ 的条件我会定义成两类：一类是超过最大重试次数仍然失败；另一类是明确判断为不可恢复，比如对象丢失、文件损坏、参数非法、元数据缺失。这类问题你再试也没意义，就应该尽快转入 DLQ。

第四，进了 DLQ 以后，我不会把它理解成“彻底失败区”，而是“待排查和待补偿区”。因为实验室内部系统体量不大，很多问题其实人工看一下日志、补一下数据、重新放一次就能解决，不需要搞得特别平台化。

第五，所以我会总结成：智图里 Kafka 消费失败先做有限重试，超过阈值或遇到不可恢复异常再切 DLQ。这个策略简单，但非常适合当前项目规模和使用场景。

### 事务消息如何保证MySQL成功而ES最终可追平？

第一，MySQL 成功而 ES 最终可追平，这里面最关键的是承认两者不是强一致关系，而是主从式的最终一致关系。也就是说，MySQL 先存主记录，ES 作为检索层后续慢一点跟上是可以接受的，但不能永远缺。

第二，事务消息在这里的作用，就是让“主记录已成功”这件事一定能驱动后续索引链路。否则最坏情况就是：文件已经在 MySQL 里了，用户列表也能看见，但搜索永远搜不到，这种体验很割裂。

第三，我会把“可追平”讲成一个补偿能力，而不是一次性绝对成功。也就是说，消息正常消费就更新 ES；失败了就重试；再失败进 DLQ；人工或补偿任务处理后再重放。只要这条链不断，ES 最终就能追上 MySQL。

第四，考虑到是学生项目，我不会夸成什么特别重的分布式一致性中台，而会更真实地说：这里就是用消息把慢动作拆出去，再用补偿把坏状态追回来。这样讲既专业，也不失真。

第五，所以这题我会答成：智图里事务消息保证的是“主数据成功后，后续索引事件别丢”；而 ES 最终可追平则依赖重试、DLQ 和补偿重放。核心不是一次成功，而是失败后仍然有路可追。

### Edit Lock心跳丢失后，锁释放策略如何避免误释放？

第一，心跳丢失不等于用户真的离开编辑。实验室网络偶尔抖一下、浏览器标签切后台、电脑短暂休眠，这些都可能导致单次心跳失败。所以如果一丢心跳就立刻释放锁，误释放的概率会很高。

第二，更合理的做法是把“是否释放”交给 TTL，而不是交给单次心跳结果。也就是说，锁本身设一个过期时间，只要在过期前又收到了合法续期，就继续保持；如果超过 TTL 还没收到，那再释放。这样能对短时抖动有一定容忍。

第三，续期时一定要校验 owner，确保只有当前持锁人能续自己的锁。否则会出现别人误续、甚至抢锁混乱的问题。这个 owner 校验其实是避免误释放和误保留的共同关键。

第四，我还会补一句，前端层面也可以做得更友好一点：如果检测到心跳已经快过期，可以提示用户协同状态不稳定，而不是等锁突然没了用户才发现。这种体验优化虽然简单，但在实验室内部使用里很实用。

第五，所以这题我会总结成：智图里 Edit Lock 心跳丢失后的释放策略，核心是“依赖 TTL 判断真正失效，而不是单次心跳失败立刻释放”，再加上 owner 校验，就能比较好地减少误释放。

### 多人并发标注冲突时，你采用乐观冲突合并还是强锁串行？

第一，智图当前更适合讲成强锁串行，而不是乐观冲突合并。因为项目场景是实验室内部协同图库，用户不多，核心诉求是让多人协同时别把标注写乱，而不是追求特别炫的实时合并算法。

第二，标注和文档编辑不一样，它通常是对具体图片对象、具体区域、具体图层的操作。一旦冲突合并做不好，最后结果会很乱，反而影响图片标注的可信度。所以在项目阶段，我更愿意先把“一个关键编辑区同一时刻只有一个主写者”这个规则立住。

第三，强锁串行的好处是实现简单、边界清楚、结果稳定。尤其在十几个人使用的实验室场景里，这种方案完全够用，而且更容易向老师和同学解释：谁现在在编辑、别人为什么只能等或者只读，大家是能接受的。

第四，如果以后项目更成熟，当然可以再往更细粒度的局部冲突检测上演进，但当前阶段我不会把自己没做的东西硬说成已经做了。我会坦诚地说：现在优先解决的是脏写问题，而不是复杂并发合并问题。

第五，所以这题我会回答成：智图当前采用的是偏强锁串行的思路，用 Edit Lock 先把高冲突操作挡住，而不是上来就做复杂的乐观合并。这更符合学生自己做系统的实际边界，也更贴合当前使用规模。

### JWT续签和权限变更同时发生时，如何避免短时越权？

第一，这个问题的关键在于：不能把“token 还有效”直接等同于“权限也还是老样子”。因为一旦权限变更和 JWT 续签同时发生，如果系统只相信旧 token 里的内容，就会出现一个短时间窗口，用户虽然权限已经被收回，但还能继续操作。

第二，所以我会把 JWT 里的信息和 Redis 中的实时权限状态分开看。JWT 负责证明身份，Redis 负责判断当前会话或权限版本是不是还有效。这样哪怕旧 token 还没自然过期，只要 Redis 侧的权限状态已经更新，服务端校验时就能感知到，不会继续按旧权限放行。

第三，续签时我也不会简单复制旧权限，而是会以当前 Redis 或服务端最新权限状态为准重新签发。也就是说，续签不是延长旧权限，而是基于最新权限重新生成新的会话凭证。这样短时越权窗口会小很多。

第四，考虑到智图是实验室内部系统，我不会把它讲成特别复杂的统一身份中心方案，而会说它是一种很实用的“身份和权限分离校验”思路。用户少、权限关系也相对清晰，这样做已经足够把风险收得比较小。

第五，所以这题我会总结成：避免 JWT 续签和权限变更同时发生时的短时越权，核心是不要只信 token 本身，而要把实时权限判断收回到 Redis 或服务端状态里；续签时也要按最新权限重签，而不是机械延长旧授权。

### ThreadLocal上下文在异步线程池中如何安全传递和清理？

第一，这题我会从两个动作来回答：一个叫“带过去”，一个叫“带干净回来”。因为 ThreadLocal 最大的问题不是你能不能拿到上下文，而是在线程池复用时很容易留下脏数据。

第二，安全传递上，最稳妥的思路是显式传递必要字段，比如 tenantId、userId、requestId，而不是假设异步线程天然知道主线程上下文。如果确实要封装 ThreadLocal 传播，也应该在任务提交时统一包装，而不是让每个业务点自己乱取。

第三，安全清理上，必须在执行完成后的 finally 里 remove。这个动作不能偷懒，因为一旦线程被线程池复用，下一个任务可能读到上一个租户的上下文。对智图这种多租户协同系统，这种串租户问题是非常危险的。

第四，面试里我还会补一句，异步任务里真正需要什么上下文，就只传什么，不要把一整坨无关信息都塞进去。因为传得越多，污染面越大，也越难维护。对学生项目来说，保持简单和可控反而更重要。

第五，所以这题我会回答成：智图里 ThreadLocal 上下文在异步线程池中要安全使用，关键就是“显式传播必要上下文 + finally 中及时清理 + 不依赖线程残留状态”。这样才能既方便透传，又不把租户边界搞乱。

### 你如何设计“协同编辑可观测性指标”用于线上告警？

第一，智图虽然不是高并发系统，但协同编辑这块依然需要可观测性，因为一旦锁异常、WebSocket 大面积掉线、标注冲突频繁，用户体验会非常直观地变差。对于实验室内部系统来说，指标不用铺得特别重，但关键点一定要抓住。

第二，我会优先关注三类指标。第一类是连接层指标，比如 WebSocket 当前连接数、握手失败数、重连次数、异常断开次数；第二类是协同状态指标，比如编辑锁持有数、锁续期失败数、锁超时释放数、锁冲突次数；第三类是业务结果指标，比如标注保存成功率、标注冲突拒绝次数、实时广播延迟。

第三，这些指标的意义也很好解释。比如握手失败数突然升高，可能是鉴权出问题；锁超时释放异常增多，可能是心跳机制有问题；冲突次数突然变高，说明协同区域设计或锁粒度可能不合理。也就是说，指标不只是为了好看，而是要能帮助定位问题。

第四，考虑到智图是学生自己做的实验室系统，我不会说一定做成特别完整的 APM 平台。我会更口语化地讲成：先把最影响使用体验的几项指标盯住，尤其是连接稳定性、锁状态和标注保存结果。因为这些已经足够支撑日常排查和简单告警了。

第五，所以这题我会总结成：智图的协同编辑可观测性指标，重点要围绕“连接是否稳定、锁是否正常、标注是否成功”这三条主线去设计。这样既不会把系统做得太重，也能真正服务于线上问题发现和排查。
