# KubeOnCall 告警上层接入重构计划

## 1. 文档目的

本文定义 KubeOnCall 与 Prometheus、Node Exporter、Alertmanager 的上层告警接入方案，重点解决以下问题：

1. 如何采集 Linux 主机 CPU、内存、磁盘、网络和系统状态。
2. Prometheus、Alertmanager 与 KubeOnCall 各自负责什么，避免职责重叠。
3. Alertmanager 如何可靠地把 FIRING/RESOLVED 告警交给 KubeOnCall。
4. 如何复用现有 `NormalizedAlarmEvent`、策略引擎、工作流、RAG、记忆和审批能力。
5. 如何避免策略双写、重复通知、消息环路和 KubeOnCall 成为告警单点。
6. 如何分阶段开发、测试、灰度、验收和回滚。

本文是实施计划，不代表文中所有能力已经完成。当前仓库已有单事件告警入口和首批 12 条告警策略，但还没有原生 Alertmanager 批量 Webhook 接入、异步告警 Inbox、策略规则编译器和完整生产闭环。

## 2. 结论与核心决策

使用 Prometheus 监控 Linux 状态作为 KubeOnCall 的上层是合理的，但完整链路不能只有 Prometheus 和 KubeOnCall，必须引入 Alertmanager：

```text
Linux 主机
  -> Node Exporter
  -> Prometheus 抓取指标并执行 recording/alerting rules
  -> Alertmanager 分组、去重、抑制、静默和基础路由
  -> KubeOnCall Webhook
  -> 标准化、策略治理、智能诊断、RAG、记忆、工单和受控处置
```

本方案确定以下架构决策：

1. **Prometheus 是指标事实源和规则执行器。** 阈值、PromQL、`for` 和 `keep_firing_for` 由 Prometheus 实际执行。
2. **Alertmanager 是基础通知治理层。** 负责分组、通知去重、路由、inhibition、silence 和 Webhook 重试。
3. **KubeOnCall 是智能治理与处置层。** 负责平台标准化、业务严重度修正、历史关联、上下文采集、RAG、记忆、诊断、工单、升级和审批。
4. **P0/P1 首次通知不依赖 KubeOnCall。** Alertmanager 同时发送给值班渠道和 KubeOnCall，防止 KubeOnCall、Redis、ES 或 LLM 故障时无人收到告警。
5. **新增 Alertmanager 专用批量 Webhook。** 保留现有 `POST /api/alarms` 兼容人工调用和旧调用方。
6. **Webhook 快速接收、后台异步处理。** 接收层不等待完整诊断工作流完成。
7. **策略必须只有一个治理源。** 目标形态由 KubeOnCall `alarm-policies.yml` 生成 Prometheus rules，避免两份阈值长期漂移。
8. **KubeOnCall 不把诊断结果重新提交为同一条 Alertmanager 告警。** 诊断结果走独立通知、工单或事件回写通道，防止形成环路。
9. **自动静默和变更动作必须审批。** 普通告警处理不得默认创建 silence、重启服务、清理文件或扩容。

官方能力边界参考：

- Prometheus Alerting Rules：<https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/>
- Prometheus Node Exporter：<https://prometheus.io/docs/guides/node-exporter/>
- Alertmanager：<https://prometheus.io/docs/alerting/latest/alertmanager/>
- Alertmanager Webhook：<https://prometheus.io/docs/alerting/latest/configuration/>

## 3. 建设目标与非目标

### 3.1 建设目标

第一阶段目标：

- Linux 主机基础指标可采集、可查询、可告警。
- Alertmanager FIRING/RESOLVED 可以稳定接入 KubeOnCall。
- 重复投递不会重复启动诊断流程。
- P0/P1 在 KubeOnCall 不可用时仍能通知值班人。
- 每条进入 KubeOnCall 的告警都有 fingerprint、owner、severity、resource、runbook 和审计记录。
- KubeOnCall 可以使用告警绑定的 PromQL 回查当前与历史指标。
- 告警可以进入现有工作流、RAG、长期记忆和审批体系。

第二阶段目标：

- 从 KubeOnCall 策略配置生成 Prometheus rules。
- 支持规则校验、dry-run、reload、历史回放、版本和回滚。
- 补充 Linux 网络、IO、conntrack、systemd、时间同步等规则。
- 补充 Blackbox Exporter 和服务 SLO 告警，覆盖“主机正常但服务不可用”的场景。

### 3.2 非目标

本次上层接入不负责：

- 替代 Prometheus 的时序存储和 PromQL 计算。
- 替代 Alertmanager 的基础通知分组与 silence 管理。
- 第一阶段直接建设跨地域长期指标存储；需要时再评估 Thanos、Mimir 或 VictoriaMetrics。
- 第一阶段自动执行高风险修复动作。
- 依靠 LLM 决定 P0/P1 等级和首次通知对象。

## 4. 当前基础与主要缺口

### 4.1 当前可复用能力

仓库当前已经具备：

- `POST /api/alarms` 单告警入口。
- `AlarmNormalizer` 对旧格式和标准格式进行统一。
- `AlarmFingerprintService` 生成稳定 fingerprint。
- `YamlAlarmPolicyRepository` 和 `AlarmPolicyEngine`。
- 分严重度 Redis 去重和 ActiveAlarm 状态。
- NodeNotReady 对 Pod 告警的基础抑制。
- 告警工作流模板和节点超时/降级机制。
- Prometheus、Kubernetes、Alertmanager 工具适配器。
- 告警 RAG Runbook 检索、记忆召回、结构化诊断、审计和 metrics。
- CPU、内存、磁盘、inode、Node、Pod、Deployment 共 12 条首批策略。

### 4.2 当前缺口

必须补齐：

1. 现有 `/api/alarms` 接收单个 `AlarmRequest`，不能直接消费 Alertmanager 的 `alerts[]` 分组结构。
2. 当前入口同步执行完整工作流，可能超过 Alertmanager Webhook 超时并引发重复投递。
3. 没有 Webhook 鉴权、批量限制、原始事件留档和死信处理。
4. 没有按 `fingerprint + status + startsAt/endsAt` 的投递级幂等模型。
5. 没有处理“RESOLVED 先到、旧 FIRING 后到”的乱序保护。
6. `alarm-policies.yml` 和未来 Prometheus rules 存在双写风险。
7. 当前 `recover` 只是策略描述，收到 RESOLVED 后没有持续恢复确认。
8. 当前升级和工单仍未形成真实外部闭环。
9. 缺少 Linux 上层组件部署资产、规则目录、配置校验和端到端测试。

### 5.2 部署建议

实验和开发环境：

- 单实例 Prometheus。
- 单实例 Alertmanager。
- 每台 Linux 一个 Node Exporter。
- KubeOnCall 使用 Redis Inbox 和现有 ES/MinIO。

生产环境：

- Prometheus 至少双实例抓取同一批目标。
- Alertmanager 使用原生集群模式，Prometheus 配置所有 Alertmanager 地址，不在 Prometheus 与 Alertmanager 之间使用普通负载均衡代替实例列表。
- KubeOnCall Webhook 可多副本部署，Ingress 后使用统一认证。
- Inbox/幂等状态必须由共享存储提供，不能使用本机内存。
- 首次值班通知由 Alertmanager 直接发送，不依赖 KubeOnCall。

## 6. 组件职责边界

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| Node Exporter | 导出 Linux 内核、硬件、文件系统、网络指标 | 告警判断、通知、诊断 |
| Prometheus | 拉取、存储、PromQL、recording rules、alerting rules | 通知分组、智能诊断、工单 |
| Alertmanager | 分组、通知去重、路由、inhibition、silence、重试 | 复杂根因分析、RAG、自动处置 |
| KubeOnCall | 标准化、业务策略、关联、诊断、RAG、记忆、审批、审计 | 替代时序数据库、承担唯一 P0 通知 |
| Grafana | 指标与告警可视化、值班排障入口 | 规则执行和告警生命周期事实源 |

边界原则：

- Prometheus 的告警状态是指标条件是否成立的事实。
- Alertmanager 的通知状态是某个 receiver 是否应该收到消息的事实。
- KubeOnCall 的处理状态是诊断、工单和处置是否完成的事实。
- 三种状态不能混成一个 `status` 字段，应分别记录和审计。

## 7. Linux 指标采集设计

### 7.1 Node Exporter 部署

Node Exporter 默认监听 `9100`。生产部署要求：

- 使用 systemd、容器或 DaemonSet 管理生命周期。
- 只允许 Prometheus 网络访问 `9100`，不直接暴露公网。
- 固定版本，不使用浮动 `latest`。
- 使用专用低权限用户运行。
- 开启必要 collector，避免无规划地暴露高基数指标。
- 为自定义文本指标单独规划 textfile collector 目录和写入权限。
- 监控 `up{job="node"}`、抓取耗时和 Node Exporter 自身资源。

### 7.2 目标发现与统一标签

小规模环境可使用 file service discovery：

```yaml
- targets:
    - 10.0.1.11:9100
    - 10.0.1.12:9100
  labels:
    cluster: lab-a
    env: prod
    region: cn-east
    service: infrastructure
    owner: infra
    criticality: tier1
```

规模扩大后优先使用 Consul、Kubernetes 或云服务发现。

每个 target 至少具备：

| 标签 | 用途 |
| --- | --- |
| `instance` | 目标地址或规范化节点名 |
| `node` | 人类可读节点名 |
| `cluster` | 集群隔离与告警聚合 |
| `env` | prod/staging/dev/lab |
| `region` | 地域和跨地域影响判断 |
| `service` | 服务归属 |
| `owner` | 告警负责人 |
| `criticality` | tier0/tier1/tier2 |

禁止把以下内容放入指标 label：

- requestId、traceId、时间戳等无限变化值。
- 完整异常堆栈。
- 用户输入或敏感数据。
- 无边界的路径、URL 参数和容器临时 ID。

### 7.3 Prometheus 抓取配置示例

```yaml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:
  - /etc/prometheus/rules/*.rules.yml

scrape_configs:
  - job_name: node
    scrape_interval: 15s
    scrape_timeout: 10s
    file_sd_configs:
      - files:
          - /etc/prometheus/targets/linux-nodes.json
        refresh_interval: 30s
    relabel_configs:
      - source_labels: [__address__]
        target_label: exporter_address
```

生产配置还需要补：

- Prometheus 自监控。
- Alertmanager target 配置。
- remote_write 或长期存储策略（如确有需要）。
- 数据保留时间、磁盘容量和 WAL 规划。
- TLS/Basic Auth 或反向代理安全控制。

## 8. Prometheus 规则设计

### 8.1 规则原则

1. 有明确值班动作才产生 page 告警。
2. 瞬时尖峰使用 `for`，恢复抖动使用 `keep_firing_for`。
3. 优先告警用户症状和资源饱和，不枚举每一种可能原因。
4. P0/P1 必须有 owner、runbook、summary 和明确影响。
5. 告警表达式尽量使用 recording rule 降低重复计算成本。
6. 每条规则必须有单测、回放样例和恢复样例。
7. 不在 annotation 中存放需要精确计算的机器字段。
8. Prometheus severity 是基础等级，KubeOnCall 只允许结合影响面进行可解释修正。

### 8.2 规则元数据契约

所有交给 KubeOnCall 的 Prometheus alert rule 必须提供：

```yaml
labels:
  severity: P1
  category: host
  resource_type: node
  service: infrastructure
  owner: infra
  runbook_id: runbook-host-cpu-high
  workflow_template: host-resource
  kubeoncall_metric: host.cpu.usage_percent
annotations:
  summary: "Host CPU usage is high"
  description: "CPU remained above the threshold for 10 minutes"
  dashboard_url: "https://grafana.example/d/linux-node"
  runbook_url: "https://runbooks.example/runbook-host-cpu-high"
```

标签选择规则：

- 用于匹配、路由、聚合的字段放 `labels`。
- 描述、链接等展示字段放 `annotations`。
- `summary`、`description` 不参与 fingerprint。
- `instance`、`mountpoint`、`device` 等高变化维度只在确实需要区分故障实例时参与聚合。

### 8.3 CPU 规则示例

```yaml
groups:
  - name: kubeoncall-linux-cpu
    interval: 30s
    rules:
      - record: instance:node_cpu_usage_percent:rate5m
        expr: 100 * (1 - avg by (cluster, env, instance, node, service, owner, criticality) (rate(node_cpu_seconds_total{mode="idle"}[5m])))

      - alert: HostHighCpuUsageP1
        expr: instance:node_cpu_usage_percent:rate5m > 70
        for: 10m
        keep_firing_for: 5m
        labels:
          severity: P1
          category: host
          resource_type: node
          runbook_id: runbook-host-cpu-high
          workflow_template: host-resource
          kubeoncall_metric: host.cpu.usage_percent
        annotations:
          summary: "Host CPU usage is high on {{ $labels.instance }}"
          description: "CPU usage is {{ printf \"%.2f\" $value }}%, above 70% for 10 minutes"

      - alert: HostHighCpuUsageP0
        expr: instance:node_cpu_usage_percent:rate5m > 85
        for: 5m
        keep_firing_for: 10m
        labels:
          severity: P0
          category: host
          resource_type: node
          runbook_id: runbook-host-cpu-high
          workflow_template: host-resource
          kubeoncall_metric: host.cpu.usage_percent
        annotations:
          summary: "Host CPU usage is critical on {{ $labels.instance }}"
          description: "CPU usage is {{ printf \"%.2f\" $value }}%, above 85% for 5 minutes"
```

## 9. 首批 Linux 告警策略目录

首批规则按可操作性分批建设，避免一次上线大量噪声告警。

### 9.1 第一批：主机可用性和容量底线

| 告警 | 初始级别 | 条件建议 | 持续时间 | 恢复/防抖 | Runbook |
| --- | --- | --- | --- | --- | --- |
| `NodeExporterDown` | P0/P1 | `up{job="node"} == 0` | 3m | keep 5m | `runbook-node-notready` |
| `HostHighCpuUsageP1` | P1 | CPU > 70% | 10m | <65%/keep 5m | `runbook-host-cpu-high` |
| `HostHighCpuUsageP0` | P0 | CPU > 85% | 5m | <75%/keep 10m | `runbook-host-cpu-high` |
| `HostMemoryPressureP1` | P1 | MemAvailable < 20% | 10m | >25% | `runbook-host-memory-pressure` |
| `HostMemoryPressureP0` | P0 | MemAvailable < 10% | 5m | >20% | `runbook-host-memory-pressure` |
| `HostDiskUsageP1` | P1 | filesystem > 85% | 10m | <80% | `runbook-host-disk-usage` |
| `HostDiskUsageP0` | P0 | filesystem > 95% | 5m | <85% | `runbook-host-disk-usage` |
| `HostInodeUsageP1` | P1 | inode > 85% | 10m | <80% | `runbook-host-inode-usage` |
| `HostInodeUsageP0` | P0 | inode > 95% | 5m | <85% | `runbook-host-inode-usage` |

### 9.2 第二批：性能退化和故障前兆

| 告警 | 初始级别 | 条件建议 | 说明 |
| --- | --- | --- | --- |
| `HostCpuSaturationP1` | P1 | CPU 高且 load/core > 1.5 | 区分真实调度饱和 |
| `HostCpuStealHighP1` | P1 | steal > 10% 10m | 虚拟化资源争抢 |
| `HostSwapUsageHighP1` | P1 | swap > 30% 10m | 内存压力前兆 |
| `HostOomKillDetectedP0` | P0 | OOM kill 增量 > 0 | 已发生进程杀死 |
| `HostDiskWillFillP1` | P1 | 预测 24h 内写满 | 比静态阈值提前介入 |
| `HostDiskIoLatencyHighP1` | P1 | IO 延迟持续超过基线 | 存储退化 |
| `HostFilesystemReadOnlyP0` | P0 | 文件系统只读 | 直接影响写入 |

### 9.3 第三批：网络、内核与系统服务

| 告警 | 初始级别 | 条件建议 | 说明 |
| --- | --- | --- | --- |
| `HostNetworkErrorsHighP1` | P1 | 错包/丢包率持续升高 | 网络质量 |
| `HostConntrackNearlyFullP1` | P1 | entries/limit > 80% | 新连接风险 |
| `HostConntrackFullP0` | P0 | entries/limit > 95% | 连接可能失败 |
| `HostFileDescriptorNearlyFullP1` | P1 | allocated/max > 80% | 句柄耗尽风险 |
| `HostClockSkewP1` | P1 | 时间偏移 > 1s | TLS/一致性风险 |
| `CriticalSystemdServiceDownP1` | P1 | 指定关键服务 inactive | 需明确白名单 |

所有阈值都是初始值。上线前必须根据历史 p95/p99、主机规格、业务峰值和误报率调优，不能把示例值直接视为所有环境的永久标准。

## 10. Alertmanager 设计

### 10.1 路由原则

- P0/P1 同时进入独立值班渠道和 KubeOnCall。
- P2/P3 默认进入 KubeOnCall、低优先级 IM 或工单，不直接电话通知。
- `group_by` 优先使用 `cluster + alertname + service`，再根据具体策略决定是否加入 `instance`。
- P0 使用更短 `group_wait`，P2/P3 使用更长聚合窗口。
- `repeat_interval` 不等于 KubeOnCall 的诊断重跑间隔，二者单独配置。

示例：

```yaml
route:
  receiver: default-low-priority
  group_by: [cluster, alertname, service]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - receiver: oncall-primary
      matchers:
        - severity=~"P0|P1"
      group_wait: 10s
      group_interval: 2m
      repeat_interval: 30m
      continue: true

    - receiver: kubeoncall-webhook
      matchers:
        - severity=~"P0|P1"
      group_wait: 10s
      group_interval: 2m
      repeat_interval: 30m

    - receiver: kubeoncall-webhook
      matchers:
        - severity=~"P2|P3|INFO"
      group_wait: 1m
      group_interval: 15m
      repeat_interval: 12h

receivers:
  - name: default-low-priority
    # email/IM/ticket configuration

  - name: oncall-primary
    # PagerDuty/phone/SMS/IM configuration

  - name: kubeoncall-webhook
    webhook_configs:
      - url: https://kubeoncall.example/api/integrations/alertmanager/webhook
        send_resolved: true
        timeout: 10s
        http_config:
          authorization:
            type: Bearer
            credentials_file: /etc/alertmanager/secrets/kubeoncall-token
```

生产配置应通过配置模板或 Secret 管理凭据，禁止把 token 提交到仓库。

### 10.2 Inhibition 建议

```yaml
inhibit_rules:
  - source_matchers:
      - alertname="NodeExporterDown"
    target_matchers:
      - resource_type=~"node|process"
    equal: [cluster, instance]

  - source_matchers:
      - alertname="HostDiskUsageP0"
    target_matchers:
      - alertname="HostDiskUsageP1"
    equal: [cluster, instance, mountpoint]

  - source_matchers:
      - alertname="HostInodeUsageP0"
    target_matchers:
      - alertname="HostInodeUsageP1"
    equal: [cluster, instance, mountpoint]
```

Alertmanager inhibition 只处理清晰稳定的基础依赖。需要跨告警历史、服务拓扑或变更事件判断的复杂关联，交给 KubeOnCall。

### 10.3 Silence 边界

- 维护窗口由 Alertmanager silence 或外部变更平台管理。
- KubeOnCall 可以在审批通过后调用 Alertmanager 创建 silence。
- P0/P1 普通诊断不能自动 silence。
- Silence 必须包含创建人、原因、关联变更单、开始和结束时间。
- KubeOnCall 需要审计 silence 的申请、审批、创建、过期和删除。

## 11. Alertmanager Webhook 接口设计

### 11.1 新接口

```http
POST /api/integrations/alertmanager/webhook
Authorization: Bearer <token>
Content-Type: application/json
```

成功响应：

```json
{
  "accepted": 3,
  "duplicates": 1,
  "rejected": 0,
  "batchId": "am-batch-20260710-xxxx"
}
```

建议状态码：

| 状态码 | 含义 | Alertmanager 行为预期 |
| --- | --- | --- |
| `202` | 已持久化并接受后台处理 | 不需要立即完成诊断 |
| `400` | JSON 或必要字段无效 | 配置错误，应告警而非无限重试 |
| `401/403` | 鉴权失败 | 安全告警 |
| `413` | 批次或请求体过大 | 调整 `max_alerts` 或分组配置 |
| `429` | 接收端过载 | 允许上游稍后重试 |
| `500/503` | 尚未可靠持久化 | Alertmanager 重试 |

只有事件已经进入可靠 Inbox 后才能返回 `202`，不能先返回成功再尝试写入。

### 11.2 Webhook DTO

```java
public record AlertmanagerWebhookRequest(
        String version,
        String groupKey,
        Integer truncatedAlerts,
        String status,
        String receiver,
        Map<String, String> groupLabels,
        Map<String, String> commonLabels,
        Map<String, String> commonAnnotations,
        String externalURL,
        List<AlertmanagerAlertDto> alerts
) {}

public record AlertmanagerAlertDto(
        String status,
        Map<String, String> labels,
        Map<String, String> annotations,
        Instant startsAt,
        Instant endsAt,
        String generatorURL,
        String fingerprint
) {}
```

### 11.3 字段映射

| Alertmanager 字段 | KubeOnCall 字段 | 规则 |
| --- | --- | --- |
| `alerts[].fingerprint` | `fingerprint` | 优先使用；缺失时平台计算 |
| `alerts[].labels.alertname` | `alertName` | 必填 |
| `alerts[].status` | `status` | firing/resolved -> FIRING/RESOLVED |
| `labels.severity` | `rawSeverity` | 平台策略可上调但不得静默降级 critical |
| `labels.resource_type` | `resourceType` | 默认 node |
| `labels.node` 或 `labels.instance` | `resourceName` | 优先 node |
| `labels.cluster` | `cluster` | 多集群必须存在 |
| `labels.service` | `service` | 用于 owner 和记忆隔离 |
| `labels.kubeoncall_metric` | `metricName` | 平台规范指标名 |
| `labels.runbook_id` | `runbookId` | 必须与策略匹配 |
| `annotations.summary` | `summary` | 展示字段 |
| `labels` | `labels` | 保留白名单内标签 |
| `annotations` | `annotations` | 限长后保留 |
| `startsAt` | `occurredAt` | 首次发生时间 |
| `generatorURL` | `metadata.generatorUrl` | 跳转到 Prometheus 表达式 |
| `groupKey` | `metadata.alertmanagerGroupKey` | 不能代替单告警 fingerprint |

`currentValue`、`threshold`、`duration` 的处理：

- threshold 和 duration 优先来自命中的 KubeOnCall policy。
- currentValue 不依赖 description 文本解析。
- KubeOnCall 通过策略 PromQL 查询 Prometheus 当前值和窗口值。
- annotation 中的 `$value` 只用于展示和辅助审计。

### 11.4 输入限制

- `alerts` 不能为空。
- 默认单批最多 100 条，超出通过 Alertmanager `max_alerts` 和路由调整。
- 请求体建议限制在 1 MiB，最终值由压测确定。
- labels/annotations 的 key、value 都要限长。
- 只允许预定义 metadata 字段进入审计和检索 filter。
- 不信任 annotation 中的命令、URL 或处置步骤。
- Webhook 内容只能作为事实候选，不能直接触发命令执行。

## 12. 接收、幂等和异步处理

### 12.1 接收链路

```text
Webhook Controller
  -> authenticate
  -> validate batch
  -> map each alert to inbound event
  -> calculate deliveryKey
  -> persist raw payload + normalized candidate to Inbox
  -> return 202

Alarm Worker
  -> claim pending event
  -> ordering/idempotency check
  -> AlarmNormalizer
  -> AlarmPolicyEngine
  -> AlertWorkflowService
  -> audit result
  -> ACK or retry/dead-letter
```

### 12.2 幂等键

建议使用两个层次：

```text
alarm identity  = fingerprint
delivery key    = hash(fingerprint + status + startsAt + endsAt)
```

- fingerprint 用于关联同一告警生命周期。
- delivery key 用于识别 Alertmanager 重复 Webhook。
- Alertmanager `groupKey` 只标识通知组，不能作为单告警幂等键。
- FIRING 重复通知可以更新 lastSeen/count，但不能重复执行全部重型诊断。
- 若诊断需要周期刷新，必须使用独立 `diagnosisRefreshInterval`，不能直接跟随 `repeat_interval`。

### 12.3 Inbox 方案

MVP 使用现有 Redis：

- Redis Stream 保存待处理事件。
- Consumer Group 多实例消费。
- Redis Hash 保存 deliveryKey 状态和告警时序游标。
- 开启 AOF，并配置合理保留时间。
- 超过最大重试次数转入 dead-letter stream。

生产量较大或要求更高持久性时，可替换成 Kafka/RabbitMQ。上层接口通过 `AlarmEventInbox` 抽象，避免业务层依赖具体消息中间件。

建议接口：

```java
public interface AlarmEventInbox {
    EnqueueResult enqueue(InboundAlarmEvent event);
    List<ClaimedAlarmEvent> claim(String consumer, int batchSize, Duration block);
    void acknowledge(String eventId);
    void retry(String eventId, String reason, Instant nextAttemptAt);
    void deadLetter(String eventId, String reason);
}
```

### 12.4 乱序保护

每个 fingerprint 保存：

- `latestStartsAt`
- `latestEndsAt`
- `latestStatus`
- `latestReceivedAt`
- `generation`

处理规则：

1. 新 FIRING 的 startsAt 早于已确认 RESOLVED 生命周期时，标记 stale，不重新打开告警。
2. RESOLVED 只允许关闭相同或更早 startsAt 的活动告警。
3. 新 startsAt 明显晚于旧生命周期，视为新一轮告警。
4. 时间字段缺失时进入兼容路径，但必须在 audit 标记低置信度。

## 13. KubeOnCall 内部处理流程

### 13.1 FIRING

```text
接收 FIRING
  -> 标准化和 policy match
  -> active state 更新
  -> 平台 dedup/关联/抑制
  -> 回查 Prometheus 当前和历史指标
  -> 获取 Linux/K8s/日志上下文
  -> 严格 Runbook RAG
  -> 召回同 fingerprint/service/resource 历史记忆
  -> 结构化诊断
  -> 发送诊断补充/创建工单
  -> 高风险动作进入审批
  -> 记录审计和处理指标
```

### 13.2 RESOLVED

当前实现收到 RESOLVED 后立即确认恢复，重构后改为：

```text
接收 RESOLVED
  -> 标记 recovery candidate
  -> 等待 policy recoveryWindow
  -> 使用 policy PromQL 回查
  -> 连续 N 次健康或窗口内无同 fingerprint FIRING
  -> confirmed recovered
  -> 关闭/更新工单
  -> 写入 incident summary memory
  -> 通知恢复
```

建议初始值：

- P0：连续 3 次健康检查，并允许人工确认。
- P1：连续 2 次健康检查。
- P2/P3：可直接依赖 Prometheus RESOLVED，但仍记录恢复窗口。
- 若 Prometheus 不可用，状态标记 `RECOVERY_UNVERIFIED`，不能伪装为已确认恢复。

### 13.3 Prometheus 回查

KubeOnCall 不从 Webhook description 反解析数值，使用：

- `/api/v1/query` 查询当前值。
- `/api/v1/query_range` 查询告警前后窗口。
- `generatorURL` 仅作为排障跳转，不直接信任其中的查询参数。
- 实际查询使用命中 policy 的 PromQL 和经过白名单校验的标签。

Prometheus 查询失败时：

- 告警仍进入工作流。
- 标记 `metricsUnavailable=true`。
- 禁止因为缺少指标而自动恢复或自动变更。
- RAG 和历史记忆可以提供建议，但必须明确当前证据缺失。

### 14.1 目标形态

当前 `alarm-policies.yml` 已有 `promql`、`threshold`、`for`、`severity`、`recover`、`runbookId` 和 `actions`。目标是新增：

### 14.3 编译规则

新增：

- `AlarmPolicyCompiler`
- `PrometheusRuleRenderer`
- `AlarmPolicyValidationService`
- `AlarmPolicyVersionService`
- `AlarmPolicyDryRunService`

编译必须校验：

- P0/P1 有 owner 和 runbook。
- PromQL 非空且可通过 promtool。

- `promtool check rules` 成功后才允许发布。
- 发布使用临时文件加原子替换。
- Prometheus reload 失败时保留旧规则。
- 保存最近 N 个已发布版本，支持一键回滚。
- KubeOnCall 审计记录发布人、版本、checksum、diff 和结果。

## 15. 通知、工单与防环设计

### 15.1 通知分层

| 消息 | 发送者 | 目的 |
| --- | --- | --- |
| 首次 P0/P1 page | Alertmanager | 最快触达值班人 |
| 告警恢复基础通知 | Alertmanager | 告知指标条件恢复 |
| 智能诊断补充 | KubeOnCall | 当前证据、Runbook、历史案例和建议 |
| 升级通知 | KubeOnCall/Incident 平台 | 未确认、影响扩大、长时间未恢复 |
| 工单 | KubeOnCall -> Ticket Adapter | 跟踪处置生命周期 |
| 处置审批 | KubeOnCall Approval | 控制重启、扩容、静默等变更 |

### 15.2 防环规则

- Alertmanager 入站消息标记 `origin=alertmanager`。
- KubeOnCall 诊断消息标记 `eventType=diagnosis`，不得调用同一告警入站接口。
- `ResultPushNode` 重构为通知/事件发布，不再把普通结果解释成创建 silence。
- 若确需把新告警发送到 Alertmanager，必须使用不同 alertName、origin 和独立 fingerprint，并配置禁止再次进入原工作流。
- 入站事件发现 `origin=kubeoncall` 时执行显式路由，默认拒绝递归处理。

## 16. 安全设计

### 16.1 网络和认证

- Webhook 使用 HTTPS。
- 生产优先 mTLS；最低要求 Bearer Token + 私网访问控制。
- token 从 Secret 文件读取，支持轮换。
- Ingress 只允许 Alertmanager 网段或身份访问。
- 限制请求速率、并发、连接数和请求体大小。
- 认证失败和异常流量进入安全审计及告警。

Alertmanager 原生 Webhook 不提供通用消息签名，因此不能假设 payload 自带 HMAC。若必须使用 HMAC，应在 Alertmanager 与 KubeOnCall 之间部署受控 webhook gateway，由 gateway 增加签名。

### 16.2 数据安全

- labels/annotations 视为不可信输入。
- 不执行 annotation 中的命令。
- URL 只允许白名单域名或作为纯文本展示。
- 审计前过滤 token、密码、Authorization、cookie 等字段。
- 原始 payload 设置保留周期和访问权限。
- 告警内容进入 RAG/LLM 前进行长度限制和提示注入防护。

### 16.3 自动化边界

- 只读 Prometheus 查询可以自动执行。
- 日志、describe、指标查询可以自动执行。
- restart、scale、patch、silence、delete 必须经过工具白名单和审批。
- P0 不代表允许更激进自动操作，反而应提高审批和证据要求。

新增指标建议：

```text
kubeoncall_alertmanager_webhook_requests_total{status}
kubeoncall_alertmanager_webhook_alerts_total{status,severity}
kubeoncall_alarm_inbox_depth
kubeoncall_alarm_inbox_oldest_seconds

kubeoncall_alarm_processing_duration_seconds{workflow,severity}

kubeoncall_alarm_dead_letter_total{reason}
kubeoncall_alarm_recovery_candidates_total

kubeoncall_prometheus_query_failures_total{operation}
kubeoncall_policy_compile_total{status}
kubeoncall_policy_reload_total{status}
```

必须建设的告警：

- Alertmanager 到 KubeOnCall Webhook 连续失败。
- Inbox 积压或最老事件超过阈值。
- dead-letter 出现新事件。
- KubeOnCall Prometheus 回查持续失败。
- policy 编译或 reload 失败。
- Node Exporter target 大面积 down。
- 告警链路心跳测试失败。

审计字段至少包括：

- batchId、eventId、deliveryKey、fingerprint。
- Alertmanager groupKey、receiver、status。
- 原始 severity 和平台最终 severity。
- policyId、policyVersion、PromQL checksum。
- suppression/dedup/recovery 决策。
- RAG 文档、记忆 ID、工具调用和审批结果。
- 通知、工单和处置结果。

## 18. 失败处理与降级

| 故障 | 预期行为 |
| --- | --- |
| KubeOnCall 不可用 | Alertmanager 继续直接通知值班人并重试 Webhook |
| Redis Inbox 不可用 | Webhook 返回 503，不返回虚假 202 |
| Prometheus 查询失败 | 保留告警，标记证据缺失，禁止自动恢复/变更 |
| ES/RAG 不可用 | 使用当前指标和固定 Runbook 链接，工作流降级 |
| LLM 不可用 | 输出规则化诊断和原始证据，不影响首次通知 |
| 工单平台不可用 | 进入 Outbox 重试，不阻塞告警接收 |
| 通知平台不可用 | Alertmanager 与 KubeOnCall 独立记录失败并重试 |
| 策略编译失败 | 不替换线上规则，继续使用上一版本 |
| Webhook 重复投递 | deliveryKey 去重，只更新 lastSeen/count |
| FIRING/RESOLVED 乱序 | 按 fingerprint 生命周期游标拒绝陈旧状态 |

- 单批 1、10、100 条告警。
- 每秒 10、50、100 个 Webhook 批次。
- 1 万条重复告警的幂等成本。
- Inbox 积压后的恢复速度。
- RAG/LLM 慢响应不影响 Webhook P95。

初始 SLO：

- Webhook P95 < 500ms，P99 < 1s，不包含后台诊断。
- 成功持久化事件丢失率为 0。
- 重复事件重型工作流重复执行率 < 0.1%。
- P0/P1 从 Alertmanager 到值班渠道 < 1 分钟。
- P0/P1 从 KubeOnCall 接收到首版诊断结果 < 5 分钟。

## 23. 验收标准

### 23.1 功能验收

- Linux CPU、内存、磁盘、inode 和 up 指标可查询。
- 第一批规则能正确 pending、firing 和 resolved。
- Alertmanager 能独立通知值班人。
- Alertmanager 批量 Webhook 可以拆分成标准事件。
- FIRING 和 RESOLVED 正确进入同一 fingerprint 生命周期。
- KubeOnCall 能回查 Prometheus、检索正确 Runbook 并生成诊断。
- 重复投递不重复执行重型工作流。
- 恢复确认后可以更新通知和工单。

### 23.2 可靠性验收

- Webhook 只有在可靠持久化后返回 202。
- Redis、ES、LLM、RAG 任一依赖故障不会阻断 Alertmanager 首次 P0/P1 通知。
- Inbox 支持重试和 dead-letter。
- 乱序告警不会错误重开或关闭生命周期。
- 规则发布失败不会破坏线上旧版本。

### 23.3 安全验收

- 未认证 Webhook 请求被拒绝。
- secrets 不出现在仓库、日志和审计 payload。
- annotation 命令不会被执行。
- 高风险动作必须审批。
- 普通 P0/P1 处理不会自动 silence。

### 23.4 治理验收

- 每条 P0/P1 有 owner、runbook、恢复条件和测试。
- 规则通过 promtool。
- 策略版本、checksum 和发布审计可追溯。
- 可以 dry-run、回放和回滚。

## 24. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Prometheus rules 与 KubeOnCall policy 双写 | 阈值和等级不一致 | 建设编译器；过渡期做一致性测试 |
| Alertmanager 分组过大 | Webhook 超限和处理变慢 | 合理 group_by、max_alerts、批量限制 |
| 同时多渠道通知 | 用户收到重复消息 | 区分首次 page 与诊断补充，统一 event link |
| Node Exporter 标签不规范 | fingerprint 错误和聚合混乱 | 强制标签契约和目标注册校验 |
| RAG/LLM 响应慢 | Webhook 超时 | Inbox 异步化，接收与诊断解耦 |
| Redis 丢失或不可用 | 事件丢失/积压 | AOF、HA、503、dead-letter、监控 |
| RESOLVED 乱序 | 错误关闭活动告警 | 生命周期游标和 startsAt 校验 |
| 告警规则太多 | 值班疲劳 | 分批上线、dry-run、回放、噪声指标 |
| KubeOnCall 成为单点 | P0 无人通知 | Alertmanager 独立值班 receiver |
| 自动 silence/处置误操作 | 隐藏故障或扩大影响 | 默认关闭、审批、工具白名单、审计 |

## 25. 回滚方案

每个阶段独立可回滚：

1. Webhook 异常：从 Alertmanager 路由中临时移除 KubeOnCall receiver，不影响值班 receiver。
2. 新规则噪声过大：禁用单条 rule 或回滚上一规则版本。
3. Inbox Worker 异常：停止 worker，保留 stream，修复后重放。
4. 新恢复逻辑异常：关闭 `verification-enabled`，退回仅记录 RESOLVED 但不执行自动关闭。
5. 策略编译器异常：关闭 `policy-publish.enabled`，继续使用上一版本 Prometheus rules。
6. 新接口异常：旧 `/api/alarms` 继续保留，供人工和兼容调用。

回滚不得删除 Inbox、dead-letter、审计和原始事件，应保留故障分析证据。

## 26. 推荐实施顺序

优先级顺序：

1. Node Exporter + Prometheus + Alertmanager 基础链路。
2. P0/P1 独立值班 receiver，先确保“能及时叫到人”。
3. Alertmanager 批量 Webhook + Redis Inbox + 幂等。
4. Prometheus 回查和 RESOLVED 恢复确认。
5. Notification/Ticket/Incident 真实闭环。
6. 策略编译、reload、版本、回放和回滚。
7. Linux 扩展规则、Blackbox 和服务 SLO。

不建议先做自动修复。只有在告警事实、去重、恢复、审计、审批和回滚全部稳定后，才逐步开放低风险自动操作。

## 27. 最终目标

重构完成后的 KubeOnCall 不只是“接收 Prometheus 告警的 Webhook”，而是一套职责清晰的智能运维闭环：

```text
Node Exporter 提供 Linux 事实
Prometheus 判断指标条件
Alertmanager 保证基础通知和降噪
KubeOnCall 完成业务治理、诊断、知识、记忆、工单和受控处置
```

这套设计保留 Prometheus 生态的可靠边界，同时发挥 KubeOnCall 在上下文理解、RAG、历史记忆和自动化编排方面的价值。即使 KubeOnCall 的智能能力暂时不可用，基础 P0/P1 告警仍然能触达值班人；当 KubeOnCall 正常时，则能够把一条资源告警提升为可解释、可审计、可执行的事故处理流程。
