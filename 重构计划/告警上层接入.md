# KubeOnCall Kubernetes 节点监控告警 MVP 计划

## 1. 目标

本轮只完成 Kubernetes 节点的最小监控告警闭环：Prometheus 发现节点异常，Alertmanager 转发告警，KubeOnCall 记录、做简单诊断并发送通知。

```text
Kubernetes 节点
  -> Node Exporter
  -> Prometheus（采集 + 5～6 条规则）
  -> Alertmanager（一个 Webhook receiver）
  -> KubeOnCall（Webhook、去重、记录、简单诊断、通知）
```

Prometheus 原生告警必须经 Alertmanager 发送，因此 Alertmanager 保留为最小转发层；本轮不把 KubeOnCall 建设成完整的告警平台或事故管理平台。

## 2. 本轮范围

### 2.1 采集组件

- 必选：每个需要监控的节点部署 Node Exporter，提供 CPU、内存、文件系统和 inode 指标。
- 可选：只有需要 `NodeNotReady` 时才部署 kube-state-metrics；该规则依赖 Kubernetes Node 状态指标，Node Exporter 本身无法提供。
- 首次演练只接入一台测试节点，Prometheus 使用静态 target；不引入服务发现、多集群或自动注册。

### 2.2 Prometheus 规则

只保留下列六类规则，其中第六项可在未部署 kube-state-metrics 时暂不启用：

| 规则 | 指标来源 | 目的 |
| --- | --- | --- |
| `NodeDown` | Prometheus `up` | Node Exporter 不可抓取或节点不可达 |
| `NodeCPUHigh` | Node Exporter | 节点 CPU 使用率持续过高 |
| `NodeMemoryLow` | Node Exporter | 节点可用内存持续过低 |
| `NodeDiskHigh` | Node Exporter | 文件系统使用率持续过高 |
| `NodeInodeHigh` | Node Exporter | 文件系统 inode 使用率持续过高 |
| `NodeNotReady` | kube-state-metrics | Kubernetes Node 处于 NotReady |

规则必须包含 `severity`、`cluster`、`instance` 或 `node`、`summary` 等足以定位节点的标签或注释。阈值和 `for` 时长以测试环境实际观测为准；本轮只要求规则可验证地经历 `pending -> firing -> resolved`。

### 2.3 Alertmanager

- 只配置一个指向 KubeOnCall 的 Webhook receiver。
- 开启 `send_resolved`，使恢复事件也会发送给 KubeOnCall。
- 采用最小分组和默认重试配置；不配置独立值班 receiver、复杂路由、inhibition 或 silence。
- Bearer Token 从配置或 Secret 文件注入，不能硬编码进仓库。

### 2.4 KubeOnCall

本轮只使用和验收以下能力：

- Alertmanager 批量 Webhook 接收；
- Bearer 鉴权；
- 按告警 fingerprint 的基础去重；
- 告警记录与审计；
- 基于已有规则或 Runbook 的简单诊断；
- 已配置通知渠道的基础通知。

现有 Redis Inbox 可以继续保留，用于把 Webhook 接收与后续处理解耦；不再为此投入 Kafka 替换、Redis HA/AOF、多消费者吞吐或 Pending reclaim 压测等生产级建设。

不把工单、审批、RAG、记忆、变更关联或自动修复作为本轮依赖或验收条件。它们即使在代码中已经存在，也不进入节点监控 MVP 的演示路径。

## 3. 组件职责

| 组件 | 本轮职责 | 不负责 |
| --- | --- | --- |
| Node Exporter | 暴露节点资源指标 | Kubernetes Node Ready 状态 |
| kube-state-metrics（可选） | 暴露 Kubernetes Node 状态 | 主机资源指标 |
| Prometheus | 抓取指标、计算 PromQL、触发规则 | 告警处理和业务诊断 |
| Alertmanager | 最小分组、重试、转发 firing/resolved | 多渠道值班、复杂降噪与 HA |
| KubeOnCall | 接收、鉴权、去重、记录、简单诊断、通知 | 工单、审批、知识检索、自动处置 |

## 4. 实施与验收顺序

### 步骤 1：接入测试节点

1. 部署 Node Exporter。
2. 在 Prometheus 配置该节点的静态 scrape target。
3. 如需 `NodeNotReady`，再部署 kube-state-metrics 并配置对应 target。

验收：Prometheus 查询 `up`、CPU、内存、文件系统和 inode 指标均有数据；若部署 kube-state-metrics，Node 状态指标也有数据。

### 步骤 2：启用最小规则

1. 仅启用第 2.2 节的五条 Node Exporter 规则；有 kube-state-metrics 时再启用 `NodeNotReady`。
2. 使用 `promtool` 校验规则文件。
3. 人为制造 CPU 或磁盘压力，验证至少一条规则的 `pending -> firing -> resolved`。

验收：规则语法通过，Prometheus UI 可见状态变化及完整节点定位信息。

### 步骤 3：接通 KubeOnCall

1. 将 Alertmanager 的唯一 receiver 指向 KubeOnCall Webhook。
2. 配置 Bearer Token，并确认认证失败返回 `401`。
3. 触发一条规则，验证 Webhook 返回 `202`、KubeOnCall 有记录和通知。
4. 重复投递同一告警，验证不重复执行重型处理；恢复后验证收到 `RESOLVED`。

验收：完成一次测试节点从触发到恢复的完整演练。

## 5. 交付物

- Node Exporter 部署说明与一台测试节点的 target 配置；
- kube-state-metrics 部署说明（仅启用 `NodeNotReady` 时需要）；
- Prometheus 节点规则文件和 `promtool` 校验结果；
- 一个 Alertmanager Webhook receiver 配置；
- KubeOnCall Bearer Token 配置说明；
- 一次 `pending -> firing -> resolved` 演练记录。

## 6. 明确延期或删除

以下项目不属于本轮，也不得作为节点监控 MVP 的完成前提：

1. P0/P1 独立值班 receiver，以及复杂 inhibition/silence。
2. mTLS、Ingress 网段控制、Redis HA/AOF、多消费者和 Pending reclaim 压测。
3. 策略编译到 Prometheus 发布、checksum、原子回滚和规则版本平台。
4. Blackbox HTTP/TCP/DNS、服务 SLO、Burn Rate。
5. 变更关联、告警健康度、周报、复杂灰度。
6. PagerDuty、Jira、ServiceNow 适配，工单、审批和自动处置。
7. RAG、记忆和自动修复作为告警处理的强制依赖。

这些能力可保留现有代码和配置，未来有明确生产需求时再单独立项；本轮不继续实现、扩展或以其作为测试标准。

## 7. 完成定义

以下四项全部满足，即视为本计划完成：

1. 一台测试节点的 Node Exporter 已被 Prometheus 稳定抓取；如启用 `NodeNotReady`，kube-state-metrics 同样已被抓取。
2. 五条基础节点规则（或含 `NodeNotReady` 的六条）通过 `promtool`，并至少完成一次 pending、firing、resolved 演练。
3. Alertmanager 的一个 receiver 能携带 Bearer Token 将 firing 与 resolved 发至 KubeOnCall，KubeOnCall 返回 `202`。
4. KubeOnCall 可看到告警记录、基础去重结果、简单诊断或通知结果。
