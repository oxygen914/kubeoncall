# KubeOnCall 告警策略重构方案

## 1. 背景与目标

KubeOnCall 当前已经具备告警事件入口与自动化处置工作流：

- `POST /api/alarms` 接收外部告警。
- `AlarmController` 将 `AlarmRequest` 转为 `AlarmEvent`。
- `AlertWorkflowService` 负责 Redis 去重、节点编排、失败降级和审计。
- `AlertWorkflowFactory` 固定编排 `logCollectionNode -> deviceInfoNode -> stateCompareNode -> knowledgeRetrieveNode -> resultPushNode`。
- `PrometheusToolExecutor`、`KubernetesToolExecutor`、`AlertmanagerToolExecutor` 已经能查询指标、K8s 上下文和 Alertmanager。

当前短板是：系统有“告警事件处理链路”，但缺少“告警策略治理层”。也就是说，告警严重级别、阈值、持续时间、抑制规则、升级策略、Runbook 绑定、自动处置边界目前没有被模型化，更多依赖上游 Alertmanager 或人工约定。

本方案目标：

1. 建立专业、可配置、可审计的告警分级体系。
2. 设计覆盖 CPU、内存、磁盘、网络、Kubernetes 节点、Pod、Deployment、控制面等核心场景的默认策略。
3. 将“策略匹配/分级/抑制/路由”和“自动诊断工作流”解耦。
4. 让告警策略可以灰度、回放、评估和持续调优。
5. 让 P0/P1 告警既能快速触达值班人，也能自动收集上下文、检索 SOP、生成处置建议。

## 2. 当前告警实现判断

### 2.1 已有能力

当前代码中已经有良好的告警工作流骨架：

- `AlarmEvent` 有 `alarmId`、`dedupKey`、`source`、`severity`、`nodeName`、`summary`、`occurredAt`、`metadata`。
- `AlertWorkflowService` 使用 Redis `setIfAbsent` 做 TTL 去重，默认 TTL 为 `600s`。
- `WorkflowNodeExecutor` 统一处理节点耗时、异常、失败、终止和降级。
- `LogCollectionNode` 会通过 Kubernetes 工具查询日志。
- `DeviceInfoNode` 会查询设备信息。
- `StateCompareNode` 会通过 Prometheus 做区间查询。
- `KnowledgeRetrieveNode` 会检索 SOP 并补充 metric snapshot。
- `ResultPushNode` 会调用 Alertmanager 工具。
- `ExecutionAuditService` 会记录告警执行审计。

这些能力适合承载“告警后自动诊断”。

### 2.2 主要问题

1. `AlarmEvent.severity` 是上游传入的字符串，缺少平台内统一分级枚举和计算规则。

2. `AlarmRequest` 过薄，缺少 `alertName`、`resourceType`、`metricName`、`currentValue`、`threshold`、`duration`、`labels`、`annotations`、`runbookId`、`fingerprint` 等关键字段。

3. 当前没有策略引擎。CPU 高、磁盘满、Pod CrashLoop、Node NotReady 等规则没有在 KubeOnCall 中沉淀。

4. 当前去重只依赖传入 `dedupKey`，没有规范化 fingerprint。如果上游没有稳定 dedupKey，会产生重复告警或错误合并。

5. `AlertWorkflowFactory` 固定写死节点序列，无法根据告警类型选择不同诊断流程。

6. `StateCompareNode` 默认查询 `up{instance="nodeName"}`，没有根据 CPU/磁盘/K8s 告警自动选择 PromQL。

7. `ResultPushNode` 当前使用 `alertmanager.createSilence` 推送结果。静默是变更/维护动作，不应作为普通告警处理结果的默认动作，尤其 P0/P1 不应自动静默。

8. 缺少告警抑制、关联、升级、恢复、维护窗口和噪声治理机制。

9. 缺少策略版本、策略测试、历史回放和误报分析。

## 3. 设计原则

1. **分级要看影响面，不只看数值。** 同样 CPU 85%，核心生产服务和实验环境节点的严重级别应不同。

2. **阈值必须配持续时间。** 单点尖峰不应直接触发高等级告警；P0 可以更敏感，但仍应至少有 2 到 5 分钟确认窗口。

3. **告警分为症状告警和根因告警。** CPU 高是症状，Node NotReady、磁盘只读、Pod CrashLoop 可能更接近根因。需要抑制低价值重复症状。

4. **P0/P1 默认通知人，不默认自动改状态。** 自动扩容、重启、静默、驱逐等动作必须受风险策略和审批约束。

5. **每条策略必须有 owner、runbook、恢复条件和测试样例。** 没有 owner 的告警最终会变成噪音。

6. **策略配置和处理流程解耦。** 策略判断可以经常调，工作流节点不应频繁改代码。

7. **先可解释，再智能化。** LLM/RAG 用于补充 SOP 和诊断建议，告警分级和通知策略应由显式规则决定。

## 4. 严重级别模型

建议统一使用 `P0/P1/P2/P3` 四级，并保留 `INFO` 用于审计和趋势事件。

| 等级 | 含义 | 响应目标 | 典型场景 | 自动化边界 |
| --- | --- | --- | --- | --- |
| P0 | 已经或即将造成核心服务不可用、数据风险或大面积故障 | 5 分钟内响应，立即电话/IM 升级 | 核心服务全量不可用、多节点 NotReady、磁盘 > 95%、API Server 不可用 | 自动诊断、上下文收集、建议生成；高风险动作需审批 |
| P1 | 明显影响稳定性或容量，短期内可能升级为 P0 | 15 分钟内响应 | CPU > 70%、磁盘 > 85%、Pod CrashLoop、Deployment 副本不足 | 可自动收集、可建议扩容/重启；执行需按风险审批 |
| P2 | 有风险但影响有限，适合工作时间处理 | 4 小时内响应 | CPU > 60%、磁盘 > 75%、重启次数异常、证书 30 天过期 | 自动建工单或低优先级通知 |
| P3 | 趋势、提醒、容量规划 | 1 到 3 天内处理 | 磁盘预测 7 天内打满、资源请求不合理 | 只记录和周报汇总 |
| INFO | 状态变化或恢复事件 | 无强响应 | 告警恢复、维护窗口进入/退出 | 审计与关联 |

严重级别计算建议使用三段式：

```text
base severity = metric threshold + duration
impact factor = env + service criticality + affected scope
final severity = max(base severity adjusted by impact factor, explicit upstream severity)
```

影响因子建议：

- `env=prod` 或 `criticality=tier0/tier1` 可上调一级。
- `env=dev/lab` 可下调一级，但 P0 根因类告警不下调。
- `affectedPods >= 3`、`affectedNodes >= 2`、`availability < 95%` 可上调一级。
- 维护窗口内只降级通知，不应直接丢弃，除非明确匹配 silence。

## 5. 告警事件标准模型

建议升级 `AlarmEvent` 为 V2，或者新增 `NormalizedAlarmEvent`，保留旧字段兼容。

核心字段：

| 字段 | 说明 |
| --- | --- |
| `alarmId` | 本次告警事件 ID |
| `fingerprint` | 平台规范化指纹，用于去重与聚合 |
| `alertName` | 策略名，如 `HostHighCpuUsage` |
| `source` | `prometheus`、`alertmanager`、`kubernetes`、`manual` |
| `severity` | 最终等级：`P0/P1/P2/P3/INFO` |
| `rawSeverity` | 上游原始等级 |
| `resourceType` | `node/pod/deployment/namespace/cluster/service` |
| `resourceName` | 资源名 |
| `cluster` | 集群 |
| `namespace` | 命名空间 |
| `service` | 服务名 |
| `metricName` | 指标名 |
| `currentValue` | 当前值 |
| `threshold` | 触发阈值 |
| `unit` | `%/bytes/count/qps/ms` |
| `duration` | 持续时间 |
| `labels` | 标签集合 |
| `annotations` | 展示信息 |
| `runbookId` | SOP/RAG 检索关联 |
| `occurredAt` | 首次发生时间 |
| `startsAt` | 本轮告警开始时间 |
| `endsAt` | 恢复时间 |
| `status` | `FIRING/RESOLVED/SUPPRESSED` |

规范化 fingerprint：

```text
fingerprint = hash(alertName + cluster + namespace + resourceType + resourceName + service + key labels)
```

`dedupKey` 可以由 fingerprint 派生，而不是完全依赖上游传入。

## 6. 默认告警策略目录

以下策略是 KubeOnCall 的建议默认集。阈值应作为初始值，后续结合历史 p95/p99、容量模型和误报率调优。

### 6.1 主机 CPU

| 策略 | 等级 | 触发条件 | 持续时间 | 恢复条件 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `HostHighCpuUsageP1` | P1 | CPU 使用率 > 70% | 10m | < 65% 持续 10m | 用户指定的 P1 基线，适合提前介入 |
| `HostHighCpuUsageP0` | P0 | CPU 使用率 > 85% | 5m | < 75% 持续 10m | 用户指定的 P0 基线，表示容量或异常进程风险高 |
| `HostCpuSaturationP0` | P0 | CPU > 85% 且 load1 / cpu_cores > 1.5 | 5m | 任一条件恢复 10m | 避免只看 CPU，增加调度队列饱和判断 |
| `HostCpuStealHighP1` | P1 | steal CPU > 10% | 10m | < 5% 持续 10m | 虚拟化宿主资源争抢 |

PromQL 示例：

```promql
100 * (1 - avg by (cluster, instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))) > 70
```

P0 示例：

```promql
100 * (1 - avg by (cluster, instance) (rate(node_cpu_seconds_total{mode="idle"}[5m]))) > 85
```

处置建议：

- 自动查询 top CPU 进程、Pod CPU 使用、最近发布/变更。
- 若为 Kubernetes 节点，查询该节点 Pod 分布和是否存在单 Pod 异常。
- P1 建议扩容、迁移低优先级负载或限流。
- P0 若核心服务受影响，通知值班人和 owner，自动化动作需审批。

### 6.2 主机内存

| 策略 | 等级 | 触发条件 | 持续时间 | 恢复条件 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `HostMemoryPressureP1` | P1 | 可用内存 < 20% | 10m | > 25% 持续 10m | 内存压力预警 |
| `HostMemoryPressureP0` | P0 | 可用内存 < 10% 或发生 OOM | 5m | > 20% 持续 10m | 高风险，可能导致进程被杀 |
| `HostSwapUsageP1` | P1 | swap 使用率 > 30% | 10m | < 10% 持续 10m | Linux 主机性能抖动风险 |

PromQL 示例：

```promql
100 * (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) < 20
```

处置建议：

- 关联 OOMKilled、Pod memory usage、JVM heap、容器 limit。
- 对实验环境可先建议扩容或降低并发。
- 对核心服务，优先判断是否存在内存泄漏和最近发布。

### 6.3 磁盘与 inode

| 策略 | 等级 | 触发条件 | 持续时间 | 恢复条件 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `HostDiskUsageP2` | P2 | 文件系统使用率 > 75% | 15m | < 70% 持续 15m | 容量趋势预警 |
| `HostDiskUsageP1` | P1 | 文件系统使用率 > 85% | 10m | < 80% 持续 15m | 需要值班介入清理或扩容 |
| `HostDiskUsageP0` | P0 | 文件系统使用率 > 95% 或根分区 > 90% | 5m | < 85% 持续 15m | 即将写满，可能导致服务不可用 |
| `HostDiskWillFillP1` | P1 | 预测 24h 内写满 | 10m | 预测时间 > 72h | 比静态阈值更早发现 |
| `HostInodeUsageP1` | P1 | inode 使用率 > 85% | 10m | < 80% 持续 15m | 小文件耗尽风险 |
| `HostInodeUsageP0` | P0 | inode 使用率 > 95% | 5m | < 85% 持续 15m | 可能无法创建文件 |
| `DiskReadOnlyP0` | P0 | 文件系统只读或 mount 异常 | 1m | 恢复读写 | 直接影响服务写入 |

PromQL 示例：

```promql
100 * (1 - node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes{fstype!~"tmpfs|overlay"}) > 85
```

预测写满：

```promql
predict_linear(node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"}[6h], 24 * 3600) < 0
```

inode：

```promql
100 * (1 - node_filesystem_files_free{fstype!~"tmpfs|overlay"} / node_filesystem_files{fstype!~"tmpfs|overlay"}) > 85
```

处置建议：

- 自动采集 `df -h`、`df -i`、最大目录、日志增长速度。
- 区分 `/`、`/var/lib/containerd`、`/var/lib/kubelet`、业务数据盘。
- P0 不建议自动删除文件；可自动给出候选清理项，需人工确认。
- 对容器日志盘，优先检查日志轮转和异常刷日志 Pod。

### 6.4 网络与连接

| 策略 | 等级 | 触发条件 | 持续时间 | 说明 |
| --- | --- | --- | --- | --- |
| `HostNetworkErrorsP1` | P1 | 网卡错误包/丢包率 > 1% | 10m | 网络质量风险 |
| `HostNetworkSaturationP1` | P1 | 出入带宽 > 80% 网卡容量 | 10m | 容量风险 |
| `TcpConntrackNearlyFullP1` | P1 | conntrack 使用率 > 80% | 10m | K8s 节点常见网络故障前兆 |
| `TcpConntrackFullP0` | P0 | conntrack 使用率 > 95% | 3m | 可能导致新连接失败 |

PromQL 示例：

```promql
node_nf_conntrack_entries / node_nf_conntrack_entries_limit > 0.8
```

### 6.5 Kubernetes 节点

| 策略 | 等级 | 触发条件 | 持续时间 | 说明 |
| --- | --- | --- | --- | --- |
| `KubeNodeNotReadyP0` | P0 | Node Ready != true | 3m | 节点不可调度或离线 |
| `KubeNodePressureP1` | P1 | MemoryPressure/DiskPressure/PIDPressure 为 true | 5m | 节点资源压力 |
| `KubeNodeUnschedulableP2` | P2 | 节点不可调度且非维护窗口 | 15m | 容量下降 |
| `KubeletDownP0` | P0 | kubelet target down | 2m | 节点管理面不可用 |
| `NodePodCapacityHighP1` | P1 | Pod 数 > 节点容量 85% | 10m | 调度容量风险 |

PromQL 示例：

```promql
kube_node_status_condition{condition="Ready",status="true"} == 0
```

处置建议：

- 自动执行 `describe node`、查询 kubelet 状态、节点事件、最近驱逐事件。
- DiskPressure 时联动磁盘策略和 `/var/lib/kubelet`、`containerd` 空间采集。
- 多节点同时 NotReady 直接 P0，并抑制单节点上的 Pod Pending/Unavailable 告警。

### 6.6 Kubernetes Pod

| 策略 | 等级 | 触发条件 | 持续时间 | 说明 |
| --- | --- | --- | --- | --- |
| `PodCrashLoopBackOffP1` | P1 | Pod 处于 CrashLoopBackOff | 5m | 服务实例持续崩溃 |
| `PodCrashLoopBackOffP0` | P0 | 核心服务可用副本低于 50% 且 CrashLoop | 3m | 可用性高风险 |
| `PodOOMKilledP1` | P1 | 10m 内 OOMKilled > 0 | 1m | 内存 limit 或泄漏问题 |
| `PodRestartRateHighP1` | P1 | 15m 内重启次数 > 3 | 10m | 异常重启 |
| `PodPendingP1` | P1 | Pending > 10m | 10m | 调度失败或镜像拉取失败 |
| `PodImagePullBackOffP1` | P1 | ImagePullBackOff > 5m | 5m | 镜像仓库、权限或 tag 问题 |
| `PodNotReadyP1` | P1 | Ready=false > 10m | 10m | 探针、依赖或启动失败 |

PromQL 示例：

```promql
max_over_time(kube_pod_container_status_waiting_reason{reason="CrashLoopBackOff"}[5m]) > 0
```

OOMKilled：

```promql
increase(kube_pod_container_status_restarts_total[10m]) > 0
and on (cluster, namespace, pod, container)
kube_pod_container_status_last_terminated_reason{reason="OOMKilled"} == 1
```

处置建议：

- 自动采集 `kubectl describe pod`、上一次容器退出原因、最近 100 行日志、事件。
- CrashLoop 优先关联最近发布、镜像变更、配置变更、依赖连通性。
- OOMKilled 自动建议检查 request/limit、heap、内存泄漏和流量峰值。

| `DeploymentReplicasUnavailableP0` | P0 | available / desired < 50% | 5m | 服务容量严重不足 |
| `DeploymentRolloutStuckP1` | P1 | rollout 超过 15m 未完成 | 15m | 发布卡住 |
| `StatefulSetReplicasUnavailableP1` | P1 | readyReplicas < replicas | 10m | 有状态服务风险 |

PromQL 示例：


HPA 打满：


处置建议：

- 自动查询 Deployment、ReplicaSet、Pod、Events、HPA 状态。
- 对 P1 建议扩容或回滚；对 P0 核心服务触发负责人升级。
- 自动扩容必须通过风险校验，避免盲目放大故障。


### 6.11 服务层 SLO 告警

除了基础设施告警，还应接入面向用户体验的 SLO 告警。

| 策略 | 等级 | 触发条件 | 持续时间 | 说明 |
| --- | --- | --- | --- | --- |
| `ServiceErrorRateP1` | P1 | 5xx 错误率 > 2% | 10m | 服务错误率升高 |
| `ServiceErrorRateP0` | P0 | 5xx 错误率 > 10% 或核心接口不可用 | 5m | 用户明显受损 |
| `ServiceLatencyP1` | P1 | p99 延迟 > SLO 2 倍 | 10m | 性能退化 |
| `SloBurnRateFastP0` | P0 | 1h burn rate > 14.4 | 5m | 快速消耗错误预算 |
| `SloBurnRateSlowP1` | P1 | 6h burn rate > 6 | 30m | 慢性退化 |

这类告警应优先于资源告警，因为它直接体现用户影响。

## 7. 抑制、聚合与升级策略

### 7.1 抑制规则

建议默认抑制：

- `KubeNodeNotReadyP0` 触发后，抑制该节点上的 `PodNotReady`、`PodPending`、`PodCpuHigh`。
- `HostDiskUsageP0` 触发后，抑制同一 mountpoint 的 P1/P2 磁盘告警。
- `DeploymentReplicasUnavailableP0` 触发后，抑制同 workload 的单 Pod 不可用告警。
- `KubeApiServerDownP0` 触发后，抑制控制面 API latency 类告警。
- 维护窗口内抑制 P2/P3，P0/P1 降噪但仍进入审计和低频通知。

### 7.2 聚合规则

聚合维度：

```text
alertName + cluster + namespace + service + resourceType + resourceName
```

聚合窗口建议：

- P0：2 分钟内聚合，立即通知。
- P1：5 分钟内聚合，避免刷屏。
- P2/P3：15 到 60 分钟聚合，进入工单或日报。

### 7.3 升级规则

- P1 持续 30 分钟未恢复，升级到负责人和二线。
- P1 持续 60 分钟且影响面扩大，升级为 P0。
- 同一服务 30 分钟内 P1 告警数量 >= 3，升级为服务级 P0/P1 聚合告警。
- P0 10 分钟未确认，升级到 backup oncall。
- P0 30 分钟未恢复，升级到团队负责人。

### 7.4 恢复通知

所有 P0/P1 必须发送恢复通知，恢复通知要包含：

- 持续时间
- 峰值
- 影响资源
- 自动诊断结论
- 是否执行过变更或人工操作

## 10. 自动处置边界

自动化动作分级：

| 动作 | 风险 | 默认策略 |
| --- | --- | --- |
| 查询日志、查询指标、describe 资源 | 低 | 自动执行 |
| 创建工单、发送通知 | 低 | 自动执行 |
| 创建 Alertmanager silence | 中 | 仅维护窗口或人工确认后执行 |
| 重启 Pod/Deployment | 中高 | P1/P0 必须审批，P2 可按白名单 |
| 扩容 workload | 中高 | 需要容量校验和审批 |
| 删除 Pod、清理磁盘文件 | 高 | 默认不自动执行，只生成建议 |
| 修改配置、回滚发布 | 高 | 必须审批和审计 |

`ResultPushNode` 建议拆分：

- `NotificationNode`: 推送诊断结果。
- `TicketNode`: 创建/更新工单。
- `SilenceNode`: 只在维护窗口或人工批准后创建 silence。
- `IncidentNode`: P0/P1 创建事故记录。

## 11. 重构计划

### 阶段 0：基线梳理与策略冻结

目标：先把当前告警入口和默认策略固化。

任务：

- 收集当前实际告警样例，包括 Alertmanager payload、Prometheus alert labels、K8s events。
- 定义 `P0/P1/P2/P3/INFO` 枚举和中文说明。
- 固化第一版策略目录，即本文第 6 节。
- 明确每条策略 owner、runbookId、默认通知渠道。

验收：

- 有一份可评审的 `alarm-policies.yml` 草案。
- CPU > 70 为 P1、CPU > 85 为 P0 被明确配置。
- 磁盘、K8s 节点、Pod、Deployment、控制面策略都有默认规则。

### 阶段 1：事件模型升级与兼容

目标：不破坏现有 `/api/alarms`，同时支持标准化告警事件。

任务：

- 新增 `AlarmSeverity`、`AlarmStatus`、`AlarmResourceType`。
- 新增 `NormalizedAlarmEvent`。
- 扩展 `AlarmRequest`，增加 `alertName`、`resourceType`、`resourceName`、`cluster`、`namespace`、`service`、`metricName`、`currentValue`、`threshold`、`labels`、`annotations`。
- 新增 `AlarmNormalizer`，兼容旧请求。
- 新增 `AlarmFingerprintService`，当 request 没有 dedupKey 时自动生成 fingerprint。

验收：

- 旧格式请求仍可触发工作流。
- 新格式请求能生成稳定 fingerprint。
- 单元测试覆盖缺字段、旧字段、metadata 中字段提升到标准字段的行为。

### 阶段 2：策略配置加载

目标：策略从代码中解耦。

任务：

- 新增 `AlarmPolicy`、`AlarmCondition`、`AlarmAction` 模型。
- 新增 `YamlAlarmPolicyRepository`，加载 `config/alarm-policies.yml`。
- 在 `KubeOnCallProperties` 增加 `alarm.policy-location`、`alarm.enabled`、`alarm.default-severity`。
- 应用启动时校验策略 ID 唯一、阈值合法、severity 合法、runbookId 不为空。
- 提供策略 reload 接口或 actuator endpoint。

验收：

- 错误策略能在启动或 reload 时明确报错。
- 策略配置可被测试读取并转换为领域对象。

### 阶段 3：策略引擎与分级

目标：由 KubeOnCall 统一计算 severity 和 workflowTemplate。

任务：

- 新增 `AlarmPolicyEngine.evaluate(NormalizedAlarmEvent)`。
- 支持按 `alertName`、`metricName`、`resourceType`、labels 匹配策略。
- 支持简单表达式：`currentValue > threshold`、范围、等值、正则标签匹配。
- 支持影响因子调整 severity：env、criticality、affectedCount、service tier。
- 输出 `AlarmEvaluationResult`：matchedPolicy、finalSeverity、threshold、reason、workflowTemplate、actions。

验收：

- CPU 69 不触发，CPU 70.1 触发 P1，CPU 85.1 触发 P0。
- prod tier0 服务可按规则上调。
- lab 非核心资源可按规则下调，但 P0 根因类不下调。

### 阶段 4：抑制、聚合与升级

目标：降低噪声并保证真正严重告警升级。

任务：

- 新增 `AlarmSuppressionService`，实现第 7.1 节抑制规则。
- 新增 `AlarmCorrelationService`，聚合同一服务/节点/namespace 相关告警。
- Redis 保存 active alarm 状态，包含 firstSeen、lastSeen、count、status、severity。
- Dedup TTL 从固定配置升级为按 severity/category 配置。
- 新增升级策略：P0 未确认升级，P1 长时间未恢复升级。

验收：

- Node NotReady 后，同节点 PodNotReady 被抑制但仍可审计。
- 同一 CPU 告警 10 分钟内不会重复刷工作流。
- P1 持续未恢复可生成升级事件。

### 阶段 5：工作流模板化

目标：不同告警走不同诊断路径。

任务：

- `AlertWorkflowFactory.buildWorkflow()` 改为接收 `workflowTemplate`。
- 新增 `WorkflowTemplateRegistry`。
- 拆分现有节点或新增专用节点：
  - `MetricsSnapshotNode`
  - `KubernetesDescribeNode`
  - `RelatedAlertsNode`
  - `NotificationNode`
  - `TicketNode`
  - `SilenceNode`
- `StateCompareNode` 根据策略自动使用配置中的 PromQL，而不是固定 `up{instance=...}`。

验收：

- CPU 告警走 host-resource template。
- Pod CrashLoop 告警走 k8s-pod template。
- P0 控制面告警走 control-plane template。
- 原有测试仍能通过或完成等价迁移。

### 阶段 6：通知、工单与静默重构

目标：把结果推送从“创建 silence”改为专业事件流。

任务：

- `ResultPushNode` 拆为 `NotificationNode`、`TicketNode`、`SilenceNode`。
- Alertmanager 工具增加 `sendAlertEvent` 或 `updateAlertAnnotation` 的适配，避免默认 `createSilence`。
- P0/P1 自动创建 incident 或高优先级工单。
- P2/P3 进入普通工单或日报。
- Silence 只允许维护窗口或人工审批后执行。

验收：

- P0/P1 不会被默认自动静默。
- 每条 P0/P1 都有通知记录和审计记录。
- 静默操作可追踪审批人、原因、持续时间。

### 阶段 7：Runbook/RAG 绑定

目标：让告警处置建议更精准。

任务：

- 每条策略配置 `runbookId` 和 `ragFilters`。
- `KnowledgeRetrieveNode` 使用 `alertName`、`resourceType`、`service`、`severity`、`runbookId` 作为过滤条件。
- 建立告警 SOP 文档模板：
  - 现象
  - 影响
  - 快速确认
  - 常见根因
  - 安全处置步骤
  - 升级路径
  - 禁止动作
- 对 P0/P1 生成结构化处置摘要。

验收：

- CPU、磁盘、CrashLoop、OOMKilled、NodeNotReady 都能检索到对应 SOP。
- RAG 失败不影响告警通知，但 diagnostics 中记录失败原因。

### 阶段 8：评估与治理

目标：让告警策略可运营。

任务：

- 建立告警回放工具，用历史样例验证策略命中和 severity。

  - P0/P1 数量
  - dedup 命中率
  - suppression 命中率
  - auto diagnosis 成功率
  - no-runbook 策略数量
  - top noisy alerts
- 每周输出策略调优报告。

验收：

- 新策略上线前可 dry-run。
- 可以回答“这条策略过去 7 天会触发多少次、影响哪些服务、误报多少”。

## 12. 最小可落地版本

如果希望先快速落地，建议第一版只做以下范围：

1. 新增 `AlarmSeverity` 和 `NormalizedAlarmEvent`。
2. 新增 `alarm-policies.yml`，先覆盖 CPU、内存、磁盘、inode、NodeNotReady、PodCrashLoop、OOMKilled、DeploymentUnavailable。
3. 新增 `AlarmPolicyEngine`，支持阈值匹配和 severity 输出。
4. `AlertWorkflowService` 在执行工作流前调用策略引擎，并把 `finalSeverity`、`policyId`、`runbookId` 写入 context。
5. `StateCompareNode` 使用策略中的 `promql`。
6. `ResultPushNode` 不再默认创建 silence，改为输出诊断 summary；silence 作为后续审批动作。

这一版的收益最大：告警分级可控、策略可审计、诊断 PromQL 更准确，并且改动不会破坏现有工具体系。

## 13. 风险与注意事项

- CPU、磁盘阈值是通用初始值，生产环境应结合历史基线和服务关键性调优。
- P0 不能只由瞬时阈值触发，必须结合持续时间、影响面或根因类信号，否则会制造噪声。
- 自动静默风险很高，默认应关闭。
- 自动重启和扩容可能掩盖根因或扩大故障，必须接审批和变更审计。
- K8s 指标依赖 kube-state-metrics、node-exporter、cadvisor、apiserver metrics，缺失时策略应降级并提示。
- PromQL 中的 label 名称要与实际监控栈对齐，本文使用的是常见命名，落地前需要做映射。
- 告警恢复和 firing 一样重要，缺少恢复事件会影响事故时长统计。

## 14. 结论

KubeOnCall 当前告警链路适合做自动诊断，但缺少策略治理层。重构重点应放在“标准事件模型 + 策略配置 + 分级引擎 + 抑制聚合 + 模板化工作流”上。

默认策略建议从 CPU、内存、磁盘、inode、K8s 节点、Pod、Workload、控制面和服务 SLO 开始。其中 CPU 明确采用用户要求的阈值：高于 70% 为 P1，高于 85% 为 P0，并配合持续时间和恢复条件降低噪声。磁盘、K8s 相关告警则需要同时覆盖静态阈值、趋势预测、根因类状态和影响面。

按本文阶段推进后，KubeOnCall 的告警能力会从”接收告警并执行固定流程”升级为”策略可治理、分级可解释、诊断可自动化、处置可审计”的专业运维告警系统。

## 15. 变更事件关联设计

### 15.1 设计目标

告警发生后，快速关联最近的变更事件，帮助判断是否由变更引入问题，并提供回滚建议。

### 15.2 变更事件模型

```java
public record ChangeEvent(

    String changeType,         // deployment/config/secret/pvc/node_drain

    String resourceType,       // deployment/statefulset/configmap/secret

    String cluster,
```

### 15.3 告警事件扩展

```java
public record NormalizedAlarmEvent(
```

### 15.4 关联规则

```yaml
change_correlation:
  # 关联时间窗口
  time_window:
    before: 1h    # 告警前 1 小时的变更
    after: 30m    # 告警后 30 分钟的变更
    
  # 关联维度
  dimensions:
    - resource_name    # 同资源名
    - namespace        # 同命名空间
    - service          # 同服务
    - node             # 同节点
    
  # 关联评分权重
  scoring:
    time_proximity: 0.3      # 时间接近度
    resource_match: 0.4      # 资源匹配度
    change_type_risk: 0.2    # 变更类型风险
    historical_pattern: 0.1  # 历史模式
    
  # 变更类型风险权重
  change_type_weights:
    deployment_image_change: 0.9    # 镜像变更风险高
    deployment_env_change: 0.8      # 环境变量变更
    configmap_change: 0.6           # 配置变更
    secret_change: 0.7              # 密钥变更
    hpa_spec_change: 0.4            # HPA 变更
    node_drain: 0.8                 # 节点驱逐
```

### 15.5 关联服务实现

```java
@Service
public class ChangeCorrelationService {
    
    private final ChangeEventRepository changeEventRepository;
    
    public List<ChangeCorrelation> findRelatedChanges(NormalizedAlarmEvent alarm) {
        // 1. 查询时间窗口内的变更
        List<ChangeEvent> candidates = changeEventRepository.findByTimeWindow(
            alarm.getOccurredAt().minus(1, HOURS),
            alarm.getOccurredAt().plus(30, MINUTES),
            alarm.getCluster(),
            alarm.getNamespace()
        );
        
        // 2. 计算关联度评分
        return candidates.stream()
            .map(change -> calculateCorrelation(alarm, change))
            .filter(c -> c.correlationScore() > 0.3)  // 过滤低关联度
            .sorted(Comparator.comparingDouble(ChangeCorrelation::correlationScore).reversed())
            .limit(5)  // 最多返回 5 个
            .toList();
    }
    
    private ChangeCorrelation calculateCorrelation(NormalizedAlarmEvent alarm, ChangeEvent change) {
        double score = 0;
        List<String> reasons = new ArrayList<>();
        List<String> suggestions = new ArrayList<>();
        
        // 时间接近度评分
        long minutesDiff = Duration.between(change.changedAt(), alarm.getOccurredAt()).toMinutes();
        double timeScore = Math.max(0, 1 - minutesDiff / 60.0);
        score += timeScore * 0.3;
        if (minutesDiff < 10) {
            reasons.add(“变更发生在告警前 “ + minutesDiff + “ 分钟”);
        }
        
        // 资源匹配评分
        if (Objects.equals(change.resourceName(), alarm.getResourceName())) {
            score += 0.4;
            reasons.add(“变更资源与告警资源完全匹配”);
            
            // 生成回滚建议
            if (“deployment_image_change”.equals(change.changeType())) {
                suggestions.add(“考虑回滚镜像版本: “ + extractOldImage(change));
            }
        } else if (Objects.equals(change.namespace(), alarm.getNamespace())) {
            score += 0.2;
            reasons.add(“同一命名空间的变更”);
        }
        
        // 变更类型风险评分
        double typeWeight = getChangeTypeWeight(change.changeType());
        score += typeWeight * 0.2;
        
        return new ChangeCorrelation(change, score, String.join(“; “, reasons), suggestions);
    }
}
```

### 19.2 工作流节点调用 Agent 能力

```java
/**
 * 诊断节点 - 可调用 Agent 进行智能诊断
 */
@Component
public class IntelligentDiagnosisNode implements AlertWorkflowNode {
    
    private final PlannerAgent plannerAgent;
    private final ExecutorAgent executorAgent;
    private final ApprovalService approvalService;
    
    @Override
    public NodeResult execute(AlertWorkflowContext context) {
        NormalizedAlarmEvent alarm = context.getNormalizedAlarm();
        AlarmPolicy policy = context.getMatchedPolicy();
        
        // 1. 构建诊断查询
        String diagnosticQuery = buildDiagnosticQuery(alarm, policy);
        
        // 2. 调用 PlannerAgent 获取诊断计划
        GraphState planState = new GraphState();
        planState.setUserRequest(diagnosticQuery);
        plannerAgent.run(planState);
        
        // 3. 执行诊断任务
        List<Task> diagnosticTasks = planState.getTaskPlan().tasks();
        List<TaskResult> results = new ArrayList<>();
        
        for (Task task : diagnosticTasks) {
            if (isHighRiskTask(task)) {
                // 高风险任务：创建审批请求
                ApprovalRequest approval = approvalService.createPending(
                    context.getExecutionId(),
                    task,
                    “High risk diagnostic task requires approval”
                );
                return NodeResult.waiting(“Waiting for approval”);
            }
            
            // 低风险任务：直接执行
            GraphState execState = buildExecutionState(alarm, task);
            executorAgent.run(execState);
            results.add(extractResult(execState));
        }
        
        context.putAttribute(“diagnosticResults”, results);
        return NodeResult.success(“Diagnosis completed”);
    }
}
```

## 20. 策略 Dry-Run 机制

### 20.1 Dry-Run API

```java
@RestController
@RequestMapping(“/api/alarm-policies”)
public class AlarmPolicyDryRunController {
    
    /**
     * 单个告警 Dry-Run
     */
    @PostMapping(“/dry-run”)
    public DryRunResult dryRun(
        @RequestBody AlarmRequest request,
        @RequestParam(defaultValue = “false”) boolean includeWorkflow
    ) {
        // 1. 标准化告警
        NormalizedAlarmEvent normalized = alarmNormalizer.normalize(request);
        
        // 2. 匹配策略
        AlarmEvaluationResult evaluation = alarmPolicyEngine.evaluate(normalized);
        
        // 3. 计算严重级别
        AlarmSeverity finalSeverity = alarmSeverityCalculator.calculate(
            evaluation.getMatchedPolicy(),
            normalized
        );
        
        // 4. 检查抑制
        List<SuppressionMatch> suppressions = alarmSuppressionService.checkSuppressions(
            normalized,
            evaluation.getMatchedPolicy()
        );
        
        // 5. 模拟工作流（可选）
        SimulatedWorkflow workflow = null;
        if (includeWorkflow) {
            workflow = alertWorkflowService.simulate(normalized, evaluation);
        }
        
        return DryRunResult.builder()
            .inputAlarm(normalized)
            .matchedPolicy(evaluation.getMatchedPolicy())
            .finalSeverity(finalSeverity)
            .suppressedBy(suppressions)
            .workflowTemplate(evaluation.getWorkflowTemplate())
            .simulatedWorkflow(workflow)
            .build();
    }
}
```
