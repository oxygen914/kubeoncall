# KubeOnCall 重构启动路线（定制版）

> 结论先行：第一阶段先从 **告警事件标准化 + 策略引擎 MVP** 开始，不建议先做 Skill、记忆或完整 RAG 大改。

## 1. 为什么第一刀从告警开始

当前几份计划里，`告警策略重构.md` 和现有代码贴合度最高，且收益最直接：

- `AlarmRequest` / `AlarmEvent` 目前字段过薄，只包含 `alarmId`、`dedupKey`、`source`、`severity`、`nodeName`、`summary`、`metadata`。
- `AlertWorkflowService` 直接用上游 `dedupKey` 做 Redis 去重，缺少稳定 fingerprint。
- `AlertWorkflowFactory` 固定编排 5 个节点，不按告警类型选择路径。
- `StateCompareNode` 默认 PromQL 是 `up{instance="nodeName"}`，不能表达 CPU、磁盘、Pod、Node 等不同策略。
- `ResultPushNode` 当前默认调用 `alertmanager.createSilence`，这在 P0/P1 告警里风险偏高。

这些问题都是代码里已经存在的真实边界，第一阶段可以通过兼容式改造解决，不需要推倒 Agent、RAG、工具体系。

更重要的是，告警标准模型会成为后续三条线的公共基础：

- RAG 需要 `alertName/resourceType/service/severity/runbookId` 做精准过滤。
- 记忆系统需要 `fingerprint/service/resourceName/status` 做同设备历史关联。
- Skill 匹配需要稳定的 `TaskType/resourceType/tags`，否则只能靠自然语言关键词猜。

## 2. 各重构方向的启动优先级

| 方向 | 启动优先级 | 判断 |
| --- | --- | --- |
| 告警策略 | P0，先做 | 贴现有代码最近，能先补事件模型、fingerprint、策略分级、PromQL 选择和静默风险。 |
| RAG 基础修复 | P0，第二做 | RAG 文档写得成熟，但会碰 ES mapping、chunk、parent、embedding。先接住告警 runbook 过滤，再修底层效果。 |
| 记忆系统 | P1，第三做 | 短期会话记忆可独立启动，但告警记忆和长期记忆依赖标准事件和 RAG `source_type`。 |
| Skill 底座 | P1/P2，第四做 | 第一版可做指令注入，但最好等告警模型、工具白名单、prompt 预算稳定后再接入。 |
| `skill沉淀设计.md` / `告警上层接入.md` | 暂缓 | 当前文件为空，不能作为实施输入。 |

## 3. 第 0 步：先补可验证性

在正式改代码前，先做一个很小的基线整理：

1. 确认本地 Java/Maven 测试入口。当前仓库有 `pom.xml`，但没有 `mvnw`，本机命令也未找到 `mvn`。
2. 补一组告警样例 JSON：
   - 旧格式：只带 `nodeName/summary/severity/dedupKey`。
   - 新格式：带 `alertName/resourceType/resourceName/cluster/namespace/service/metricName/currentValue/threshold/labels/annotations`。
3. 先加单测，不急着接真实中间件：
   - `AlarmNormalizerTest`
   - `AlarmFingerprintServiceTest`
   - `AlarmPolicyEngineTest`
   - `AlertWorkflowServiceTest` 扩展无 `dedupKey` 场景
   - `StateCompareNodeTest` 覆盖从策略读取 PromQL
   - `ResultPushNodeTest` 覆盖默认不创建 silence

验收口径：旧请求行为不破坏，新请求能被标准化，策略计算和 fingerprint 稳定可测。

## 4. 第一阶段：告警事件标准化与兼容

目标：不破坏 `/api/alarms`，同时让平台内部拥有可治理的标准告警事件。

建议实现：

1. 新增领域枚举：
   - `AlarmSeverity`: `P0/P1/P2/P3/INFO`
   - `AlarmStatus`: `FIRING/RESOLVED/SUPPRESSED`
   - `AlarmResourceType`: `NODE/POD/DEPLOYMENT/NAMESPACE/CLUSTER/SERVICE/HOST`
2. 新增 `NormalizedAlarmEvent`，字段至少包含：
   - `alarmId`
   - `fingerprint`
   - `alertName`
   - `source`
   - `rawSeverity`
   - `severity`
   - `resourceType`
   - `resourceName`
   - `cluster`
   - `namespace`
   - `service`
   - `metricName`
   - `currentValue`
   - `threshold`
   - `labels`
   - `annotations`
   - `runbookId`
   - `status`
   - `occurredAt`
   - `metadata`
3. 扩展 `AlarmRequest`，保留旧字段，新增标准字段。
4. 新增 `AlarmNormalizer`：
   - 旧字段 `nodeName` 映射到 `resourceName`。
   - `severity` 先作为 `rawSeverity`，平台 severity 可由策略引擎覆盖。
   - 从 `metadata` 中提升常用字段，如 `namespace/service/cluster/alertName/runbookId`。
5. 新增 `AlarmFingerprintService`：
   - 优先使用请求中的 `dedupKey/fingerprint`。
   - 缺失时用 `alertName + cluster + namespace + resourceType + resourceName + service + key labels` 生成稳定 hash。
6. `AlertWorkflowService` 增加标准事件入口：
   - 保留 `process(AlarmEvent)` 兼容旧调用。
   - 新增或内部转换为 `process(NormalizedAlarmEvent)`。
   - Redis 去重从 `alarmEvent.dedupKey()` 改为标准 `fingerprint`。

第一阶段验收：

- 旧格式告警仍能走完整工作流。
- 新格式告警能生成稳定 fingerprint。
- 无 `dedupKey` 时不会出现 `alarm-dedup:null` 这类去重键。
- 测试覆盖旧字段、标准字段、metadata 提升字段、缺字段 fallback。

## 5. 第二阶段：策略配置与分级 MVP

目标：让 severity、runbook、PromQL、工作流模板从代码中解耦。

建议实现：

1. 新增 `alarm-policies.yml`，第一批只覆盖高价值策略：
   - `HostHighCpuUsageP1`
   - `HostHighCpuUsageP0`
   - `HostMemoryPressureP1/P0`
   - `HostDiskUsageP1/P0`
   - `HostInodeUsageP1/P0`
   - `KubeNodeNotReadyP0`
   - `PodCrashLoopBackOffP1`
   - `PodOOMKilledP1`
   - `DeploymentUnavailableP1`
2. 新增模型：
   - `AlarmPolicy`
   - `AlarmCondition`
   - `AlarmEvaluationResult`
3. 新增 `YamlAlarmPolicyRepository`：
   - 启动加载配置。
   - 校验 policy id 唯一、severity 合法、threshold 合法、runbookId 不为空。
4. 新增 `AlarmPolicyEngine`：
   - 支持 `alertName/metricName/resourceType/labels` 匹配。
   - 支持 `currentValue > threshold` 的最小表达式。
   - 输出 `finalSeverity/policyId/runbookId/promql/workflowTemplate/reason`。
5. `AlertWorkflowService` 在执行节点前调用策略引擎，把结果放入 `AlertWorkflowContext`。

第二阶段验收：

- CPU 69 不触发，CPU 70.1 触发 P1，CPU 85.1 触发 P0。
- 策略结果能写入 workflow context。
- `StateCompareNode` 使用策略中的 PromQL，而不是固定 `up{instance=...}`。

## 6. 第三阶段：安全化结果输出

目标：先消除默认静默风险。

建议实现：

1. `ResultPushNode` 第一版改成输出结构化诊断 summary，不默认调用 `createSilence`。
2. 如需推送到 Alertmanager，优先增加 `sendAlertEvent` 或 `updateAlertAnnotation` 这类非变更动作。
3. `createSilence` 保留为后续 `SilenceNode`，只在维护窗口或人工审批后执行。

第三阶段验收：

- P0/P1 默认不会自动静默。
- 告警执行结果仍会进入审计。
- 后续拆 `NotificationNode/TicketNode/SilenceNode` 时有清晰迁移点。

## 7. 第四阶段：RAG 与告警绑定

目标：让告警策略能精准召回 runbook，而不是只拿 `summary + nodeName/severity` 检索。

先做小步修复：

1. `KnowledgeRetrieveNode` 增加过滤条件：
   - `alertName`
   - `resourceType`
   - `service`
   - `severity`
   - `runbookId`
2. RAG 侧优先修：
   - parent 持久化或 MinIO 回源。
   - chunk metadata 标准化。
   - repository 不再按 `createdAt` 覆盖相关性排序。
   - `KnowledgeChunker` 从固定 280 字符改为配置化 recursive chunker。

这一步完成后，再进入 embedding、ES kNN、rerank 主路径和评估集。

## 8. 第五阶段：工作流模板化

目标：不同告警走不同诊断路径。

建议等前四阶段稳定后再做：

1. `AlertWorkflowFactory.buildWorkflow(workflowTemplate)`。
2. 新增 `WorkflowTemplateRegistry`。
3. 第一批模板：
   - `host-resource`
   - `k8s-pod`
   - `k8s-node`
   - `workload`
   - `control-plane`
4. 拆分或新增节点：
   - `MetricsSnapshotNode`
   - `KubernetesDescribeNode`
   - `RelatedAlertsNode`
   - `NotificationNode`
   - `TicketNode`
   - `SilenceNode`

## 9. 记忆与 Skill 的接入时机

记忆系统建议分两步：

1. 在告警标准化后，先做 `AskService` 的 `sessionId + SessionStore`，解决交互追问无状态问题。
2. 在 RAG metadata 契约稳定后，再做长期记忆 `source_type=memory`、告警记忆关联和自动提取。

Skill 底座建议等以下条件满足后再开始：

1. 告警事件和 TaskType 已稳定。
2. RAG/记忆已经有明确 `source_type` 和 token 预算边界。
3. `AgentToolCatalog` 的工具白名单过滤策略明确。

第一版 Skill 只做 `SkillRegistry + SkillMatcher + PlannerLlmService 注入`，不要先碰真 tool-calling。

## 10. 推荐第一批 PR 拆分

1. PR 1：`AlarmRequest` 扩展 + `NormalizedAlarmEvent` + `AlarmNormalizer` + `AlarmFingerprintService`。
2. PR 2：`AlertWorkflowService` 接入 normalized event/fingerprint 去重，保留旧入口兼容。
3. PR 3：`alarm-policies.yml` + policy 模型 + YAML loader + 配置校验。
4. PR 4：`AlarmPolicyEngine` + workflow context 写入 policy result。
5. PR 5：`StateCompareNode` 使用策略 PromQL。
6. PR 6：`ResultPushNode` 默认不 create silence，改为结构化 summary。
7. PR 7：`KnowledgeRetrieveNode` 使用 `runbookId/alertName/resourceType/service` 过滤。

做到 PR 7，告警链路就从“固定流程 + 上游字符串 severity + 默认静默”变成“标准事件 + 策略分级 + 精准诊断 + 安全输出”。这时再继续 RAG、记忆、Skill，会顺很多。
