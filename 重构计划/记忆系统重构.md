# KubeOnCall 记忆系统重构方案

> 范围：在 KubeOnCall 现有 RAG 知识检索能力之上，补齐「会话记忆 / 告警记忆 / 长期记忆」三个缺失的轴。
> 参考项目：
> - `/Users/didi/Desktop/code/paicli`（Java/Spring 同生态，会话记忆 + 长期记忆实现，`memory/` 包）
> - `/Users/didi/Desktop/code/as-cil`（逆向 Claude Code，六子系统协同记忆，已有分析文档 `看代码/记忆设计分析.md`）

## 1. 背景与问题定位

### 1.1 当前 kubeoncall 的"记忆"只有一个轴

KubeOnCall 目前只有 **RAG 知识检索**（`rag/` 包：`KnowledgeIngestService` / `HybridRetrievalService` / `RerankService` / `ElasticsearchKnowledgeRepository` + MinIO）。这套能力解决的是「全员共享的运维 SOP / runbook 检索」，是**知识库**，不是**记忆**。

对 `kubeoncall/src` 全量检索 memory / history / conversation / session / recall 关键词，结果是空——**项目里没有任何"会话记忆 / 对话历史 / 长期记忆"概念**。证据：

```java
// AskService.handle() —— 每次都新建状态，纯无状态
public AskExecutionResult handle(String question) {
    GraphState state = new GraphState();   // ← 每次重来
    state.setUserRequest(question);
    plannerAgent.run(state);
    ...
}
```

```java
// AskController —— 只接收一个 question，没有会话 id
public AskResponse ask(@Valid @RequestBody AskRequest request) {
    AskService.AskExecutionResult result = askService.handle(request.question());
    ...
}
```

`AlarmController.ingest()` 同理，每条告警独立处理，不关联同设备历史告警。

### 1.2 记忆 ≠ 知识库：必须先划清边界

这是整个重构的前提。KubeOnCall 已有 RAG，现在要加记忆，二者职责不同：

| 维度 | RAG 知识库（已有） | 记忆（待补） |
|------|-------------------|------------|
| 内容 | SOP / runbook / 手册 / 故障复盘文档 | 设备告警历史 / 服务已知事实 / 已处置事件 / 已知坑 |
| 共享性 | 全员共享 | 设备/服务/用户作用域，部分私有 |
| 时效 | 相对稳定，版本化管理 | 强时效，易陈旧 |
| 写入 | 人工入库 / JSONL 导入 | 系统自动从告警/Ask 中蒸馏 |
| 检索 | BM25 + 向量 + rerank | 复用同一套检索基础设施 |
| 在 ES 中的隔离 | `source_type = md/runbook/manual` | `source_type = memory` |

**核心原则**：记忆和知识库共用一套 ES + 检索基础设施，靠 `source_type` 隔离，但语义、写入、防陈旧逻辑各自独立。别把个人/设备记忆塞进共享知识库污染 SOP 检索，也别把共享 SOP 当成"记忆"。

### 1.3 三个轴的缺口

| 轴 | 当前状态 | 缺口 | 影响场景 |
|----|---------|------|---------|
| 短期会话记忆 | 无 | `AskService` 无状态，追问接不住 | 用户问完 payment-service 又追问"刚才那个呢" → 模型丢失上下文 |
| 告警记忆 | 无 | 同设备反复告警、历史处置无关联 | 同一 Pod 反复 OOM，每次都从零诊断，不知道上次怎么处理的 |
| 长期记忆 | 无 | 服务已知事实/坑无沉淀 | "payment-service 的 db 连接池上限是 50"这类事实每次重新发现 |

## 2. 参考项目分析与取舍

### 2.1 paicli：同生态范本，借鉴成本最低

`paicli/src/main/java/com/paicli/memory/`（11 个类，Java 17）提供了一套完整的会话 + 长期记忆实现。与 kubeoncall 同为 Java/Spring 生态，且哲学一致（克制 / 可审计 / 不过度抽象）。

**核心组件**：

| 组件 | 职责 | kubeoncall 可借鉴点 |
|------|------|-------------------|
| `ConversationMemory` | 短期记忆，context window 内的对话要点 | 直接对应 kubeoncall 的 `GraphState.observations` + 多轮 agent loop |
| `ConversationHistoryCompactor` | 对话历史压缩 | kubeoncall ReAct 循环 observation 累积撑爆 context 的应对 |
| `ContextCompressor` | 双层压缩分离：shortTermMemory 压缩 vs conversationHistory 压缩 | 关键设计点，见 2.1.1 |
| `TokenBudget` | token 预算 + 摘要输出预留 + 安全缓冲 | 压缩触发的预算计算 |
| `LongTermMemory` | JSON 持久化长期记忆，project/global 双作用域 | 作用域模型可映射为 service/global |
| `MemoryRetriever` | 关键词检索 + 时间衰减打分 | ⚠️ 检索部分**不借鉴**，kubeoncall 有更强的 ES |
| `MemoryEntry` | 记忆条目数据模型（id/content/type/timestamp/metadata/tokenCount） | 记忆条目 schema 参考 |

#### 2.1.1 最值得借鉴的设计：双层压缩分离 + 长期事实单独注入

paicli `ContextCompressor` 明确区分 **shortTermMemory 压缩** 与 **conversationHistory 压缩**，自动压缩阈值按 window 预留摘要输出 + 安全缓冲。这对应 kubeoncall 的痛点：planner / verifier / executor 三段 agent 反复 loop，`observations` 和 `nodeResults` 持续累积，目前没有任何压缩，长告警处理必然撑爆 context。

paicli `MemoryRetriever.retrieveLongTerm()` 有一个**精巧且关键**的设计（源码注释明确写了原因）：

```java
/**
 * 仅从长期记忆中检索稳定事实，用于 system prompt 注入。
 * 当前轮用户输入和短期对话已经在 message history 里，不应再次以"相关记忆"身份
 * 注入给模型，否则容易让模型把当前请求误读成历史事实。
 */
public List<MemoryEntry> retrieveLongTerm(String query, int limit) { ... }
```

**kubeoncall 接入记忆时必须遵守这条**：注入 system prompt 的只能是"长期稳定事实"，绝不能把当前告警本身又当成"历史知识"塞回去，否则模型会把当前请求误读成已经发生过的历史事件。

#### 2.1.2 值得借鉴：project/global 双作用域

paicli `LongTermMemory.isVisibleInProject(entry, projectKey)` / `scopeOf(entry)` 实现了 project / global 作用域隔离。kubeoncall 是多服务/多环境运维平台，天然需要按 `service` / `env` / `namespace` 分作用域——「payment-service 的 db 连接池上限」是 service-scoped，「公司 K8s 集群名是 prod-cluster-01」是 global。这套隔离模型可直接复用。

#### 2.1.3 不借鉴：paicli 的低配检索

paicli `MemoryRetriever.computeRelevanceScore` 是纯 `toLowerCase().contains()` 关键词匹配 + 24h 线性时间衰减。这对 CLI 够用，但 kubeoncall **已经有 ES + 向量 + rerank**，长期记忆检索应直接复用 `HybridRetrievalService`，用 `source_type=memory` 过滤——这反而是 kubeoncall 比两个参考项目都强的地方，不该倒退。

### 2.2 as-cil：思想最成熟，但实现过重需选择性吸收

as-cil（逆向 Claude Code）的记忆系统是六子系统协同：`memdir`（持久记忆）+ `SessionMemory`（会话记忆）+ `extractMemories`（后台抽取）+ `autoDream`（夜间整理）+ `teamMemorySync`（团队同步）+ `compact`（压缩）。详见 `as-cil/看代码/记忆设计分析.md`。

as-cil 是 TS + forked-subagent + prompt-cache 的 CLI 架构，**整体不能照搬**到 Spring 后端，但有四个思想高度契合运维场景：

#### 2.2.1 ⭐ 闭源四类分类法 + "排除可派生内容"

as-cil 把记忆严格限定为四类：`user` / `feedback` / `project` / `reference`，并在 `WHAT_NOT_TO_SAVE_SECTION` 明确排除可从代码/git 派生的内容（代码结构、文件路径、git history、修复配方）。

**对 kubeoncall 这条尤其重要**：运维系统最忌讳把"上次怎么修的"当记忆存——修法在代码/runbook/git 里，记忆里只存"上次修了什么、谁修的、什么时候、结果如何"。这能从源头控制记忆噪声，避免记忆库变成低质量 dump。

#### 2.2.2 ⭐ 防陈旧（drift）多层防线——运维场景的安全底线

as-cil 的 `MEMORY_DRIFT_CAVEAT` + "推荐前先验证文件/函数还存在" + 新鲜度标注（"47 days ago" 而非 ISO 时间戳，因为 LLM 不擅长时间推理）。

**运维场景陈旧性极强**：3 个月前的处置方案可能因服务重构而完全失效。kubeoncall 从记忆取出的"建议/操作"注入 prompt 时，**必须**带新鲜度标注 + "先验证当前集群状态"提示。否则在 oncall 场景推荐过时的 runbook 操作是**事故级风险**。这是整个重构里不可妥协的安全要求。

#### 2.2.3 ⭐ 后台自动提取（extractMemories）思想——运维场景比 CLI 更需要

as-cil 在每个 query loop 结束后用 forked subagent 自动提取记忆。paicli 是纯手动 `/save`，记忆积累慢。

**运维场景比 CLI 更需要自动提取**：oncall 工程师在处理告警时绝不会手动 `/save`。如果靠人工，记忆库基本不会有沉淀。但 as-cil 的 forked-agent + prompt-cache 实现kubeoncall 用不了。

**改造方案**：在 `AskService.handle()` / 告警工作流结束时，用 Spring `@Async` 异步触发一次 LLM 提取（复用已有 `PlannerLlmService` 的 ChatClient 机制），把"本次告警 + 处置 + 结果"蒸馏成记忆条目。思想照搬 as-cil，实现用 Spring 原生异步。

#### 2.2.4 索引 + 主题文件两段式 → 映射为"摘要常驻 + 按需检索"

as-cil 用 `MEMORY.md` 作轻量索引常驻 context，正文按主题分文件按需召回。kubeoncall 是后端服务不需要文件系统这套，但"轻量摘要常驻 system prompt + 完整记忆按需走 ES 检索"的思想可直接映射。

### 2.3 不借鉴的部分

| as-cil 子系统 | 不借鉴原因 |
|--------------|-----------|
| `teamMemorySync` | 运维的"团队"是 oncall 排班协作，不是代码协作，需求模型不同 |
| `autoDream` 三阶段 forked 整理 | 实现过重，kubeoncall 用 `@Scheduled` 定时任务做轻量合并去重即可，但"定期合并去重 + 相对日期转绝对"的思想可取 |
| memdir 文件系统存储 | 后端服务用 ES/DB 更合适，不引入文件系统复杂度 |

### 2.4 借鉴取舍汇总

| 能力 | 来源 | 借鉴方式 |
|------|------|---------|
| 短期记忆 + 双层压缩 | paicli `ConversationMemory`/`ContextCompressor` | 思想 + 接口形态，适配 `GraphState` |
| token 预算 | paicli `TokenBudget` | 思想，适配 Spring AI |
| 长期事实单独注入 | paicli `retrieveLongTerm` | **强制规则**，直接采纳 |
| 作用域隔离 | paicli `isVisibleInProject` | 改造为 service/env/global |
| 记忆分类 + 排除可派生 | as-cil 四类 + `WHAT_NOT_TO_SAVE` | 改造为运维四类（见 3.2） |
| 防陈旧 | as-cil drift 多层 | **强制安全要求**，直接采纳 |
| 自动提取 | as-cil `extractMemories` | Spring `@Async` 实现 |
| 记忆检索 | ❌ paicli 关键词 | 复用 kubeoncall 已有 `HybridRetrievalService` |
| 夜间整理 | as-cil `autoDream`（轻量版） | Spring `@Scheduled` |
| 团队同步 | ❌ as-cil `teamMemorySync` | 不适用 |

## 3. 目标架构

### 3.1 记忆三层模型

```
┌─────────────────────────────────────────────────────────────────┐
│ 短期会话记忆 (SessionMemory)                                      │
│ 生命周期：单次 Ask 会话 / 单次告警工作流                            │
│ 载体：GraphState（已有）+ 新增 SessionStore（跨 handle 调用）       │
│ 内容：本轮 observations / nodeResults / 当前告警上下文              │
│ 压缩：ContextCompressor（借鉴 paicli 双层压缩）                    │
│ 注入：完整注入当前轮 prompt                                        │
└─────────────────────────────────────────────────────────────────┘
                              │ 会话结束异步蒸馏
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ 长期记忆 (LongTermMemory) —— 持久化到 ES                          │
│ 生命周期：跨会话/跨告警                                            │
│ 载体：ES（source_type=memory）+ MemoryEntry 领域模型               │
│ 作用域：global / service-scoped / env-scoped                       │
│ 检索：复用 HybridRetrievalService（source_type=memory 过滤）        │
│ 注入：仅稳定事实注入 system prompt（paicli retrieveLongTerm 规则）   │
│ 防陈旧：新鲜度标注 + "先验证当前状态"提示（as-cil drift）            │
└─────────────────────────────────────────────────────────────────┘
                              ▲ 告警/Ask 结束异步提取
                              │
┌─────────────────────────────────────────────────────────────────┐
│ 告警记忆 (AlertMemory) —— 长期记忆的运维特化子集                    │
│ 按 device/service 聚合同设备历史告警 + 处置结果                     │
│ 用于：同设备反复告警时召回上次处置、已知坑、已知事实                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 运维记忆四类分类法（借鉴 as-cil，改造为运维语义）

严格限定为四类，**排除可派生内容**（不存 SOP 步骤本身——那在 RAG 知识库；不存具体修复命令——那在 runbook/git；只存非派生性历史事实）：

| 类型 | 含义 | 运维示例 | 何时保存 |
|------|------|---------|---------|
| `device_history` | 设备/服务的历史告警与处置 | "payment-service 在 2026-07-05 OOM，扩容到 4Gi 解决" | 每次告警处置完成后自动提取 |
| `service_fact` | 服务/集群的稳定事实 | "payment-service db 连接池上限 50"、"prod 集群 API Server 是 1.28" | 从 Ask/告警中发现非派生事实时 |
| `known_pitfall` | 已知的坑/注意事项 | "payment-service 重启后需等 30s 健康检查，否则误报" | 处置中发现非显然陷阱时 |
| `user_preference` | 值班人/用户的运维偏好 | "张三偏好先看日志再看指标"、"该服务禁止 restart，只准 scale" | 学到用户工作方式时 |

**排除清单（`WHAT_NOT_TO_SAVE`，运维版）**：
- ❌ SOP 具体步骤（在 RAG 知识库，记忆只存"该 SOP 适用于此场景"的指针）
- ❌ 具体修复命令/kubectl 操作（在 runbook/git）
- ❌ 集群当前实时状态（每次实时查 K8s API，不缓存为记忆）
- ❌ 可从 Prometheus/Grafana 查到的指标历史
- ❌ 临时任务进度（用 `GraphState` 的 task，不用记忆）
- ✅ 只存：谁/何时/为什么/处置结果/非显然事实/已知坑

### 3.4 领域模型

```java
// 记忆条目 —— 与 KnowledgeDocument 平级但独立
public record MemoryEntry(
        String id,
        MemoryType type,           // device_history / service_fact / known_pitfall / user_preference
        String content,            // 非派生性事实正文
        MemoryScope scope,         // global / service / env
        String scopeKey,           // scope=service 时为 service 名；global 时为 null
        Map<String, String> metadata,  // env / namespace / severity / sourceAlarmId 等
        Instant createdAt,
        Instant updatedAt,
        int tokenCount,
        boolean enabled            // 软删除
) {}

public enum MemoryType {
    DEVICE_HISTORY, SERVICE_FACT, KNOWN_PITFALL, USER_PREFERENCE
}

public record MemoryScope(String level, String key) {
    public static MemoryScope global() { return new MemoryScope("global", null); }
    public static MemoryScope service(String name) { return new MemoryScope("service", name); }
    public static MemoryScope env(String env) { return new MemoryScope("env", env); }
}
```

### 3.5 与现有 ES 知识库的隔离

长期记忆作为 `source_type=memory` 的文档写入同一 ES 索引（复用已有 mapping 与检索能力），靠 `source_type` + metadata 过滤隔离：

```java
// 检索知识（SOP）—— 不含记忆
RetrievalRequest knowledgeReq = new RetrievalRequest(
    question, Map.of("source_type", "md", ...), topK, ...);

// 检索记忆 —— 不含 SOP
RetrievalRequest memoryReq = new RetrievalRequest(
    question, Map.of("source_type", "memory", "scope.service", serviceName, ...), topK, ...);
```

这样：
- 记忆复用 ES + 向量 + BM25 + RRF + rerank 全套能力（不倒退到 paicli 关键词检索）
- 知识与记忆互不污染
- 后续若记忆量大，可拆独立索引 `kubeoncall-memory-v1`，初期同索引 + 过滤即可

## 4. 关键设计细节

### 4.1 短期会话记忆：让 AskService 有状态

**当前问题**：`AskService.handle()` 每次 `new GraphState()`，无法支持追问。

**方案**：引入 `sessionId`，跨 `handle()` 调用复用 `SessionMemory`。

```java
// AskRequest 增加 sessionId（可选，无则新建）
public record AskRequest(String question, String sessionId) {}

// AskService.handle 改造
public AskExecutionResult handle(String question, String sessionId) {
    SessionMemory session = sessionStore.getOrCreate(sessionId);
    GraphState state = session.attachToNewGraphState(question);  // 继承历史上下文
    ...
    // 会话内压缩（借鉴 paicli 双层压缩）
    if (tokenBudget.exceeds(state)) {
        contextCompressor.compact(state, session);
    }
    ...
    // 会话结束异步提取长期记忆
    memoryExtractor.extractAsync(session, state);
    return result;
}
```

`SessionMemory` 持有跨轮的对话历史摘要，`GraphState` 仍是单次执行的细粒度状态载体。二者关系：`SessionMemory` 是会话级"长期"，`GraphState` 是单次执行级"短期"。

**压缩触发点**：planner / verifier / executor 的 ReAct loop 内，`observations` 超过 token 预算时，`ContextCompressor` 把早期 observation 压缩成摘要，保留近期原始内容 + 摘要（paicli 双层压缩思想）。

### 4.2 长期记忆注入：仅稳定事实 + 防陈旧

`MemoryInjector` 在 `PlannerLlmService.buildSystemPrompt()` 注入点工作：

```java
// 改造后的 buildSystemPrompt
private String buildSystemPrompt(String serviceName) {
    String memoryBlock = memoryInjector.buildStableFactBlock(serviceName);
    return """
            You are KubeOnCall's planner agent. Produce one compact JSON object only.
            ...
            %s
            """.formatted(memoryBlock);
}
```

`MemoryInjector.buildStableFactBlock` 实现（**严格遵循 paicli retrieveLongTerm 规则 + as-cil drift 防线**）：

```java
public String buildStableFactBlock(String serviceName) {
    // 1. 只取长期稳定事实（service_fact / known_pitfall），不取 device_history 的当前事件
    //    —— 防止把当前告警当成历史事件注入（paicli 规则）
    List<MemoryEntry> facts = longTermMemoryService.retrieveStableFacts(
        serviceName, Set.of(MemoryType.SERVICE_FACT, MemoryType.KNOWN_PITFALL), 5);

    if (facts.isEmpty()) return "";

    StringBuilder sb = new StringBuilder("\n## 相关服务记忆（可能陈旧，行动前务必验证当前集群状态）\n\n");
    for (MemoryEntry fact : facts) {
        // 2. 新鲜度标注：用"X days ago"而非 ISO 时间戳（as-cil drift，LLM 不擅长时间推理）
        String age = formatAge(fact.updatedAt());   // "12 days ago"
        sb.append("- [").append(fact.type()).append(", ").append(age).append("] ")
          .append(fact.content()).append("\n");
    }
    sb.append("\n注意：以上记忆为历史观察，非实时状态。涉及具体资源时，先通过 K8s/Prometheus 验证当前状态再行动。\n");
    return sb.toString();
}
```

**两个强制规则**：
1. **只注入稳定事实**：`SERVICE_FACT` / `KNOWN_PITFALL`，不注入 `DEVICE_HISTORY` 的具体事件（具体事件由告警记忆在告警场景单独召回）。
2. **必须带防陈旧提示**：新鲜度标注 + "先验证当前状态"——这是运维场景安全底线。

### 4.3 告警记忆：同设备历史关联

`AlertMemoryService` 在 `AlertWorkflowService.process()` 入口召回同设备历史：

```java
// AlertWorkflowService.process 改造
public List<NodeResult> process(AlarmEvent event) {
    // 召回同设备/同服务的历史告警记忆 + 上次处置结果
    List<MemoryEntry> history = alertMemoryService.recallDeviceHistory(
        event.nodeName(), event.metadata().get("service"));

    GraphState state = new GraphState();
    state.setUserRequest(buildAlarmContext(event, history));  // 历史注入上下文
    state.getContext().put("deviceMemoryHistory", history);
    ...
    // 告警处置完成后异步提取
    memoryExtractor.extractFromAlarmAsync(event, state);
}
```

`AlertMemoryService.recallDeviceHistory` 委托 `HybridRetrievalService`，过滤 `source_type=memory` + `type=device_history` + `scope.service=xxx`，按 `updatedAt` 排序取最近 N 条。

**价值**：同一 Pod 反复 OOM 时，模型能看到"2 小时前同类告警，扩容到 4Gi 解决"，避免从零诊断。

### 4.4 自动提取：Spring 异步实现 as-cil extractMemories

`MemoryExtractor`（`@Async`）在告警/Ask 结束后触发：

```java
@Async
public void extractFromAlarmAsync(AlarmEvent event, GraphState state) {
    if (!properties.getMemory().isExtractEnabled()) return;

    // 1. 主 Agent 这一轮若已产生明显事实，跳过（as-cil 主/后台去重协作）
    // 2. 用 LLM 从 state.observations + 处置结果蒸馏出记忆条目
    List<MemoryEntry> extracted = extractionPromptBuilder.extract(event, state);
    // 3. 排除可派生内容（运维版 WHAT_NOT_TO_SAVE）
    List<MemoryEntry> filtered = filterDerivable(extracted);
    // 4. 写入 ES（source_type=memory）
    filtered.forEach(longTermMemoryService::store);
}
```

**去重协作**（借鉴 as-cil）：如果 executor 已经在 observations 里明确记录了事实，提取器不重复提取；只在主流程没沉淀时补漏。

**门控**：`kubeoncall.memory.extract.enabled` 配置开关 + 失败不阻断主流程（提取失败只记 warning）。

### 4.5 夜间整理：轻量版 autoDream

`MemoryConsolidationJob`（`@Scheduled`，借鉴 as-cil autoDream 思想但大幅简化）：

```java
@Scheduled(cron = "${kubeoncall.memory.consolidation.cron:0 0 3 * * *}")
public void consolidate() {
    // 1. 时间门 + 锁门：距上次整理 ≥ 24h，分布式锁防并发
    // 2. 合并近似重复记忆（同 service + 同 type + 内容相似度 > 阈值）
    // 3. 相对日期转绝对（"昨天 OOM" → "2026-07-06 OOM"）
    // 4. 软删除长期未命中且已陈旧的 device_history（> 90 天未更新）
}
```

不实现 as-cil 的三阶段 forked agent（Orient/Gather/Consolidate），用纯 Java 逻辑 + 一次 LLM 调用做合并判断即可。

## 6. 分阶段实施计划

### 阶段 0：会话状态化（短期记忆基础）—— P0

**目标**：让 `AskService` 支持追问，解决无状态硬伤。

**任务**：
1. 新增 `SessionMemory` / `SessionStore`，按 `sessionId` 存储跨 `handle()` 的会话状态。
2. `AskRequest` / `AskResponse` 增加 `sessionId`（可选，向后兼容）。
3. `AskService.handle(question, sessionId)` 复用历史 `GraphState` 摘要。
4. 新增 `TokenBudget`，监测 `observations` token 量。

**验收**：
- 同一 `sessionId` 连续两次 `/api/ask`，第二次能引用第一次的上下文。
- 无 `sessionId` 时行为与现状一致（向后兼容）。

### 阶段 1：会话内压缩 —— P0

**目标**：长告警/长会话不撑爆 context。

**任务**：
1. 新增 `ConversationHistoryCompactor` / `ContextCompressor`（借鉴 paicli 双层压缩）。
2. 在 planner/verifier/executor 的 loop 内接入压缩触发点。
3. 压缩保留近期原始 observation + 早期摘要 + 安全缓冲。

**验收**：
- 模拟 50 轮 observation 的长会话，token 不超预算，关键上下文不丢失。
- 压缩前后 planner 决策一致性测试通过。

### 阶段 2：长期记忆存储 + 检索 —— P1

**目标**：长期记忆可写可查，复用 ES。

**任务**：
1. 新增 `MemoryEntry` / `MemoryType` / `MemoryScope` 领域模型。
2. `LongTermMemoryService`：写入 ES（`source_type=memory`）+ 委托 `HybridRetrievalService` 检索。
3. 检索时按 `source_type` / `scope` / `type` 过滤，与知识库隔离。
4. 记忆管理 API（查询/软删除）。

**验收**：
- 写入的记忆可在知识库检索中按 `source_type=memory` 过滤召回。
- 知识检索（`source_type=md`）不受记忆污染。

### 阶段 3：长期记忆注入 + 防陈旧 —— P1

**目标**：planner/executor 能看到相关服务记忆，且不会推荐过时操作。

**任务**：
1. `MemoryInjector.buildStableFactBlock`：仅注入 `SERVICE_FACT`/`KNOWN_PITFALL`（paicli retrieveLongTerm 规则）。
2. 接入 `PlannerLlmService.buildSystemPrompt()` / executor prompt。
3. 新鲜度标注（"X days ago"）+ "先验证当前状态"提示（as-cil drift）。

**验收**：
- 注入的记忆块带新鲜度标注与验证提示。
- `DEVICE_HISTORY` 不进入 system prompt（只在告警场景单独召回）。

### 阶段 4：自动提取 —— P1

**目标**：告警/Ask 结束自动沉淀记忆，不依赖人工。

**任务**：
1. `MemoryExtractor`（`@Async`）+ `MemoryExtractionPromptBuilder`。
2. 在 `AskService.handle()` / `AlertWorkflowService.process()` 结束时触发。
3. 排除可派生内容（运维版 `WHAT_NOT_TO_SAVE`）。
4. 主/后台去重协作，失败不阻断主流程。

**验收**：
- 一次告警处置完成后，ES 出现 `source_type=memory` 条目。
- 提取失败时主流程不受影响。
- 可派生内容（具体 kubectl 命令等）不被存入记忆。

### 阶段 5：告警记忆关联 —— P2

**目标**：同设备反复告警时关联历史处置。

**任务**：
1. `AlertMemoryService.recallDeviceHistory`：按 device/service 召回 `DEVICE_HISTORY` 记忆。
2. `AlertWorkflowService.process()` 入口注入历史上下文。
3. 告警处置结果回写为 `DEVICE_HISTORY` 记忆。

**验收**：
- 同设备二次告警时，planner 能看到上次处置结果。
- 误报场景能识别"已知坑"避免重复处置。

### 阶段 6：夜间整理 + 评估 —— P2

**目标**：记忆库可维护、可度量。

**任务**：
1. `MemoryConsolidationJob`（`@Scheduled`）：合并近似重复 + 相对日期转绝对 + 陈旧软删除。
2. 记忆命中率 metrics（`memory.inject.count` / `memory.recall.hit_rate` / `memory.extract.count`）。
3. 可选：小型评估集，验证记忆注入是否提升告警处置准确率。

**验收**：
- 定时任务运行后，近似重复记忆被合并。
- 陈旧 `DEVICE_HISTORY`（>90 天）被软删除。
- metrics 可观察记忆系统健康度。

## 7. 风险与注意事项

1. **记忆污染知识检索**：必须严格靠 `source_type` 隔离，初期同索引时检索 API 默认带 `source_type` 过滤，避免记忆条目污染 SOP 检索结果。记忆量大时拆独立索引。

2. **陈旧记忆导致事故**：运维场景记忆陈旧性是事故级风险。`DEVICE_HISTORY` 的具体操作建议**绝不**直接注入 system prompt 让模型照做，只能作为"参考上下文"，且必须带"先验证当前状态"提示。高风险动作仍走审批（复用已有 `ApprovalService`）。

3. **自动提取噪声**：`@Async` 提取若不加 `WHAT_NOT_TO_SAVE` 过滤，会把大量可派生内容（kubectl 命令、临时状态）灌进记忆库。提取 prompt 必须强制排除清单 + 抽取后二次过滤。

4. **记忆 vs 实时状态混淆**：集群当前状态（Pod 数、指标值）绝不能缓存为记忆——每次实时查 K8s API / Prometheus。记忆只存"历史观察 + 非派生事实"，不存"当前状态快照"。

5. **token 预算**：记忆注入要计入 `TokenBudget`，避免记忆块 + RAG 知识块 + 对话历史三者叠加超窗。`inject-top-k` 默认 5 条，可配置。

6. **会话状态存储**：`SessionStore` 初期可用内存（参考现有 `InMemoryApprovalRepository` 模式），生产环境需 Redis（参考已有 `RedisApprovalRepository`）。会话 TTL 清理避免内存泄漏。

7. **提取的 LLM 成本**：每次告警/Ask 结束都触发提取会增加 LLM 调用。门控 `extract.enabled` + 仅在处置产生新信息时提取（去重协作）+ 异步不阻塞主流程。

8. **与 RAG 重构的协同**：本方案与 `RAG重构方案.md` 共用 ES 基础设施。`source_type` 字段需在 RAG 重构的 metadata 契约中预留 `memory` 取值；记忆检索复用 RAG 重构后的 `KnowledgeRetrievalFacade` / `RetrievalHit`（带 score/rank）。两个重构应协同推进，避免重复造检索轮子。

## 8. 优先级与最小可落地版本

### 第一优先级（立即做，解决无状态硬伤）

1. **阶段 0**：`AskService` 会话状态化（`SessionMemory` / `SessionStore` + `sessionId`）。
2. **阶段 1**：会话内压缩（`ContextCompressor`，防长会话撑爆）。

这两个阶段不依赖 ES 记忆存储，纯内存，风险最低，先解决"追问接不住"这个最痛的点。

### 第二优先级（决定记忆能否沉淀）

3. **阶段 2**：长期记忆存储 + 检索（复用 ES）。
4. **阶段 3**：长期记忆注入 + 防陈旧（安全底线）。
5. **阶段 4**：自动提取（让记忆自动积累，不靠人工）。

### 第三优先级（运维场景深化）

6. **阶段 5**：告警记忆关联（同设备历史）。
7. **阶段 6**：夜间整理 + 评估。

### 最小可落地版本（MVP）

如果先做小步快跑，建议范围：

1. `SessionMemory` / `SessionStore` + `sessionId`，让 `AskService` 支持追问。
2. `TokenBudget` + 最简 `ContextCompressor`（observation 超阈值时摘要早期内容）。
3. `MemoryEntry` 模型 + `LongTermMemoryService` 写入 ES（`source_type=memory`）。
4. `MemoryInjector` 在 planner system prompt 注入稳定事实（带防陈旧提示）。
5. `MemoryExtractor` 异步提取（只提取 `SERVICE_FACT`/`KNOWN_PITFALL`，排除可派生）。

这个版本能让 kubeoncall 从"无状态 + 纯知识检索"进化到"有会话 + 有长期记忆 + 自动沉淀"，且全部复用已有 ES/Agent 基础设施，改动路径短。

## 9. 结论

KubeOnCall 当前的"记忆系统"实际上只是**知识检索系统**，缺失**会话记忆**和**持久记忆**两个轴，导致无状态追问接不住、同设备反复告警无法关联、服务已知事实无法沉淀。

重构策略是**扬长避短**：
- **不照搬** paicli 的低配关键词检索——kubeoncall 已有更强的 ES + 向量 + rerank，长期记忆检索直接复用 `HybridRetrievalService`。
- **不整体照搬** as-cil 的 forked-agent + 文件系统架构——后端服务不适配。
- **借** paicli 的短期记忆 + 双层压缩 + 作用域模型 + "长期事实单独注入"规则。
- **借** as-cil 的四类分类法 + 排除可派生 + 防陈旧多层防线 + 自动提取思想（用 Spring `@Async` 实现）。

最终在 kubeoncall **已有的 ES/RAG/Agent 基础设施上**补齐三层记忆（短期会话 / 长期持久 / 告警特化），靠 `source_type` 与知识库隔离，以"仅注入稳定事实 + 强制防陈旧"为安全底线。这是综合三个项目后，kubeoncall 独有的最优解。

建议先做阶段 0 + 1（会话状态化 + 压缩），用最低风险解决最痛的无状态问题；再推进长期记忆存储/注入/提取，让记忆自动沉淀；最后深化告警关联与夜间整理。每个阶段都可独立验收，不破坏现有 RAG 与 Agent 链路。
