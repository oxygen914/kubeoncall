# KubeOnCall 全项目重构实施计划

## 1. 总览

本计划用于统筹 KubeOnCall 后端重构，目标是达到**后端可验收闭环**，采用**分阶段验收**方式推进。

固定实施顺序：

1. 工具链基线
2. 告警治理
3. 工作流模板化
4. RAG 基础重构
5. 记忆系统
6. Skill 底座
7. 全链路收敛

约束：

- 不引入 PostgreSQL/MySQL 等新存储。
- Redis 存短期状态、会话状态、active alarm 状态。
- Elasticsearch 存知识库与长期记忆。
- MinIO 存原始知识文档。
- RAG 向量能力首轮做接口与可测实现，真实 embedding/kNN 通过配置启用。
- 现有公开 API 必须保持向后兼容。
- 现有工作区中的无关删除和未跟踪文件不得回滚或清理。

## 2. 公开接口与类型调整

### 2.1 `/api/alarms`

保持旧格式兼容，`AlarmRequest` 增加标准字段：

- `fingerprint`
- `alertName`
- `resourceType`
- `resourceName`
- `cluster`
- `namespace`
- `service`
- `metricName`
- `currentValue`
- `threshold`
- `unit`
- `duration`
- `labels`
- `annotations`
- `runbookId`
- `status`

响应保持 `List<NodeResult>`。

新增领域类型：

- `AlarmSeverity`: `P0/P1/P2/P3/INFO`
- `AlarmStatus`: `FIRING/RESOLVED/SUPPRESSED`
- `AlarmResourceType`
- `NormalizedAlarmEvent`
- `AlarmEvaluationResult`

### 2.2 `/api/ask`

`AskRequest` 增加可选 `sessionId`。

`AskResponse` 返回 `sessionId`。

无 `sessionId` 时保持现有单轮行为。

### 2.3 `/api/knowledge/query`

`KnowledgeQueryRequest` 增加：

- `topK`
- `retrieveMethod`: `KEYWORD/VECTOR/HYBRID`
- `includeTrace`

默认保持兼容旧请求。

### 2.4 工具目录

新增安全读类能力：

- `kubernetes.describeResource`
- `alertmanager.sendAlertEvent`

`alertmanager.createSilence` 保留，但只能作为审批后的显式动作，不再作为告警结果默认动作。

## 4. 阶段二：告警治理主线

目标：把告警链路从“上游字符串 + 固定流程”升级为“标准事件 + 策略分级 + 可审计诊断”。

任务：

1. 实现 `AlarmNormalizer`。
   - 旧字段映射到 `NormalizedAlarmEvent`。
   - 从 `metadata` 提升 `namespace/service/cluster/alertName/runbookId` 等常用字段。
2. 实现 `AlarmFingerprintService`。
   - 优先使用 `fingerprint`。
   - 其次使用 `dedupKey`。
   - 缺失时使用 `alertName + cluster + namespace + resourceType + resourceName + service + metricName + sorted stable labels` 生成 SHA-256。
3. `AlertWorkflowService` 内部改用 normalized event 和 fingerprint 去重。
4. 保留 `process(AlarmEvent)` 兼容入口。
5. 实现 `YamlAlarmPolicyRepository` 与 `AlarmPolicyEngine`。
6. 首批策略覆盖：
   - CPU
   - 内存
   - 磁盘
   - inode
   - NodeNotReady
   - PodCrashLoop
   - OOMKilled
   - DeploymentUnavailable
7. `StateCompareNode` 使用策略中的 PromQL/window。
8. `ResultPushNode` 默认只输出结构化诊断 summary，不自动 `createSilence`。

验收：

- 旧格式请求仍能执行。
- 新格式请求生成稳定 fingerprint。
- 无 `dedupKey` 时不会产生 `alarm-dedup:null`。
- CPU 69 不触发策略，70.1 触发 P1，85.1 触发 P0。
- P0/P1 默认不创建 silence。

## 5. 阶段三：工作流模板、抑制与恢复

目标：不同告警走不同诊断路径，并具备噪声治理能力。

任务：

1. 新增 `WorkflowTemplateRegistry`。
2. `AlertWorkflowFactory.buildWorkflow(workflowTemplate)` 支持：
   - `host-resource`
   - `k8s-pod`
   - `k8s-node`
   - `workload`
   - `control-plane`
3. Redis 存 active alarm：
   - `firstSeen`
   - `lastSeen`
   - `count`
   - `status`
   - `severity`
   - `fingerprint`
4. 去重 TTL 按 severity/category 配置。
5. NodeNotReady 抑制同节点 Pod 噪声。
6. P0/P1 未确认升级。
7. 支持恢复事件确认。
8. 拆分安全节点：
   - `NotificationNode`
   - `TicketNode`
   - `SilenceNode`

验收：

- 不同 `workflowTemplate` 生成不同节点序列。
- 依赖失败时降级和审计正确。
- Silence 只走审批路径。

## 6. 阶段四：RAG 重构

目标：修复当前 RAG 的数据工程问题，让后续记忆和告警 Runbook 绑定有稳定基础。

任务：

1. `KnowledgeIngestService` 保留兼容 facade。
2. 内部拆分：
   - `KnowledgeIngestionFacade`
   - `KnowledgeRetrievalFacade`
3. 标准化 metadata：
   - `doc_id`
   - `chunk_id`
   - `chunk_index`
   - `total_chunks`
   - `parent_document_id`
   - `document_type`
   - `source_type`
   - `dataset_version`
   - `chunk_enable`
   - `file_hash`
4. 替换固定 280 字符 chunker 为配置化 Markdown/recursive chunker。
5. 保存 parent 文档。
6. 检索不再按 `createdAt` 覆盖相关性。
7. 抽象：
   - `EmbeddingClient`
   - `EmbeddingService`
   - `VectorRetriever`
8. 测试使用确定性 mock embedding。
9. ES kNN 通过配置启用。
10. Rerank 接收 retrieval hit 和 score trace，失败时回退 RRF。

验收：

- parent 可回源。
- chunk metadata 完整。
- 排序不被 createdAt 覆盖。
- vector disabled/mock/failed 三种路径可测。

## 7. 阶段五：记忆系统

目标：补齐会话记忆、长期记忆和告警记忆。

任务：

1. `SessionStore` 使用 Redis。
2. `AskService` 支持多轮 session。
3. 无 `sessionId` 时仍单轮。
4. 新增：
   - `MemoryEntry`
   - `MemoryType`
   - `MemoryScope`
5. 长期记忆写入 ES，`source_type=memory`。
6. 知识检索默认不被 memory 污染。
7. `MemoryInjector` 只注入：
   - `SERVICE_FACT`
   - `KNOWN_PITFALL`
8. 注入内容必须带新鲜度和“先验证当前状态”提示。
9. `MemoryExtractor` 异步从 Ask/Alarm 结果中提取记忆。
10. 提取时排除：
    - kubectl 命令
    - 实时状态
    - SOP 全文
    - 可从监控/日志重新获得的内容
11. `AlertMemoryService` 按 fingerprint/service/resource 召回历史处置。

验收：

- 同一 session 可追问。
- 长期记忆按 `source_type=memory` 隔离。
- 陈旧提示存在。
- 自动提取失败不影响主流程。
