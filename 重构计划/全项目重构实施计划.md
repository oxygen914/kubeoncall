# KubeOnCall 全项目重构实施计划

## 1. 总览

本计划用于统筹 KubeOnCall 后端重构，目标是达到**后端可验收闭环**，采用**分阶段验收**方式推进。

固定实施顺序：

1. 工具链基线
2. 告警治理
3. 工作流模板化
4. RAG 基础重构
5. 记忆系统
6. Skill 底座
7. 全链路收敛

约束：

- 不引入 PostgreSQL/MySQL 等新存储。
- Redis 存短期状态、会话状态、active alarm 状态。
- Elasticsearch 存知识库与长期记忆。
- MinIO 存原始知识文档。
- RAG 向量能力首轮做接口与可测实现，真实 embedding/kNN 通过配置启用。
- 现有公开 API 必须保持向后兼容。
- 现有工作区中的无关删除和未跟踪文件不得回滚或清理。

## 4. 阶段二：告警治理主线

目标：把告警链路从“上游字符串 + 固定流程”升级为“标准事件 + 策略分级 + 可审计诊断”。

任务：

1. 实现 `AlarmNormalizer`。
   - 旧字段映射到 `NormalizedAlarmEvent`。
   - 从 `metadata` 提升 `namespace/service/cluster/alertName/runbookId` 等常用字段。
2. 实现 `AlarmFingerprintService`。
   - 优先使用 `fingerprint`。
   - 其次使用 `dedupKey`。
   - 缺失时使用 `alertName + cluster + namespace + resourceType + resourceName + service + metricName + sorted stable labels` 生成 SHA-256。
3. `AlertWorkflowService` 内部改用 normalized event 和 fingerprint 去重。
4. 保留 `process(AlarmEvent)` 兼容入口。
5. 实现 `YamlAlarmPolicyRepository` 与 `AlarmPolicyEngine`。
6. 首批策略覆盖：
   - CPU
   - 内存
   - 磁盘
   - inode
   - NodeNotReady
   - PodCrashLoop
   - OOMKilled
   - DeploymentUnavailable
7. `StateCompareNode` 使用策略中的 PromQL/window。
8. `ResultPushNode` 默认只输出结构化诊断 summary，不自动 `createSilence`。

验收：

- 旧格式请求仍能执行。
- 新格式请求生成稳定 fingerprint。
- 无 `dedupKey` 时不会产生 `alarm-dedup:null`。
- CPU 69 不触发策略，70.1 触发 P1，85.1 触发 P0。
- P0/P1 默认不创建 silence。

- 50 轮 session 压缩后保留早期关键事实和最近结论。
- planning context 和 observations 不超过配置预算。
- 长期记忆按 `source_type=memory` 隔离。
- memory 搜索复用 hybrid retrieval，并可返回 trace。
- cleanup/consolidation/restore 有独立 Memory 审计。
- 多实例定时整理由 Redis lease lock 互斥。
- 软删除记忆可通过恢复 API 回滚。
- 陈旧提示存在。
- 自动提取失败不影响主流程。

### Skill

- 无关请求不激活。
- OOM 请求激活示例 skill。
- 工具白名单过严时记录 warning 并 fallback。
