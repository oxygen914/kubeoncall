## 2. 总体结论

当前重构**尚未完成**。

项目已经达到“核心骨架可运行、MVP 主链路基本成形”的状态：告警标准化和策略引擎、工作流模板、RAG facade、Redis session、长期记忆基础、Skill 自动激活、基础审计和 metrics 均已有实现。

但是距离“后端可验收闭环”和专项方案的完整目标仍有明显差距，主要集中在：

1. Alertmanager 上层接入尚未落地：缺批量 Webhook、认证、Redis Stream Inbox、Consumer Group、乱序保护和 dead-letter；当前 `/api/alarms` 仍是同步兼容入口。
2. 告警策略已有 reload/version/dry-run/replay、维护窗口和根因抑制，但仍缺灰度、历史版本回滚、聚合、变更关联、按持续时间升级和多环境覆盖。
3. RAG dense-vector/kNN、`RetrievalHit`、完整 score/latency trace 和 alias/reindex/rollback 代码已完成；真实 HTTP embedding/cross-encoder、真实 alias 切换、数据增强和通用知识治理仍待完成。
4. 告警恢复、升级、通知、工单和维护窗口已形成代码闭环；具体 PagerDuty/Jira/ServiceNow 等生产 adapter 的认证、契约和端到端联调仍待完成。
5. 记忆系统已补 token 预算、历史压缩、hybrid 检索、重复整理、软删除恢复、Redis 分布式整理锁、独立审计、告警诊断消费和相对日期标准化；仍缺 LLM 提取/诊断增强、精确 tokenizer 以及更广泛的并发/外部 adapter 联调。
6. Skill 已补 project 覆盖、禁用、reload、版本/来源和 LLM 指名链路；动态 MCP discovery、统一 Skill/RAG/memory token budget 和真 `load_skill` tool-calling 仍未实现。
7. Prometheus/Grafana、Dockerfile、Helm Chart、CI 已具备静态资产；仍待实际镜像构建、运行环境部署、Prometheus 抓取和外部依赖验收。

因此，总计划中“阶段一、阶段二、阶段三已完成”的结论，只能理解为“第一版核心代码已落地”，不能理解为专项方案全部验收完成。

## 5. 优先处理的正确性问题

### 5.1 P0：旧格式告警 severity 兼容（已修复）

相关位置：

- `src/main/java/com/kubeoncall/alarm/policy/AlarmPolicyEngine.java:45`
- `src/main/java/com/kubeoncall/alarm/policy/AlarmPolicyEngine.java:107`
- `src/main/java/com/kubeoncall/alarm/domain/AlarmEvaluationResult.java:32`
- `src/test/resources/samples/alarm-legacy-format.json`

原问题：

1. 默认策略中的 `labels.team` 被 `AlarmPolicyEngine` 当作强制匹配条件。
2. 旧格式样例没有 `team` label，也没有 `metricName/currentValue`。
3. 策略未命中时，`AlarmEvaluationResult.unmatched()` 使用默认 `P3`。
4. 该路径没有保留 `AlarmNormalizer` 已解析出的上游 `critical -> P0`。

结果是旧格式告警虽然还能进入工作流，但可能丢失正确的策略、PromQL、工作流模板和严重级别，属于“接口可调用但语义不完全兼容”。

本轮完成：

1. 策略 YAML 新增独立 `matchLabels`；`labels` 只作为 owner/routing 输出标签。
2. unmatched 使用默认 severity 与上游 severity 中更严重者。
3. 没有 `currentValue` 时，按精确 alertName 或规范化告警族 + 上游 severity 选择策略。
4. 增加旧 JSON、无 team label、unknown critical 和自定义 alertName + 已知 metric 回归测试。

验收标准：

- 旧格式 `critical` 告警不会被降为 P3。
- 字段缺失时 diagnostics/audit 能说明为什么未命中策略。
- 旧格式 CPU/Node/Pod 样例能得到预期策略或明确兼容 fallback。

### 5.2 P0：ES 相关性顺序（已修复）

相关位置：

- `src/main/java/com/kubeoncall/rag/repository/ElasticsearchKnowledgeRepository.java:130`

原实现会在 ES 返回 hit 后按 `createdAt` 降序重排，覆盖 BM25/ES 原始相关性顺序。

本轮完成：

1. 删除 repository 层 `createdAt` 二次排序，保留 ES hit 顺序。
2. diagnostics 增加 `rankingSource/lexicalRankingSource/vectorRankingSource`。
3. diagnostics 增加 `rawQuery/rewrittenQuery`。
4. 增加“高相关旧文档排在低相关新文档前”的回归测试。

验收标准：

- 高相关旧文档不会被低相关新文档挤到前面。
- 已有相关性顺序单测。
- keyword/hybrid trace 可看到排序来源。

### 5.3 P0：记忆 cleanup 安全边界（已修复）

相关位置：

- `src/main/java/com/kubeoncall/memory/MemoryService.java:73`
- `src/main/java/com/kubeoncall/web/MemoryController.java:14`

原实现会物理删除所有超过 `stale-after-days` 的 memory 文档，稳定事实也可能被删除。

本轮完成：

2. `SERVICE_FACT/KNOWN_PITFALL` 不按时间删除。
3. 使用 `memory_enabled=false/chunk_enable=false/deleted_at/delete_reason` 软删除。
4. API 新增 `dryRun`；响应增加 `eligible/dryRun`。
5. 搜索过滤软删除记忆；增加稳定事实保留、软删除和 dry-run 测试。

本轮已补：cleanup/consolidation/restore 独立 `ExecutionAudit`、`POST /api/memory/{memoryId}/restore` 恢复接口，以及整理任务的 Redis lease lock。

验收标准：

- cleanup 不误删 `SERVICE_FACT/KNOWN_PITFALL`。
- 支持 dry-run、软删除和审计追踪。
- 恢复或回滚软删除可测试。

## 6. 告警重构未完成项

### 6.0 Alertmanager 上层接入

`重构计划/告警上层接入.md` 已补充完整设计，但对应工程能力尚未实现。当前 `AlarmController` 的 `POST /api/alarms` 会同步标准化并直接执行工作流，它不是 Alertmanager 可靠 Webhook 接入层。

仍缺：

- Alertmanager 批量 Webhook DTO、Mapper、Validator 和 `202 Accepted` 语义
- Bearer token/mTLS 认证、payload 大小限制和敏感字段过滤
- Redis Stream Inbox、Consumer Group、后台 worker、重试和 dead-letter
- 重复、批量、乱序和超限保护，以及 FIRING/RESOLVED 生命周期游标
- Alertmanager P0/P1 独立值班 receiver、inhibition 和 silence 配置
- Node Exporter target/service discovery、Linux 基础 dashboard 和 promtool 规则测试
- `alarm-policies.yml` 到 Prometheus rules 的编译、checksum、发布与回滚
- Blackbox Exporter、HTTP/TCP/DNS 探测和服务症状与资源告警关联

因此，现有告警处理链路只能视为“内部标准事件处理闭环”，不能视为《告警上层接入》阶段 1—6 已完成。

### 6.1 策略模型和策略目录

当前已有 18 条策略，覆盖 CPU、内存、磁盘、inode、Node、Pod、Deployment、conntrack、API Server、证书、服务错误率、集群容量和时间同步。仍需按实际监控指标扩展：

- rollout stuck、频繁重启等扩展工作负载策略
- scheduler/controller-manager/etcd 等控制面细分策略
- 延迟、burn-rate 和容量预测策略

治理现状与缺口：

- YAML 顶层 `version` 已进入领域模型、评估结果和告警审计。
- 已提供策略 reload、dry-run 和历史批量 replay API；reload 采用先完整解析、后原子替换。
- 仍没有灰度、版本历史和按历史版本回滚。
- label 只支持精确匹配，没有正则、范围或更完整的条件表达式。
- impact factor 只有硬编码的 `dev/lab` 和 `tier0`，没有配置化的多环境覆盖。

### 6.2 抑制、聚合与升级

当前已新增通用 `AlarmSuppressionService`、版本化 YAML 规则、source/target 资源与 alertName 通配匹配、correlateBy 关联键、Redis TTL 和 reload API。默认规则覆盖 NodeNotReady→同节点 Pod，以及 API Server 根因→同集群控制面派生告警。命中审计包含 ruleId、ruleVersion 和根因 fingerprint；Redis 故障时 fail-open。仍缺：

- 同 service/node/namespace 的关联聚合
- 根因告警和派生告警关系模型
- DiskFull 等更多生产抑制规则
- 按 category 的 dedup TTL

维护窗口已补：Redis 起止时间索引、cluster/namespace/service/resource/alert/label 通配 matcher、创建人与审批人分离、approval reference、创建/撤销 API，以及工作流抑制和 ExecutionAudit。Redis 查询失败时 fail-open，避免维护窗口存储故障吞掉真实告警；相关代码已进入 217 个全量单测基线。

当前 P0/P1 升级通过追加 `alarmEscalation` NodeResult 实现，但：

- 已新增 `POST /api/alarms/acknowledgements`，写入 `alarm-ack:{fingerprint}`，记录确认人、原因、确认时间和 TTL，并清除已有 escalation 去重键。
- acknowledge 已写入独立 metrics 和 Alarm ExecutionAudit；升级判断会读取同一 ack key，已确认告警不再升级。
- 升级达到阈值后会实际调用 `alertmanager.sendAlertEvent` 和 `incident.escalateIncident`；任一外部调用失败时 `alarmEscalation` 返回 FAILURE。
- P1 是按重复 count 升级，不是专项方案中的“持续未恢复时间”。

### 6.3 恢复确认

已完成：

- `RESOLVED` 不再立即确认，而是写入 `alarm-recovery:{fingerprint}` 恢复候选。
- 从策略 `recover` 解析 `for 10m` 等持续窗口；无法解析时按严重度使用配置化默认窗口。
- P2/P3/INFO 到期后由定时任务检查 active alarm 仍为 `RESOLVED`，期间同 fingerprint 再次 FIRING 会取消恢复候选。
- P0/P1 通过 `POST /api/alarms/recovery-confirmations` 人工确认，必须在稳定窗口结束后提交 `healthCheckPassed=true`。
- 恢复事件保留原告警 severity、policyId 和 count，不再被 INFO/P3 覆盖。
- 恢复服务缺失时 fail-closed，返回 `RECOVERY_SERVICE_UNAVAILABLE`，不会旁路确认为已恢复。
- 候选、取消和确认均有 metrics；最终确认写入 Alarm ExecutionAudit。

主动健康检查已补：稳定窗口结束后调用可配置 HTTP endpoint，只有传输成功且响应明确包含 `healthy=true` 才允许确认；endpoint 必需但未配置、超时、异常或不明确响应均 fail-closed，候选保持 pending 供下次扫描重试。P0/P1 人工确认同时要求操作者提交健康检查确认和系统主动检查通过，结果详情进入恢复审计。Docker profile 显式配置健康检查 endpoint。另已补 `TIMED_OUT` 状态和可配置 confirmation timeout；人工候选及长期健康检查失败的自动候选都会审计超时，不再静默依赖 Redis TTL。
- 最终恢复会调用 `alertmanager.sendAlertEvent`、`incident.resolveIncident`，P0/P1 同时调用 `incident.createPostmortem`。
- 恢复已确认但外部收尾失败时，审计状态为 `RECOVERED_DEGRADED`，并记录各 adapter 响应。

### 6.4 工作流节点与外部闭环

已拆出 `NotificationNode/TicketNode/SilenceNode`。`NotificationNode` 调用 Alertmanager HTTP adapter；`TicketNode` 调用 Incident HTTP adapter，P0/P1 执行 `createOrUpdateIncident`，P2/P3 执行 `createTicket`。仍缺：

- 对具体 PagerDuty/Jira/ServiceNow 等生产系统的认证和契约联调。
- P2/P3 日报聚合策略；当前为逐告警普通工单。
- workflow template 仍由 Java 固定编排，没有配置化或热加载。
- `MetricsSnapshotNode/KubernetesDescribeNode/RelatedAlertsNode` 未作为独立节点实现。
- `IntelligentDiagnosisNode` 第一版已实现：合并当前指标/日志/RAG 与历史处置，输出结构化诊断和防陈旧 guardrails；仍缺 LLM 证据推理和变更事件关联。
