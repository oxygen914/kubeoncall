## 1. 文档目的

本文基于以下材料与当前源码进行交叉审计，用于回答“重构是否完成、哪些内容未完成、下一步如何验收”：

审计与续作时间：2026-07-10 CST。

本文随已完成的重构代码、测试和剩余风险持续更新。

## 2. 总体结论

当前重构**尚未完成**。

项目已经达到“核心骨架可运行、MVP 主链路基本成形”的状态：告警标准化和策略引擎、工作流模板、RAG facade、Redis session、长期记忆基础、Skill 自动激活、基础审计和 metrics 均已有实现。

但是距离“后端可验收闭环”和专项方案的完整目标仍有明显差距，主要集中在：

1. 真实 embedding/dense-vector/kNN 代码链路已实现，但还未通过真实 ES/embedding 服务集成验收。
2. 告警恢复、升级、工单、Runbook 绑定未形成生产闭环。
3. 记忆系统缺少 token 预算、历史压缩、hybrid 检索和自动整理。
4. Skill 只有 classpath MVP，缺少覆盖、禁用、reload 和版本治理。
5. 缺少策略回放、长会话验证和真实依赖集成测试。
6. 缺少 Prometheus/Grafana、Dockerfile、Helm Chart、CI 等交付资产。

因此，总计划中“阶段一、阶段二、阶段三已完成”的结论，只能理解为“第一版核心代码已落地”，不能理解为专项方案全部验收完成。

## 5. 优先处理的正确性问题

### 5.1 P0：旧格式告警 severity 兼容（已修复）

相关位置：

- `src/main/java/com/kubeoncall/alarm/policy/AlarmPolicyEngine.java:45`
- `src/main/java/com/kubeoncall/alarm/policy/AlarmPolicyEngine.java:107`
- `src/main/java/com/kubeoncall/alarm/domain/AlarmEvaluationResult.java:32`
- `src/test/resources/samples/alarm-legacy-format.json`

原问题：

1. 默认策略中的 `labels.team` 被 `AlarmPolicyEngine` 当作强制匹配条件。
2. 旧格式样例没有 `team` label，也没有 `metricName/currentValue`。
3. 策略未命中时，`AlarmEvaluationResult.unmatched()` 使用默认 `P3`。
4. 该路径没有保留 `AlarmNormalizer` 已解析出的上游 `critical -> P0`。

结果是旧格式告警虽然还能进入工作流，但可能丢失正确的策略、PromQL、工作流模板和严重级别，属于“接口可调用但语义不完全兼容”。

本轮完成：

1. 策略 YAML 新增独立 `matchLabels`；`labels` 只作为 owner/routing 输出标签。
2. unmatched 使用默认 severity 与上游 severity 中更严重者。
3. 没有 `currentValue` 时，按精确 alertName 或规范化告警族 + 上游 severity 选择策略。
4. 增加旧 JSON、无 team label、unknown critical 和自定义 alertName + 已知 metric 回归测试。

验收标准：

- 旧格式 `critical` 告警不会被降为 P3。
- 字段缺失时 diagnostics/audit 能说明为什么未命中策略。
- 旧格式 CPU/Node/Pod 样例能得到预期策略或明确兼容 fallback。

### 5.2 P0：ES 相关性顺序（已修复）

相关位置：

- `src/main/java/com/kubeoncall/rag/repository/ElasticsearchKnowledgeRepository.java:130`

原实现会在 ES 返回 hit 后按 `createdAt` 降序重排，覆盖 BM25/ES 原始相关性顺序。

本轮完成：

1. 删除 repository 层 `createdAt` 二次排序，保留 ES hit 顺序。
2. diagnostics 增加 `rankingSource/lexicalRankingSource/vectorRankingSource`。
3. diagnostics 增加 `rawQuery/rewrittenQuery`。
4. 增加“高相关旧文档排在低相关新文档前”的回归测试。

验收标准：

- 高相关旧文档不会被低相关新文档挤到前面。
- 已有相关性顺序单测。
- keyword/hybrid trace 可看到排序来源。

### 5.3 P0：记忆 cleanup 安全边界（已修复）

相关位置：

- `src/main/java/com/kubeoncall/memory/MemoryService.java:73`
- `src/main/java/com/kubeoncall/web/MemoryController.java:14`

原实现会物理删除所有超过 `stale-after-days` 的 memory 文档，稳定事实也可能被删除。

本轮完成：

1. cleanup 只处理过期 `DEVICE_HISTORY/INCIDENT_SUMMARY`。
2. `SERVICE_FACT/KNOWN_PITFALL` 不按时间删除。
3. 使用 `memory_enabled=false/chunk_enable=false/deleted_at/delete_reason` 软删除。
4. API 新增 `dryRun`；响应增加 `eligible/dryRun`。
5. 搜索过滤软删除记忆；增加稳定事实保留、软删除和 dry-run 测试。

仍待补：cleanup 独立 ExecutionAudit、恢复软删除 API、MemoryConsolidationJob。

验收标准：

- cleanup 不误删 `SERVICE_FACT/KNOWN_PITFALL`。
- 支持 dry-run、软删除和审计追踪。
- 恢复或回滚软删除可测试。

## 6. 告警重构未完成项

### 6.1 策略模型和策略目录

当前已有 12 条首批 CPU、内存、磁盘、inode、Node、Pod、Deployment 策略，但专项方案中的完整目录尚未覆盖：

- 网络和连接
- K8s 容量与资源请求
- Kubernetes 控制面
- 证书和时间同步
- 服务层 SLO
- rollout stuck、频繁重启等扩展工作负载策略

其他缺口：

- YAML 顶层 `version` 没有进入领域模型和审计。
- 没有策略 reload API/actuator endpoint。
- 没有灰度、active version、变更历史和回滚。
- label 只支持精确匹配，没有正则、范围或更完整的条件表达式。
- impact factor 只有硬编码的 `dev/lab` 和 `tier0`，没有配置化的多环境覆盖。

### 6.2 抑制、聚合与升级

当前只实现 NodeNotReady 对同节点 Pod 告警的抑制，仍缺：

- 通用 `AlarmSuppressionService`
- 同 service/node/namespace 的关联聚合
- 根因告警和派生告警关系模型
- ApiServerDown、DiskFull 等其他抑制规则
- 维护窗口模型
- 按 category 的 dedup TTL

当前 P0/P1 升级通过追加 `alarmEscalation` NodeResult 实现，但：

- 仓库中没有告警 acknowledge API。
- `alarm-ack:{fingerprint}` 没有应用内写入路径。
- 升级结果不会再次经过 NotificationNode/TicketNode。
- P1 是按重复 count 升级，不是专项方案中的“持续未恢复时间”。

### 6.3 恢复确认

当前收到 `RESOLVED` 后立即返回 `Alarm recovery confirmed`，没有实现专项方案中的：

- 指标持续低于恢复阈值
- 连续健康检查
- 一段时间无新同 fingerprint 告警
- P0/P1 人工恢复确认
- 确认超时策略
- P0/P1 自动创建复盘
- 关闭关联工单

### 6.4 工作流节点与外部闭环

已拆出 `NotificationNode/TicketNode/SilenceNode`，但仍缺：

- `TicketNode` 只准备 payload，没有真实工单/incident adapter。
- P0/P1 没有保证一定创建高优先级 incident。
- P2/P3 没有日报/普通工单策略。
- workflow template 仍由 Java 固定编排，没有配置化或热加载。
- `MetricsSnapshotNode/KubernetesDescribeNode/RelatedAlertsNode` 未作为独立节点实现。
- 变更事件关联和 `IntelligentDiagnosisNode` 未实现。

### 6.5 告警 Runbook/RAG 绑定

相关位置：

- `src/main/java/com/kubeoncall/workflow/node/KnowledgeRetrieveNode.java:34`

当前只用 `nodeName` 和 `severity` 作为 RAG filters，没有按方案使用：

- `alertName`
- `resourceType`
- `service`
- `runbookId`
- 策略中的 `ragFilters`

仓库内也没有对应 CPU、磁盘、CrashLoop、OOMKilled、NodeNotReady 的可验收 SOP 数据和端到端测试。

### 6.6 策略治理和补充方案

以下专项内容尚未实现：

- 告警历史回放工具
- 策略 Dry-Run API
- 误报率、漏报率、重复率、MTTA、MTTR
- 告警健康度看板
- top noisy alerts
- 每周策略调优报告

## 7. RAG 重构未完成项

### 7.1 架构验收边界

本轮聚焦 RAG 模块拆分、向量存储/检索、候选融合、精排和失败回退。评估数据集、Recall/MRR/HitRate 脚本和 baseline 报告不属于当前架构重构交付范围，后续如进入效果优化阶段再单独建设。

### 7.2 入库和 metadata 工程

已完成基本 metadata 和 parent 保存，但仍缺：

- `IngestionResult`
- `KnowledgeMetadataFactory`
- `heading_path`
- `created_at/updated_at` 的标准可查询字段
- 幂等入库和同文档更新
- file hash 去重流程
- JSONL 批量导入

当前 chunker 虽然支持 `fixed/markdown/recursive`，但默认配置仍是：

```yaml
chunk-size: 280
chunk-overlap: 0
```

与专项方案建议的 `1000/200` 仍不一致。

### 7.3 真实 embedding 和 ES kNN（代码链路已完成）

本轮已完成：

- `KnowledgeDocument`、`EsKnowledgeDocumentEntity` 增加 `embedding_text/embedding`。
- `KnowledgeIndexAdmin` 创建或补充 `dense_vector` mapping，并校验配置维度和现有索引维度。
- 入库只对启用的 chunk 生成 embedding，写入 model/version/provider/dim/mock/status metadata；失败不阻断原文入库。
- `HttpEmbeddingClient` 对齐 OpenAI `/v1/embeddings` 的 `model/input` 和 `data[0].embedding`，保留旧响应兼容。
- query embedding 通过 `RepositoryVectorRetriever` 传入 repository，使用 ES native kNN query 和 metadata filter。
- 删除 `content matches` 假向量兜底；向量后端不可用时 hybrid 明确回退 keyword。
- `vector-backend=es|external` 保证 ES 和外部向量 adapter 互斥。

仍待完成：

- 使用真实 Elasticsearch 验证索引创建、mapping 升级、写入和 kNN 结果。
- 使用真实 embedding 服务验证认证、超时、维度和批量吞吐。
- embedding model/version 与 index alias、dataset version 的重建治理。
- vector disabled/mock/failed 已有单测；真实服务路径仍需集成测试。

### 7.4 RetrievalHit、候选和 RRF trace

已完成：

- `candidateTopN = min(max(50, 10 * topK), 200)`，并保留 fused 候选到 rerank。
- lexical 默认过滤 `chunk_enable=true`。
- raw query、rewritten query、排序来源和各通道文档 ID trace。

仍缺：

- `RetrievalHit` 中的 ES score、rank、channel
- 每阶段 latency
- lexical/vector/fused 的 score trace

### 7.5 Cross-encoder 主路径

本轮已完成：

- fused top 30 进入 rerank，Facade 最后裁 `topK`。
- HTTP 请求使用 `model/query/documents/top_n`，解析 `results[index/relevance_score]`。
- 配置启用且服务成功时 cross-encoder 是主排序路径。
- 超时、异常或空分数时严格保留 retrieval/RRF 顺序，不再重新按 overlap 排序。
- trace 包含 `crossEncoderScoreByDocument/crossEncoderFallbackReason/rerankStrategy/rankTrace`。
- 已增加 mock HTTP 契约、主排序和 fallback 回归测试。

仍待完成：真实 cross-encoder 服务联调和吞吐/超时验证。

### 7.6 数据增强和知识库治理

完全未实现：

## 8. 记忆系统未完成项

### 8.1 会话压缩和 token 预算

完全缺少：

- `TokenBudget`
- `ConversationHistoryCompactor`
- `ContextCompressor`
- planner/verifier/executor loop 压缩触发点
- 近期原文 + 早期摘要 + 安全缓冲

当前 `SessionSnapshot` 只保留最近 N 个 turn，`AskService` 只注入最近 4 轮的截断文本。这可以限制长度，但会直接丢弃早期上下文，不满足“50 轮仍保留关键上下文”的验收要求。

### 8.2 长期记忆模型和检索

- `DEVICE_HISTORY`
- `SERVICE_FACT`
- `KNOWN_PITFALL`
- `INCIDENT_SUMMARY`
- `USER_PREFERENCE`
- `USER_NOTE`

已兼容专项设计的四类记忆，同时保留 `INCIDENT_SUMMARY/USER_NOTE` 旧类型；仍没有领域模型级 `tokenCount/enabled` 字段，软删除状态目前保存在 metadata。

`MemoryService.search()` 仍直接使用 lexical repository，没有复用 `KnowledgeRetrievalFacade/HybridRetrievalService`，因此不能返回完整 hybrid trace。

### 8.3 记忆注入和消费

已完成：只向 Ask planner 注入 `SERVICE_FACT/KNOWN_PITFALL`，并包含新鲜度和“先验证当前状态”提示。

- 同设备二次告警尚不能基于上次处置调整诊断或避免重复处置。

### 8.4 自动提取质量

- `MemoryExtractionPromptBuilder`

- 近似重复判断
- 更完整的 `WHAT_NOT_TO_SAVE`

### 8.5 夜间整理

完全缺少：

- `MemoryConsolidationJob`
