## 2. 总体结论

当前计划**尚未完成**，但待办已收紧，不再以完整生产平台作为完成标准。

项目已经达到“核心骨架可运行、MVP 主链路基本成形”的状态：告警标准化和策略引擎、工作流模板、RAG facade、Redis session、长期记忆基础、Skill 自动激活、基础审计和 metrics 均已有实现。

当前仅保留以下两条实施主线：

1. **节点监控告警 MVP：** Node Exporter、Prometheus 五条规则、单一 Alertmanager receiver 与 KubeOnCall Webhook/Bearer/基础去重的真实演练；`NodeNotReady` 仅在接入 kube-state-metrics 后加入。
2. **RAG 知识代码层：** 通用知识生命周期、统一 metadata、Markdown 标题路径与 active dataset 自动过滤均已完成代码与单测；真实 embedding/cross-encoder 服务联调仍待环境验收。

其余告警生产化、alias 实战切换、记忆、Skill、外部工单和部署治理能力均保留为历史审计或后续 backlog，不计入当前完成度。

因此，总计划中“阶段一、阶段二、阶段三已完成”的结论，只能理解为“第一版核心代码已落地”，不能理解为专项方案全部验收完成。

## 5. 优先处理的正确性问题

### 5.1 P0：旧格式告警 severity 兼容（已修复）

相关位置：

- `src/main/java/com/kubeoncall/alarm/policy/AlarmPolicyEngine.java:45`
- `src/main/java/com/kubeoncall/alarm/policy/AlarmPolicyEngine.java:107`
- `src/main/java/com/kubeoncall/alarm/domain/AlarmEvaluationResult.java:32`
- `src/test/resources/samples/alarm-legacy-format.json`

原问题：

1. 默认策略中的 `labels.team` 被 `AlarmPolicyEngine` 当作强制匹配条件。
2. 旧格式样例没有 `team` label，也没有 `metricName/currentValue`。
3. 策略未命中时，`AlarmEvaluationResult.unmatched()` 使用默认 `P3`。
4. 该路径没有保留 `AlarmNormalizer` 已解析出的上游 `critical -> P0`。

结果是旧格式告警虽然还能进入工作流，但可能丢失正确的策略、PromQL、工作流模板和严重级别，属于“接口可调用但语义不完全兼容”。

本轮完成：

1. 策略 YAML 新增独立 `matchLabels`；`labels` 只作为 owner/routing 输出标签。
2. unmatched 使用默认 severity 与上游 severity 中更严重者。
3. 没有 `currentValue` 时，按精确 alertName 或规范化告警族 + 上游 severity 选择策略。
4. 增加旧 JSON、无 team label、unknown critical 和自定义 alertName + 已知 metric 回归测试。

验收标准：

- 旧格式 `critical` 告警不会被降为 P3。
- 字段缺失时 diagnostics/audit 能说明为什么未命中策略。
- 旧格式 CPU/Node/Pod 样例能得到预期策略或明确兼容 fallback。

### 6.1 策略模型和策略目录

当前已有 18 条策略，覆盖 CPU、内存、磁盘、inode、Node、Pod、Deployment、conntrack、API Server、证书、服务错误率、集群容量和时间同步。节点监控 MVP 只使用其中 5～6 条；以下扩展项明确不排期：

- rollout stuck、频繁重启等扩展工作负载策略
- scheduler/controller-manager/etcd 等控制面细分策略
- 延迟、burn-rate 和容量预测策略

治理现状与缺口：

- YAML 顶层 `version` 已进入领域模型、评估结果和告警审计。
- 已提供策略 reload、dry-run 和历史批量 replay API；reload 采用先完整解析、后原子替换。
- 本轮新增进程内版本快照，提供 `POST /api/alarm-policies/versions` 和 `POST /api/alarm-policies/rollback`；告警可通过 `kubeoncall_policy_version` label 或 `policyVersion` metadata 固定命中已加载版本，用于灰度。
- 版本历史当前在进程内保存，重启后不会恢复；尚未实现外部持久化、审批发布和历史版本 replay。
- label 只支持精确匹配，没有正则、范围或更完整的条件表达式。
- impact factor 只有硬编码的 `dev/lab` 和 `tier0`，没有配置化的多环境覆盖。

### 6.2 抑制、聚合与升级

当前已新增通用 `AlarmSuppressionService`、版本化 YAML 规则、source/target 资源与 alertName 通配匹配、correlateBy 关联键、Redis TTL 和 reload API。默认规则覆盖 NodeNotReady→同节点 Pod，以及 API Server 根因→同集群控制面派生告警。命中审计包含 ruleId、ruleVersion 和根因 fingerprint；Redis 故障时 fail-open。以下扩展缺口明确不作为当前待办：

- 更细粒度的 node/namespace 多维聚合与聚合摘要通知（当前按策略 + service/resource/namespace/cluster scope 聚合；P0 和恢复事件始终直通）
- 根因告警和派生告警关系模型
- DiskFull 等更多生产抑制规则
- 按 category 的 dedup TTL

维护窗口已补：Redis 起止时间索引、cluster/namespace/service/resource/alert/label 通配 matcher、创建人与审批人分离、approval reference、创建/撤销 API，以及工作流抑制和 ExecutionAudit。Redis 查询失败时 fail-open，避免维护窗口存储故障吞掉真实告警；相关代码已进入 217 个全量单测基线。

当前 P0/P1 升级通过追加 `alarmEscalation` NodeResult 实现，但：

- 已新增 `POST /api/alarms/acknowledgements`，写入 `alarm-ack:{fingerprint}`，记录确认人、原因、确认时间和 TTL，并清除已有 escalation 去重键。
- acknowledge 已写入独立 metrics 和 Alarm ExecutionAudit；升级判断会读取同一 ack key，已确认告警不再升级。
- 升级达到阈值后会实际调用 `alertmanager.sendAlertEvent` 和 `incident.escalateIncident`；任一外部调用失败时 `alarmEscalation` 返回 FAILURE。
- P0/P1 现同时支持重复 count 与持续未恢复时间门槛：默认 P0 10 分钟、P1 30 分钟，达到任一条件后升级；已确认告警仍不会升级。

### 6.3 恢复确认

已完成：

- `RESOLVED` 不再立即确认，而是写入 `alarm-recovery:{fingerprint}` 恢复候选。
- 从策略 `recover` 解析 `for 10m` 等持续窗口；无法解析时按严重度使用配置化默认窗口。
- P2/P3/INFO 到期后由定时任务检查 active alarm 仍为 `RESOLVED`，期间同 fingerprint 再次 FIRING 会取消恢复候选。
- P0/P1 通过 `POST /api/alarms/recovery-confirmations` 人工确认，必须在稳定窗口结束后提交 `healthCheckPassed=true`。
- 恢复事件保留原告警 severity、policyId 和 count，不再被 INFO/P3 覆盖。
- 恢复服务缺失时 fail-closed，返回 `RECOVERY_SERVICE_UNAVAILABLE`，不会旁路确认为已恢复。
- 候选、取消和确认均有 metrics；最终确认写入 Alarm ExecutionAudit。

主动健康检查已补：稳定窗口结束后调用可配置 HTTP endpoint，只有传输成功且响应明确包含 `healthy=true` 才允许确认；endpoint 必需但未配置、超时、异常或不明确响应均 fail-closed，候选保持 pending 供下次扫描重试。P0/P1 人工确认同时要求操作者提交健康检查确认和系统主动检查通过，结果详情进入恢复审计。Docker profile 显式配置健康检查 endpoint。另已补 `TIMED_OUT` 状态和可配置 confirmation timeout；人工候选及长期健康检查失败的自动候选都会审计超时，不再静默依赖 Redis TTL。
- 最终恢复会调用 `alertmanager.sendAlertEvent`、`incident.resolveIncident`，P0/P1 同时调用 `incident.createPostmortem`。
- 恢复已确认但外部收尾失败时，审计状态为 `RECOVERED_DEGRADED`，并记录各 adapter 响应。
