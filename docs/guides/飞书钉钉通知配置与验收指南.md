# 飞书、钉钉通知配置与验收指南

本文说明如何启用 KubeOnCall 的多渠道通知底座、配置逻辑路由，以及如何区分代码验证、平台受理和真实接收者验收。

## 1. 前置条件

- MySQL 与 Flyway 已启用，`V19__notification_delivery.sql` 已成功执行。
- Outbox Worker 正常运行。
- 已在飞书或钉钉的测试群中创建自定义机器人。
- Webhook 和签名密钥保存在 Secret Manager、Kubernetes Secret 或部署平台密钥配置中，不写入仓库。
- `oncall-phone` 不得映射为飞书或钉钉群机器人；电话、Pager 等强提醒能力需要独立 Provider。

## 2. 配置示例

以下示例让 `oncall` 同时投递到飞书和钉钉，让 `approval` 只投递到飞书。目的地中的 `target` 是配置别名，不是 Webhook。

```yaml
kubeoncall:
  mysql-enabled: true
  notifications:
    enabled: true
    routes:
      - key: oncall
        destinations:
          - id: feishu-infra-primary
            provider-key: feishu
            target: infra-primary
            required-capabilities:
              - GROUP_WEBHOOK
          - id: dingtalk-infra-backup
            provider-key: dingtalk
            target: infra-backup
            required-capabilities:
              - GROUP_WEBHOOK
      - key: approval
        destinations:
          - id: feishu-approval
            provider-key: feishu
            target: approval
            required-capabilities:
              - GROUP_WEBHOOK
    feishu:
      targets:
        infra-primary:
          webhook-url: ${KUBEONCALL_FEISHU_INFRA_WEBHOOK}
          secret: ${KUBEONCALL_FEISHU_INFRA_SECRET}
          timeout-millis: 5000
        approval:
          webhook-url: ${KUBEONCALL_FEISHU_APPROVAL_WEBHOOK}
          secret: ${KUBEONCALL_FEISHU_APPROVAL_SECRET}
          timeout-millis: 5000
    dingtalk:
      targets:
        infra-backup:
          webhook-url: ${KUBEONCALL_DINGTALK_INFRA_WEBHOOK}
          secret: ${KUBEONCALL_DINGTALK_INFRA_SECRET}
          timeout-millis: 5000
```

安全边界：

- 飞书仅允许 `https://open.feishu.cn/open-apis/bot/v2/hook/` 或对应 Lark 官方主机。
- 钉钉自定义机器人仅允许 `https://oapi.dingtalk.com/robot/send`。
- 非 HTTPS、非官方主机、带用户信息的 URL 或错误路径会在启动时被拒绝。
- Provider 只声明 `GROUP_WEBHOOK`；私聊、@人、卡片更新和回调不能借此配置冒充已支持。

平台协议以[飞书自定义机器人文档](https://open.feishu.cn/document/ukTMukTMukTM/ucTM5YjL3ETO24yNxkjN?lang=zh-CN)、[飞书消息卡片发送文档](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/feishu-cards/quick-start/send-message-cards-with-custom-bot)和[钉钉自定义机器人文档](https://open.dingtalk.com/document/orgapp/custom-robot-access)为准。

## 3. 事件与路由

| 事件 | 默认逻辑路由 | 说明 |
| --- | --- | --- |
| `alarm.firing.initial` | 告警策略的 `notificationChannel`，缺省 `oncall` | 诊断前快速通知 |
| `alarm.firing.diagnosis-completed` | 同上 | 诊断完成后的补充通知 |
| `alarm.escalated` | 同上 | 未确认达到升级阈值 |
| `alarm.acknowledged` | `oncall` | 告警确认 |
| `alarm.recovery.confirmed` / `alarm.recovered` | `oncall` | 恢复确认 |
| `alarm.silence.approved` | `oncall` | 静默批准 |
| `approval.requested` / `approval.decided` | `approval` | 工作流审批生命周期 |

自定义群机器人不支持原消息更新，因此“诊断完成”当前表现为追加消息。需要更新原卡片时，应新增具备 `CARD_UPDATE` 能力的应用机器人 Provider。

## 4. 投递状态

一条逻辑通知会为每个实际目的地创建一条 `koc_notification_delivery`：

- `PENDING`：已持久化，等待 Worker。
- `PROCESSING`：Worker 正在调用平台。
- `RETRYING`：临时失败，Outbox 已安排退避重试。
- `DELIVERED`：HTTP 成功且平台业务码为成功；含义是“平台接口受理”，不是“某位人员已阅读”。
- `FAILED`：永久配置或业务错误，不自动重试。
- `DEAD_LETTER`：临时错误耗尽最大尝试次数。

Outbox 保障的是至少一次处理。飞书、钉钉自定义群机器人接口不提供可由本系统控制的服务端幂等键，因此极端情况下若平台已受理、进程却在落库前中断，重试可能产生重复消息。投递 ID 可用于排查，但不能把自定义机器人描述为端到端严格一次。

管理员可调用：

```text
POST /api/v1/integrations/notifications/{deliveryId}/replays
Permission: integration:manage
Body: {"reason":"credential rotated and verified"}
```

该操作只接受 `FAILED` 或 `DEAD_LETTER`，会写操作审计、增加 `replayCount` 并创建新的 Outbox 事件。

## 5. 验收顺序

1. 启动检查：确认 Flyway、通知配置和 Provider 注册均无错误。
2. Mock 检查：验证飞书 `interactive` 卡片、钉钉 `markdown`、时间戳签名和非零业务错误码。
3. 单目的地检查：分别向飞书、钉钉测试群发送，确认投递表为 `DELIVERED`。
4. 多目的地检查：同一 `oncall` 事件产生两条投递记录，单个平台失败不影响另一平台。
5. 重试检查：模拟限流或 5xx，确认 `RETRYING`、退避和最终恢复。
6. 死信与重放：使凭证失效至 `DEAD_LETTER`，修复凭证后由管理员重放。
7. 真实接收检查：由测试群中的真实值班人员确认消息可见、内容正确且无敏感数据。

只有第 7 步完成后，才能表述为“真实渠道已验收”；代码测试、HTTP 200 或平台业务码 0 都不能替代真实接收证明。
