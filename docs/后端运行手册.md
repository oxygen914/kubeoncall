# KubeOnCall 后端运行手册

## 本地启动

基础验证命令：

```bash
cd backend
./mvnw verify
```

本地运行：

```bash
cd backend
./mvnw spring-boot:run
```

默认 profile 为 `local`，配置入口在 `backend/src/main/resources/application.yml` 和 `application-local.yml`。

## 单文件 Kubernetes 部署

仓库提供一个面向本地 Kubernetes/Minikube 的单文件部署清单：

```text
deploy/kubernetes/kubeoncall-standalone.yaml
```

该文件包含：

- KubeOnCall 应用及 ClusterIP Service。
- Redis、Elasticsearch 8 和 MinIO。
- 三个数据 PVC。
- MinIO `kubeoncall-docs` Bucket 初始化 Job。
- 依赖等待、健康检查和基础资源限制。

Standalone 清单默认使用阿里云百炼 OpenAI 兼容接口运行 `qwen-plus` 和 `text-embedding-v4`，MCP、Cross Encoder 和外部工具调用仍保持关闭。模型密钥不写入清单或 Git，部署前必须先创建 Kubernetes Secret。

从环境变量创建模型 Secret：

```bash
kubectl -n kubeoncall create secret generic kubeoncall-model-secrets \
  --from-literal=aliyun-api-key="$ALIYUN_API_KEY" \
  --dry-run=client -o yaml | kubectl apply -f -
```

`ALIYUN_API_KEY` 应设置为可访问百炼模型的密钥。不要把实际值写进仓库文件或终端历史。

### Minikube 部署

如果本机启用了 HTTP/HTTPS 代理，先让 `kubectl` 绕过 Minikube API 地址：

```bash
export NO_PROXY="${NO_PROXY:+$NO_PROXY,}$(minikube ip)"
export no_proxy="$NO_PROXY"
```

先把当前源码构建到 Minikube 的容器运行时：

```bash
cd /home/jsa/kubeoncall
minikube image build -t kubeoncall:standalone backend
```

如果 Minikube 内部 Docker 代理不可用，或者宿主机 Docker 缺少 buildx，可采用预编译 JAR 路径：

```bash
mkdir -p "$HOME/.m2/repository"

docker run --rm \
  --user "$(id -u):$(id -g)" \
  -e MAVEN_CONFIG=/m2 \
  -v "$PWD:/workspace" \
  -v "$HOME/.m2:/m2" \
  -w /workspace/backend \
  maven:3.9.9-eclipse-temurin-17 \
  mvn --batch-mode --no-transfer-progress \
    -Dmaven.repo.local=/m2/repository \
    -DskipTests package

docker build \
  -f deploy/local/Dockerfile.prebuilt \
  -t kubeoncall:standalone .

minikube image load kubeoncall:standalone
```

`Dockerfile.prebuilt` 只负责把已经生成的 Spring Boot JAR 制作为 Java 17 运行镜像。正式发布仍应在 CI 中先执行测试，再构建镜像。

部署全部资源：

```bash
kubectl apply -f deploy/kubernetes/kubeoncall-standalone.yaml
kubectl -n kubeoncall get pods,pvc,svc,jobs
kubectl -n kubeoncall rollout status deployment/kubeoncall --timeout=300s
```

本机已有服务占用 8080 时，使用端口转发到 18090：

```bash
kubectl -n kubeoncall port-forward service/kubeoncall 18090:8080
```

另一个终端验证：

```bash
curl -fsS http://127.0.0.1:18090/actuator/health
curl -fsS http://127.0.0.1:18090/api/status
```

查看启动和 Runbook 导入日志：

```bash
kubectl -n kubeoncall logs deployment/kubeoncall --tail=200
kubectl -n kubeoncall logs job/minio-create-kubeoncall-docs
```

### 切换到真实模型

真实部署前至少需要：

1. 替换清单中的 MinIO 默认凭据，或改为引用外部 Secret。
2. 确保 `kubeoncall-model-secrets` 已创建，并通过 Secret 注入真实 `SPRING_AI_OPENAI_API_KEY` 与 `RAG_EMBEDDING_API_KEY`。
3. 当前清单已启用 `qwen-plus` 和 1536 维 `text-embedding-v4`；更换模型时需同步修改 endpoint、模型名和维度。
4. 按需开启 Cross Encoder 和 MCP，并配置集群内可解析的 Service 地址。
5. 为 Elasticsearch、Redis、MinIO 设置生产级认证、备份、存储类和网络策略。
6. 移除或替代 Elasticsearch 的 privileged sysctl init container；生产集群应由节点管理员统一设置 `vm.max_map_count=262144`。

### 完整卸载

删除清单内的工作负载、Service 和 PVC：

```bash
kubectl delete -f deploy/kubernetes/kubeoncall-standalone.yaml --cascade=foreground
```

若需要保留数据，应在删除前备份；也可以分别删除 Deployment、Job 和 Service，但保留 Namespace 与 PVC，不要直接执行整份清单的删除命令。

## 集成依赖

默认单测不依赖 Redis、Elasticsearch、MinIO。需要完整联调时先启动外部依赖：

```bash
docker compose up -d redis elasticsearch minio minio-init
```

执行全部真实依赖集成测试（Elasticsearch 知识链路、Redis Skill 状态、MinIO 原文存储）：

```bash
docker compose up -d redis elasticsearch minio minio-init
(cd backend && ./mvnw -Pintegration-test verify)
```

当前存储约束：

- Redis：session、approval、audit、active alarm、短期抑制和升级状态。
- Elasticsearch：知识库、长期记忆。
- MinIO：原始知识文档。

## 告警策略

策略文件固定在：

```text
backend/src/main/resources/alarm-policies.yml
```

核心配置前缀：

```yaml
kubeoncall:
  alarm:
    policy-location: classpath:alarm-policies.yml
    p0-dedup-ttl-seconds: 1800
    p1-dedup-ttl-seconds: 1200
    node-not-ready-suppression-ttl-seconds: 1800
    escalation-ttl-seconds: 3600
    silence-approval-ttl-seconds: 1800
```

`ResultPushNode` 只输出诊断摘要；`SilenceNode` 只有策略 `autoSilence=true` 且 Redis 中存在未过期人工审批时才会调用 `alertmanager.createSilence`。

人工批准一次 silence：

```http
POST /api/alarms/silence-approvals
Content-Type: application/json

{
  "fingerprint": "fp-payment-oom",
  "approvedBy": "incident-commander",
  "reason": "maintenance window",
  "ttlSeconds": 1800
}
```

审批状态写入 Redis key `alarm-silence-approval:{fingerprint}`，过期后工作流会自动回到“不创建 silence”的安全路径。

## RAG 重建

生产 SOP 正文位于 `backend/src/main/resources/runbooks/*.md`，frontmatter 必须包含 `runbookId/title/category/owner/version`。手工检查或导入：

```http
POST /api/knowledge/runbooks/import
Content-Type: application/json

{"dryRun": true}
```

将 `dryRun` 改为 `false` 执行导入。导入按 `runbookId + dataset_version` 幂等；也可设置 `kubeoncall.rag.runbook-bootstrap-enabled=true` 在启动时导入。

写入知识：

```http
POST /api/knowledge/ingest
```

检索知识：

```http
POST /api/knowledge/query
```

可选参数：

- `topK`
- `retrieveMethod`: `KEYWORD`、`VECTOR`、`HYBRID`
- `includeTrace`

默认 vector 关闭；真实 embedding、ES kNN、rerank 服务都通过 `kubeoncall.rag.*` 配置启用。

告警策略可声明静态 SOP metadata 约束：

```yaml
- id: pod-oom-killed-p1
  runbookId: runbook-pod-oom
  ragFilters:
    document_type: runbook
    category: k8s-pod
```

SOP 入库 metadata 至少应包含对应 `runbookId/document_type/category`。`KnowledgeRetrieveNode` 首次检索再追加告警的 `alertName/resourceType/service/nodeName/severity`。如果严格维度没有结果，只使用 `runbookId + ragFilters` 重试，不会检索其他 runbook。响应中的 `ragFilterFallback/ragRetrievalAttempts` 可用于排障。

本地 ES kNN 示例：

```yaml
kubeoncall:
  rag:
    vector-enabled: true
    vector-backend: es
    es-knn-enabled: true
    embedding-enabled: true
    mock-embedding-enabled: false
    embedding-endpoint: http://localhost:18086/v1/embeddings
    embedding-model: text-embedding-3-small
    embedding-version: v1
    embedding-dimensions: 1536
    cross-encoder-enabled: true
    cross-encoder-endpoint: http://localhost:18086/v1/rerank
    cross-encoder-model: cross-encoder
    rerank-top-n: 30
```

`embedding-dimensions` 必须与 embedding 服务返回长度一致，也必须与现有 ES 索引 mapping 一致。`KnowledgeIndexAdmin` 会在首次写入向量或执行 kNN 前创建/补充 `dense_vector` 和 `metadata=flattened` mapping。维度冲突会失败；旧索引若为 `metadata=object`，必须改用新索引重新导入，不能在线修改字段类型。

如使用外部向量检索 adapter，设置 `vector-backend: external` 和 `vector-endpoint`。`es` 与 `external` 不会同时召回。

embedding 入库失败不会丢失 parent/chunk 原文；chunk metadata 会写 `embedding_status=failed`。向量检索不再使用 `content matches` 冒充 kNN；无可用向量 backend 时会明确回退 keyword。

开启 `includeTrace=true` 时，`diagnostics` 会包含检索和 rerank 的轻量 trace：

- `lexicalDocumentIds`、`vectorDocumentIds`、`fusedDocumentIds`
- `rerankInputDocumentIds`、`rerankedDocumentIds`
- `rankTrace`: 每个最终文档的 `rank/documentId/ruleScore/crossEncoderScore`
- `rerankStrategy`、`crossEncoderFallback`、`crossEncoderFallbackReason`
- `rankingSource`、`lexicalRankingSource`、`vectorRankingSource`
- `rawQuery`、`rewrittenQuery`

## 记忆检索与压缩

显式检索长期记忆：

```http
POST /api/memory/search
Content-Type: application/json

{
  "query": "payment-service owner",
  "filters": {
    "service": "payment-service"
  },
  "topK": 5,
  "includeTrace": true
}
```

服务端强制追加 `source_type=memory`，不会返回普通 SOP。`includeTrace=true` 时返回 hybrid retrieval 的 `rankingSource/vectorFallback/rerankStrategy` 等 diagnostics。

会话和运行上下文预算：

```yaml
kubeoncall:
  memory:
    max-session-turns: 12
    session-recent-turns: 6
    session-token-budget: 1200
    session-summary-token-budget: 600
    context-token-budget: 2400
    observation-token-budget: 800
    max-observation-entries: 20
    temporal-normalization-zone: Asia/Shanghai
```

超过预算后，Redis session 保存早期摘要/关键事实和最近原始 turns；`skillPrompt/memoryContext/sessionContext` 进入 planner 前统一压缩。运行 observations 保留关键失败/审批事件和最近记录。

告警工作流在指标比较和 RAG 检索后进入 `IntelligentDiagnosisNode`。节点会读取同 fingerprint/service/resource 的历史记忆，输出：

- `strategy`：无历史时为 `CURRENT_EVIDENCE_ONLY`；有历史且已有实时证据时为 `VERIFY_CURRENT_EVIDENCE_BEFORE_REUSING_PRIOR_HANDLING`。
- `repeatedIncident`、`activeCount`、`memoryConsumedCount`、`memoryIds`。
- `previousHandlingCandidates`：经过 token budget 限制，包含类型、用途、更新时间、`ageDays/stale`。
- `guardrails`：先验证当前指标/日志/资源状态；禁止执行记忆中的命令；历史与当前证据冲突时优先使用当前 runbook。

`USER_PREFERENCE/USER_NOTE` 不进入告警诊断。历史记忆只作证据，不会直接触发工具或变更操作。

所有长期记忆在 `MemoryService.remember()` 写入前执行相对日期标准化：

- “今天/昨天/前天/N 天前/N 周前/上周”及英文对应表达转为绝对日期或日期区间。
- 解析锚点使用记忆 `createdAt`，时区使用 `temporal-normalization-zone`，不依赖服务器默认时区。
- “最近/前些天/last month”等模糊表达保留原文，并标记 `temporal_normalization_status=unresolved`。
- metadata 保存 reference、zone、replacement count 和 unresolved expressions，便于审计。

## 记忆清理

长期记忆以 `source_type=memory` 写入知识库，默认不会污染 SOP 检索。

告警记忆只沉淀结构化处置摘要；写入前会过滤包含 `kubectl` 命令、实时值、当前值的摘要片段。

清理陈旧记忆：

```http
POST /api/memory/cleanup
Content-Type: application/json

{
  "scanLimit": 500,
  "dryRun": true
}
```

清理阈值由以下配置控制：

```yaml
kubeoncall:
  memory:
    stale-after-days: 30
```

清理只处理过期 `DEVICE_HISTORY/INCIDENT_SUMMARY`。`SERVICE_FACT/KNOWN_PITFALL` 不会按时间删除。

默认使用软删除：写入 `memory_enabled=false`、`chunk_enable=false`、`deleted_at` 和 `delete_reason`。建议先用 `dryRun=true` 查看候选，再用 `dryRun=false` 执行。

恢复单条软删除记忆：

```http
POST /api/memory/{memoryId}/restore
```

恢复仅接受 `source_type=memory` 且当前已禁用的文档；成功后重新启用 memory/chunk，并清理 `deleted_at/delete_reason/duplicate_of`，保留原 embedding。

响应会返回：

- `scanned`
- `eligible`
- `deleted`
- `status`
- `scanLimit`
- `staleThreshold`
- `staleAfterDays`
- `dryRun`

整理重复记忆：

```http
POST /api/memory/consolidate
Content-Type: application/json

{
  "scanLimit": 500,
  "dryRun": true
}
```

定时整理默认关闭：

```yaml
kubeoncall:
  memory:
    consolidation-enabled: false
    consolidation-cron: "0 0 3 * * *"
    consolidation-scan-limit: 500
    duplicate-similarity-threshold: 0.92
    consolidation-lock-ttl-seconds: 1800
```

整理按记忆作用域和主题分组，保留最新 canonical；重复项只软删除，并写入 `duplicate_of` 和 `delete_reason=duplicate_consolidation`。整理同时标准化存量记忆的相对日期。`dryRun=true` 返回 `normalizationEligible` 且不写入；正式执行返回 `normalized`。定时任务通过 Redis `SET NX + TTL` lease lock 互斥；锁 TTL 应大于单次扫描的预期最长耗时。

## Skill 添加

Skill 文件放在：

```text
backend/src/main/resources/skills/*/SKILL.md
```

每个 Skill 使用 YAML frontmatter：

```markdown
---
id: payment-oom-triage
name: Payment OOM Triage
triggers:
  - oom
services:
  - payment-service
maxRisk: MEDIUM
toolWhitelist:
  - kubernetes.describeResource
---
正文经验会注入 planner prompt，但不会直接触发 tool-calling。
```

当前第一版 Skill 只做自动匹配和 prompt 注入；工具白名单过严时 executor 会记录 warning 并按原计划 fallback。

## Metrics

Micrometer 指标通过 `/actuator/metrics` 暴露。关键指标：

- `kubeoncall.graph.executions`
- `kubeoncall.alarm.executions`
- `kubeoncall.alarm.silence_approvals`
- `kubeoncall.rag.retrievals`
- `kubeoncall.rag.result_count`
- `kubeoncall.rag.latency_ms`
- `kubeoncall.memory.operations`
- `kubeoncall.memory.operation_count`
- `kubeoncall.skill.activations`
- `kubeoncall.skill.activated_count`

最小仪表盘建议：

- Alarm：按 `status/degraded/auto_handled` 查看 `kubeoncall.alarm.executions`，关注 `DEGRADED`、`DEDUP_HIT`、`SUPPRESSED`、`RECOVERED` 的比例。
- Silence：按 `outcome` 查看 `kubeoncall.alarm.silence_approvals`，`invalid/failed` 上升时先检查审批请求体、Redis 连接和 key TTL。
- RAG：观察 `kubeoncall.rag.retrievals` 的 `vector_fallback=true` 和 `vector_source=fallback`，再对照 `result_count/latency_ms` 判断向量服务或 rerank 是否退化。
- Memory：按 `operation/outcome` 查看 `kubeoncall.memory.operations`，重点关注 `cleanup/search/remember/consolidate/restore` 的失败。
- Skill：查看 `skill.activations` 与 `skill.activated_count`，无关请求激活率异常升高时检查 Skill trigger 和 service/resourceType frontmatter。

## 审计查看

执行统计：

```http
GET /api/stats
```

审计记录覆盖 Ask、Alarm、Approval Resume 和 Memory cleanup/consolidation/restore，并包含重试、降级、审批、工具成功/失败计数等字段。

`ExecutionAuditRecord.metadata` 保留轻量索引字段，避免塞入大段 prompt 或知识正文：

- Ask：`sessionId`、`plannerSource`、`plannerIntent`、`activatedSkillIds`、`activatedSkillMaxRisk`、`injectedMemoryCount`、`currentTaskId`、`currentTaskType`、`verifierDecision`、`executorKind`、`executorAction`、`executorResultStatus`。
- Alarm：`fingerprint`、`alertName`、`severity`、`policyId`、`policyRagFilters`、`workflowTemplate`、`activeCount`、`alertMemoryRecallCount`、`alertMemoryConsumed`、`alertMemoryConsumedIds`、`repeatIncident`、`suppressed`、`dedupHit`、`recovered`、`nodeNames`、`latestNode`、`silenceApproved`、`silenceApprovedBy`、`silenceApprovalReason`、`silenceApprovalExpiresAt`。
- Memory：`requestType=MEMORY`，metadata 包含 `memoryOperation` 及各操作的扫描、删除、恢复或重复整理摘要字段。

## 生产排障

- 告警未进入工作流：先看 `/api/alarms` 响应是否为 `alarmDedup/alarmSuppressed/alarmRecovery`，再查审计 metadata 中的 `fingerprint/status/policyId`。
- 告警重复过多：确认请求是否传入稳定 `fingerprint`，否则检查标准字段是否足以生成稳定 fingerprint；Redis key 前缀是 `alarm-dedup:`。
- Pod 告警被抑制：查看 metadata 的 `suppressedBy/suppressionKey`，确认同节点是否存在未恢复的 NodeNotReady key。
- P0/P1 没升级：确认 active alarm `count` 是否达到 `p0-escalation-count/p1-escalation-count`，以及 Redis 是否已有 `alarm-ack:{fingerprint}`。
- Silence 没创建：必须同时满足策略 `autoSilence=true`、Redis 存在未过期 `alarm-silence-approval:{fingerprint}`、`alertmanager` executor 可用；审计 metadata 会给出 `silenceApproved/silenceApprovalWarning/latestNode`。
- RAG 检索差：开启 `includeTrace=true` 查看 lexical/vector/fused/rerank 文档 id 和 fallback 原因；先确认 `source_type=memory` 没有污染默认 SOP 检索。
- 记忆不生效：检查 sessionId 是否沿用、`memory.enabled/long-term-enabled` 是否开启、metadata `source_type=memory` 是否存在，以及注入类型是否属于 `SERVICE_FACT/KNOWN_PITFALL`。
- Skill 没激活：查看 `activatedSkillIds` 和 `skillToolWhitelistWarning`，再检查 Skill 的 `triggers/services/resourceTypes/maxRisk/toolWhitelist`。
