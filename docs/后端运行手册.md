# KubeOnCall 后端运行手册

## 本地启动

基础验证命令：

```bash
./mvnw test
```

本地运行：

```bash
./mvnw spring-boot:run
```

默认 profile 为 `local`，配置入口在 `src/main/resources/application.yml` 和 `application-local.yml`。

## 集成依赖

默认单测不依赖 Redis、Elasticsearch、MinIO。需要完整联调时先启动外部依赖：

```bash
docker compose up -d redis elasticsearch minio
```

当前存储约束：

- Redis：session、approval、audit、active alarm、短期抑制和升级状态。
- Elasticsearch：知识库、长期记忆。
- MinIO：原始知识文档。

## 告警策略

策略文件固定在：

```text
src/main/resources/alarm-policies.yml
```

核心配置前缀：

```yaml
kubeoncall:
  alarm:
    policy-location: classpath:alarm-policies.yml
    p0-dedup-ttl-seconds: 1800
    p1-dedup-ttl-seconds: 1200
    node-not-ready-suppression-ttl-seconds: 1800
    escalation-ttl-seconds: 3600
    silence-approval-ttl-seconds: 1800
```

`ResultPushNode` 只输出诊断摘要；`SilenceNode` 只有策略 `autoSilence=true` 且 Redis 中存在未过期人工审批时才会调用 `alertmanager.createSilence`。

人工批准一次 silence：

```http
POST /api/alarms/silence-approvals
Content-Type: application/json

{
  "fingerprint": "fp-payment-oom",
  "approvedBy": "incident-commander",
  "reason": "maintenance window",
  "ttlSeconds": 1800
}
```

审批状态写入 Redis key `alarm-silence-approval:{fingerprint}`，过期后工作流会自动回到“不创建 silence”的安全路径。

## RAG 重建

写入知识：

```http
POST /api/knowledge/ingest
```

检索知识：

```http
POST /api/knowledge/query
```

可选参数：

- `topK`
- `retrieveMethod`: `KEYWORD`、`VECTOR`、`HYBRID`
- `includeTrace`

默认 vector 关闭；真实 embedding、ES kNN、rerank 服务都通过 `kubeoncall.rag.*` 配置启用。

开启 `includeTrace=true` 时，`diagnostics` 会包含检索和 rerank 的轻量 trace：

- `lexicalDocumentIds`、`vectorDocumentIds`、`fusedDocumentIds`
- `rerankInputDocumentIds`、`rerankedDocumentIds`
- `rankTrace`: 每个最终文档的 `rank/documentId/ruleScore/crossEncoderScore`
- `rerankStrategy`、`crossEncoderFallback`、`crossEncoderFallbackReason`

## 记忆清理

长期记忆以 `source_type=memory` 写入知识库，默认不会污染 SOP 检索。

告警记忆只沉淀结构化处置摘要；写入前会过滤包含 `kubectl` 命令、实时值、当前值的摘要片段。

清理陈旧记忆：

```http
POST /api/memory/cleanup
Content-Type: application/json

{
  "scanLimit": 500
}
```

清理阈值由以下配置控制：

```yaml
kubeoncall:
  memory:
    stale-after-days: 30
```

清理过程只删除 `source_type=memory` 且 `updated_at` 早于阈值的长期记忆文档。响应会返回：

- `scanned`
- `deleted`
- `status`
- `scanLimit`
- `staleThreshold`
- `staleAfterDays`

## Skill 添加

Skill 文件放在：

```text
src/main/resources/skills/*.md
```

每个 Skill 使用 YAML frontmatter：

```markdown
---
id: payment-oom-triage
name: Payment OOM Triage
triggers:
  - oom
services:
  - payment-service
maxRisk: MEDIUM
toolWhitelist:
  - kubernetes.describeResource
---
正文经验会注入 planner prompt，但不会直接触发 tool-calling。
```

当前第一版 Skill 只做自动匹配和 prompt 注入；工具白名单过严时 executor 会记录 warning 并按原计划 fallback。

## Metrics

Micrometer 指标通过 `/actuator/metrics` 暴露。关键指标：

- `kubeoncall.graph.executions`
- `kubeoncall.alarm.executions`
- `kubeoncall.alarm.silence_approvals`
- `kubeoncall.rag.retrievals`
- `kubeoncall.rag.result_count`
- `kubeoncall.rag.latency_ms`
- `kubeoncall.memory.operations`
- `kubeoncall.memory.operation_count`
- `kubeoncall.skill.activations`
- `kubeoncall.skill.activated_count`

最小仪表盘建议：

- Alarm：按 `status/degraded/auto_handled` 查看 `kubeoncall.alarm.executions`，关注 `DEGRADED`、`DEDUP_HIT`、`SUPPRESSED`、`RECOVERED` 的比例。
- Silence：按 `outcome` 查看 `kubeoncall.alarm.silence_approvals`，`invalid/failed` 上升时先检查审批请求体、Redis 连接和 key TTL。
- RAG：观察 `kubeoncall.rag.retrievals` 的 `vector_fallback=true` 和 `vector_source=fallback`，再对照 `result_count/latency_ms` 判断向量服务或 rerank 是否退化。
- Memory：按 `operation/outcome` 查看 `kubeoncall.memory.operations`，重点关注 `cleanup/search/remember` 的失败。
- Skill：查看 `skill.activations` 与 `skill.activated_count`，无关请求激活率异常升高时检查 Skill trigger 和 service/resourceType frontmatter。

## 审计查看

执行统计：

```http
GET /api/stats
```

审计记录覆盖 Ask、Alarm、Approval Resume，并包含重试、降级、审批、工具成功/失败计数等字段。

`ExecutionAuditRecord.metadata` 保留轻量索引字段，避免塞入大段 prompt 或知识正文：

- Ask：`sessionId`、`plannerSource`、`plannerIntent`、`activatedSkillIds`、`activatedSkillMaxRisk`、`injectedMemoryCount`、`currentTaskId`、`currentTaskType`、`verifierDecision`、`executorKind`、`executorAction`、`executorResultStatus`。
- Alarm：`fingerprint`、`alertName`、`severity`、`policyId`、`workflowTemplate`、`activeCount`、`alertMemoryRecallCount`、`suppressed`、`dedupHit`、`recovered`、`nodeNames`、`latestNode`、`silenceApproved`、`silenceApprovedBy`、`silenceApprovalReason`、`silenceApprovalExpiresAt`。

## 生产排障

- 告警未进入工作流：先看 `/api/alarms` 响应是否为 `alarmDedup/alarmSuppressed/alarmRecovery`，再查审计 metadata 中的 `fingerprint/status/policyId`。
- 告警重复过多：确认请求是否传入稳定 `fingerprint`，否则检查标准字段是否足以生成稳定 fingerprint；Redis key 前缀是 `alarm-dedup:`。
- Pod 告警被抑制：查看 metadata 的 `suppressedBy/suppressionKey`，确认同节点是否存在未恢复的 NodeNotReady key。
- P0/P1 没升级：确认 active alarm `count` 是否达到 `p0-escalation-count/p1-escalation-count`，以及 Redis 是否已有 `alarm-ack:{fingerprint}`。
- Silence 没创建：必须同时满足策略 `autoSilence=true`、Redis 存在未过期 `alarm-silence-approval:{fingerprint}`、`alertmanager` executor 可用；审计 metadata 会给出 `silenceApproved/silenceApprovalWarning/latestNode`。
- RAG 检索差：开启 `includeTrace=true` 查看 lexical/vector/fused/rerank 文档 id 和 fallback 原因；先确认 `source_type=memory` 没有污染默认 SOP 检索。
- 记忆不生效：检查 sessionId 是否沿用、`memory.enabled/long-term-enabled` 是否开启、metadata `source_type=memory` 是否存在，以及注入类型是否属于 `SERVICE_FACT/KNOWN_PITFALL`。
- Skill 没激活：查看 `activatedSkillIds` 和 `skillToolWhitelistWarning`，再检查 Skill 的 `triggers/services/resourceTypes/maxRisk/toolWhitelist`。
